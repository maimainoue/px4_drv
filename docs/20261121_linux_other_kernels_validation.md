# Linux の別カーネル版での検証 (2026年11月21日)

この文書は、`px4_drv` の Linux 版を、6.12 以外のカーネル (Debian 12 の通常カーネル 6.1 と、Ubuntu 24.04 のカーネル 6.8) と、複数機材の同時受信で確かめた記録です。
各機種の文書 ([dt295](devices/dt295.md)、[xz](devices/xz.md)) の「未確認」の項目のうち、ここで確認できたものを反映しています。

検証したコードは、`refactor/restructure-clean` の `78e7ffc` (`px4_drv` 0.7.1) です。

## 検証環境

| 項目 | 内容 |
|---|---|
| ホスト | 実機 (AMD Ryzen 7 5700U、メモリ 8 GB)。Debian 13、カーネル 6.12.117。検証の間、ホストの `px4_drv` と `denpa` は止めた |
| 仮想マシン | ホストのコンテナ内の QEMU 10.0.13 / KVM (2 vCPU、メモリ 3 GB)。機材は `usb-host` (`hostbus`、`hostport`) で渡した |
| ゲスト A | Debian 12、通常カーネル 6.1.0-56-amd64 (GCC 12.2) |
| ゲスト B | Ubuntu 24.04.5 LTS、カーネル 6.8.0-151-generic (GCC 13.3) |
| 機材 | 10 台: TBS 5530、Sony CECH-ZD1 J 3 台、PIX-DT295 Rev.01 と Rev.02、GV-MVP/XZ、PX-Q3U4 2 台、PX-S1UD V2.0 (カードリーダーは渡していない) |
| 受信 | UHF 21ch (PX-S1UD V2.0 だけ 16ch)。試験ツールは `PTX_SET_CHANNEL` と `PTX_START_STREAMING` で受信し、TS の同期ずれ、TEI、連続性の飛びを数える |
| 注意 | すべて仮想マシン経由の結果。物理マシンでの受信とは、USB の遅延などが違う可能性がある |

仮想マシンを作るときの注意は、次のとおりです。

- Debian 12 の cloud イメージは、既定の cloud カーネル (`6.1.0-56-cloud-amd64`) のままだと、機材を扱うには USB が足りない。通常カーネル (`linux-image-amd64`) を入れて、cloud カーネルを外した。Ubuntu 24.04 の cloud イメージは、`linux-image-generic` を入れると、そのまま通常カーネルで起動した。
- cloud カーネルには、QEMU の既定の NIC (`e1000`) のドライバーがない。`virtio-net-pci` を指定した。
- `qemu-xhci` は、既定の 4 ポートだと仮想の full speed ハブが挟まり、機材が 12M で見える。`p2=16,p3=16` でポートを増やすと、実機と同じ速度で見える。
- Linux 標準の `smsusb` が、PX-S1UD V2.0 を先に握る (どちらのゲストも)。`smsusb` から unbind して、`px4_usb` へ結び付けた ([Siano の別紙](siano_tuners.md))。

## 10 機材の同時受信 (10 分)

| 機種 (デバイスファイル) | パケット | TEI (6.1 / 6.8) | 連続性エラー (6.1 / 6.8) | 同期ずれ |
|---|---|---|---|---|
| PIX-DT295 Rev.02 (`dt295video0`) | 11,952,128 | 0 / 0 | 0 / 0 | 0 |
| GV-MVP/XZ (`xzvideo0`) | 6,889,472 | 0 / 0 | 0 / 0 | 0 |
| Sony CECH-ZD1 J (`tornevideo1`) | 6,889,472 | 0 / 0 | 0 / 0 | 0 |
| Sony CECH-ZD1 J (`tornevideo2`) | 6,889,472 | (6.1 は未実施) / 0 | (同左) / 0 | 0 |
| PX-S1UD V2.0 (`px4video8`) | 6,889,472 | 0 / 0 | 0 / 0 | 0 |
| PX-Q3U4 (`px4video2`) | 6,889,472 | 8,148 / 6,621 | 161 / 111 | 0 |
| PX-Q3U4 (`px4video3`) | 6,889,472 | 7,722 / 5,917 | 109 / 108 | 0 |
| PX-Q3U4 (`px4video6`) | 6,889,472 | 6,125 / 0 | 61 / 0 | 0 |
| PX-Q3U4 (`px4video7`) | 6,889,472 | 6,151 / 6,187 | 63 / 74 | 0 |
| TBS 5530 (`tbs5530video0`) | 6.1: 11,296,768、6.8: 10,760,192 | 6 / 8 | 783,427 / 950,923 | 0 |

- **PX-Q3U4:** 4 ノードのうち、6.1 は 4 ノード、6.8 は 3 ノードに、同じ規模の TEI (約 0.1%) と、少数の連続性エラーが出ました。同期ずれは 0 で、USB の取りこぼしではなく、復調器が訂正できないエラーと考えられます。
  実機のホスト (カーネル 6.12.117) の同時受信でも、PX-Q3U4 だけに、断続的に同様の誤りが出ています ([20261113_common_fixes.md](20261113_common_fixes.md))。カーネルの版ではなく、アンテナ側の信号の条件によるとみられます。確認はしていません。
- **TBS 5530:** 連続性エラーが多く出ました。ヌルを除くパケットに対して、6.1 は約 10.7% (783,427 / 7,329,043)、6.8 は約 12.9% (950,923 / 7,376,853) で、実機のホストの 10 台同時受信 (120 秒) の約 8.8% (同じ数え方) と、同程度です。仮想マシンを介さない場合と大きく変わらないため、仮想マシンのパススルーだけが原因ではありません ([TBS 5530 の別紙](devices/tbs5530.md))。
- **Sony CECH-ZD1 J の 3 台目 (`tornevideo2`):** モジュールの読み込み後、最初の選局が、どちらのゲストでも `ETIMEDOUT` で失敗しました。6.1 では、続く 3 回も `EAGAIN` で、別のチャンネル (16ch) で成功した後は、21ch も受信できました。6.8 では、別のチャンネル (16ch) で先に選局すると、以降は受信できました。
  実機のホストでも、初回の選局が失敗する例があり、原因は未確認です。6.1 の 10 分の同時受信には、この機材を入れていません (別のチャンネルで 3 秒、TEI 0、連続性エラー 0)。
- **PIX-DT295 Rev.01** は、試した全チャンネルでロックしません (`EAGAIN`)。実機のホストの結果と同じです。Sony CECH-ZD1 J の 1 台目 (`tornevideo0`) は、選局できますが、全パケットがヌルで、信号がありません。

## 未確認のこと

- カーネル 6.1 と 6.8 での PX-MLT 系、ISDB2056 系、ISDBT2071 系、T230C / T230A の実機 (機材がない)。
- PX-Q3U4 の ISDB-S (アンテナがない)。B-CAS カードの通信 (カードリーダーを仮想マシンへ渡していない)。
- 24 時間級の連続受信、USB の物理的な抜去、`DEBUG_ATOMIC_SLEEP` や KASAN を有効にしたカーネル。
- 6.1 と 6.8 と 6.12 以外のカーネル (6.13 以降、6.2〜6.7、6.9〜6.11、LTS の 5.10、5.15、6.6、arm64)。
- PX-Q3U4 の誤りと TBS 5530 の連続性エラーの原因の切り分け (カーネルの版、仮想マシンの影響、アンテナ)。
