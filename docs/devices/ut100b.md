# Quixun QRS-UT100B (ASICEN ASV5211) の調査記録

## この資料の位置づけ

QRS-UT100B は、px4_drv の Linux カーネルモジュールと、DriverHost_PX4 (Windows、Linux の libusb 版、macOS) が、ISDB-T の受信と内蔵 B-CAS カードの読み出しに対応しています (実験的)。
この資料は、同じ USB ブリッジ (ASICEN ASV5211) を使う [GV-MVP/HZ2W](hz2w.md) の調査の延長として、UT100B の実機から分かったことと、px4_drv での実装、確認した範囲をまとめた記録です。
前半は、firmware の起動、機器の識別情報、内蔵 B-CAS カードの読み出し、TS の受信、64 ビット Windows でのドライバーの扱いを扱います。受信は、recfriio (Linux) と BonDriver_HDP2 (Windows) の 2 つの既存の経路で確かめました。
px4_drv での実装と、その確認結果は、[px4_drv での対応](#px4_drv-での対応) にあります。

確認は 2026-11-25 に、次の環境で行いました。

| 呼び名 | 内容 |
|---|---|
| 検証 PC | Windows 11 Pro (x64、build 26200)。UT100B を直接つないだ。Secure Boot は無効、仮想化ベースのセキュリティ (VBS) は動作中 |
| 検証 VM | Windows 10 Pro (x64、build 19045) の仮想マシン。Secure Boot を無効、テスト署名モードを有効にしてある。UT100B は、USB パススルーでつないだ |
| 検証ホスト | VM を動かす Linux (Debian) の物理マシン。UT100B をつなぎ、`recfriio` と、libusb 版の DriverHost_PX4 を直接実行した |

UT100B と同じ作りの機種 (MonsterTV HDUS / HDUC など) は、対象にしていません。
recfriio (waya0125/recfriio、MIT) の `docs/QRS-UT100B.md` が、UT100B の命令表、起動手順、Linux での受信の確認をまとめています。この資料は、そこに書かれた手順 (起動時の GPIO) を実機で再現した結果を含みます。

## 機器の概要

| 項目 | 内容 |
|---|---|
| USB ブリッジ | ASICEN ASV5211 (HZ2W と同じ) |
| カードの IC | ASIE5606 (I2C `0x4a`)。HZ2W の ASIE5606B と、レジスタ 9 の値 (`06`) が同じ |
| cold の USB ID | `1738:5211` (製造元 `ASICEN`、製品名 `AUSBDTV`、`bcdDevice` `0001`)。**HZ2W と同じで、ディスクリプターでは区別できない** |
| warm の USB ID | `3275:7020` (製造元 `Quixun`、製品名 `Quixun HDTV`、`bcdDevice` `0001`) |
| インターフェース | 複合デバイス。MI_00 が `Quixun HDTV`、MI_01 が `Quixun IR2HID` (リモコン) |
| シリアル番号 | なし (`iSerialNumber` が 0。EEPROM にも個体で変わる値がない) |

cold の USB ID は、Quixun と SKNET のローダーの INF (`Quixun_AS11Loader.inf`、`SKNET_AS11Loader.inf`) にも `1738:5211` と書かれています。

## firmware の起動

製品の付属 CD (`ROBRO_Origin` と `ROBRO_Origin+（forNetbook)` の 2 種) の `Driver` フォルダにある `Quixun_AS11Loader.sys` から、`fwtool/asv5211fw` で firmware を取り出し、cold の機器へ送りました。
送る手順は、[HZ2W の資料](hz2w.md)の `hz2w_fw_load` と同じです (vendor 要求 `0xab` を 3 回、`0xac` を 1 回、`wIndex` は起動アドレス)。送信には、WinUSB を使う確認用のツール (リポジトリには含まれない) を使いました。

| firmware | 起動アドレス | SHA-256 の先頭 | 結果 |
|---|---|---|---|
| ROBRO Origin のローダー (版 1.08.11.17、2008-11-17) の主の版 | `0x5399` | `1f70eb59` | 4 つの転送がすべて成功。約 6 秒後に `3275:7020` で出直した |
| ROBRO Origin+ (forNetbook) のローダー (版 1.09.02.19、2009-02-19) の主の版 | `0x53e4` | `50d406d5` | 挿し直して cold に戻した後、同じ手順で成功 |
| I-O DATA の GV-MVP/HZ2W 用 (`0x5583`) | `0x5583` | `39428b36` | 挿し直して cold に戻した後、成功。`3275:7020` で出直した (`04bb:0526` ではない) |
| SKNET のローダーの 2 つ目 (`0x55d8`) | `0x55d8` | `f4848c8c` | 送っていない |

ローダーの 2 つ目の firmware (`0x515f`、古い版) は、ローダーが送らない版で、試していません。

firmware の版による差は、見つかっていません。出直した後の標準ディスクリプター、`GetCusInfo`、起動時の GPIO への応答は、どの firmware でも同じでした。
warm の機器が名乗る USB ID と文字列は、firmware ではなく、基板の EEPROM から来るとみられます。このため、cold の `1738:5211` へ HZ2W 用の firmware を送っても、UT100B は warm で起動します。ASV5211 を使う他社の機器と、cold の USB ID が共通であることに注意が要ります。

## 機器の識別情報

warm にした UT100B から、読み出しだけの要求で取りました。

| 項目 | 結果 |
|---|---|
| `GetCusInfo` (要求 `0x0c`、58 バイト) | 状態 `01`、`ae 36`、VID/PID `3275 7020` (ビッグエンディアン)、`"Quixun    "`、`"Quixun HDTV     "`、`"Quixun IR2HID  "`、末尾 `0c`。HZ2W と同じ構造 |
| EEPROM (I2C `0xa8`、256 バイト) | `0x00`〜`0x35` は `GetCusInfo` の先頭と一致。`0x38` が `0c`、`0x39`〜`0xbf` はすべて `0x00`、`0xc0`〜`0xff` はすべて `0xff` |

個体を区別できる値は、見つかっていません。読んだのは 1 台だけです。
I2C の `0xa0` は 256 回とも状態 1 で全バイトが `0xff` でしたが、実在する EEPROM かは区別していません。

I2C の読み出し (要求 `0x02`) は、起動時の GPIO を送る前は、`0xa0`〜`0xae`、`0x4a`、`0x4c` のどれも応答しません。起動時の GPIO を送ると、`0x4a` (ASIE5606) と `0xa8` (EEPROM) が応答します (`0x5a` と `0x4c` は応答しない)。
起動時の GPIO は、要求 `0x17` (値 2) の読み出し、GPIO `0xfb`/`0x07`、拡張 GPIO `0x02`/`0x00`、チューナー電源 (`0x08`)、ASIE5606 のリセットのパルス (`0x11`)、`0xd5` のパルスを、recfriio の UT100B の `Open()` と同じ順に送ったものです。

## 周期処理と、機器が消える現象

[HZ2W の資料](hz2w.md#周期的な処理と機器が消える現象)にある現象 (起動時の書き込みの後、周期処理を止めると USB から消える) が、UT100B でも起きました。

- 起動時の GPIO と ASIE5606 の操作を送り、周期処理 (`0x4a` のレジスタ 4 の読み出しを 437.5 ミリ秒ごと、要求 `0x22` を 6.25 秒ごと) を別のスレッドで送り続けた間は、機器は USB に残りました。
- 確認用のツールが閉じる手順を送らずに終わると、機器は USB から消え、cold に戻らず、挿し直すまで現れませんでした。
- firmware を送っただけで、起動時の書き込みをしていない warm は、周期処理がなくても 10 分以上残ることがありました。自然に cold へ戻ることもありました。この差の原因は調べていません。

## 内蔵 B-CAS カードの読み出し

warm の UT100B の内蔵スロットに B-CAS カードを挿した状態で、[HZ2W の共通層](hz2w.md#内蔵カードの読み出し-qrs-ut100b) (`hz2w_card`) を、WinUSB の確認用ツールの上で動かしました。

| 項目 | 結果 |
|---|---|
| カードの検出 | 成功 (`0x4a` のレジスタ 4 の bit 0) |
| 電源投入と ATR | 成功。ATR は 13 バイトで、HZ2W のカードと同じ値 |
| T=1 の RESYNCH | 応答は `00 e0 00 e0` で、正しい形 |
| T=1 の IFS (S ブロックで 124 を要求) | 応答は `00 e1 01 7c 9c` で、受け入れられた |
| 初期化命令 (`90 30 00 00 00`)、IFS の後 | 65 バイトの 1 つのブロック (LEN 61)。フレームの長さと LRC が合い、末尾は SW `90 00` |

2 枚の B-CAS カードで試しました。IFS を送ると、1 枚目も 2 枚目も、上の結果 (65 バイトの 1 ブロックと SW `90 00`) になりました。IFS を送らず、カードの既定のブロックの上限のまま命令を送ると、返り方がカードで違いました。1 枚目は、LEN が 30 のまま、63 バイトの 1 つのフレームで返りました (全体の LRC は合うが、LEN は全長と合わない。2 回続けて同じで、レジスタ 3 は命令の 120 ミリ秒後に 63 で安定)。2 枚目は、36 バイトと 33 バイトの 2 ブロック (INF が 32 バイトと 29 バイト) で返り、R ブロックで続きを取ると、末尾が SW `90 00` になりました。
1 枚目の 63 バイトは、ASIE5606 が、チェーンの 2 ブロックを 1 つのフレームにまとめたとも見えますが、確認していません。ホストの `SmartCard` は、RESYNCH の後に IFS を交渉するため、この形にはならないはずです。

## TS の受信

地上波の T27 (NHK 総合、557 MHz) を、アンテナを接続した状態で受信し、保存した TS を調べました。調べた項目は、188 バイト境界の同期外れ、TEI、パケットごとの連続性カウンター (PID ごと)、ヌルパケット、スクランブル制御ビットです。

| 経路 | 内容 | 結果 |
|---|---|---|
| Linux、`recfriio -hdp` | 検証ホストで、warm の機器 (起動後) を直接開き、20 秒録画。firmware は、`recfriio` の `-firmware` で送れる (Origin 版) | 204,537 パケット (約 15.4 Mbps)。同期外れ 0、TEI 0、連続性エラー 0。スクランブルのパケットが 196,833 個 (約 96%)。CNR は約 30 dB |
| Linux、`recfriio -hdp -b25` | 内蔵スロットの B-CAS で復号しながら、30 秒録画 (カードは ASIE5606 revision 3) | 329,074 パケット。同期外れ 0、TEI 0、連続性エラー 0、スクランブルのパケット 0 |
| Windows、`BonDriver_HDP2.dll` (32 ビット) | 検証 VM で、`uusbd64` を通して読み込み、`27ch` を選局して 20 秒保存。確認用の読み込みツール (リポジトリには含まれない) を 32 ビットでビルドして使った。チューナー名は `HDP2`、信号レベルは 34 | 216,431 パケット (16.28 Mbps)。同期外れ 0、TEI 0、連続性エラー 0、スクランブルのパケットが 0 |

Windows の経路は、保存した TS のスクランブルが、復号の設定をしていないのに 0 でした。`BonDriver_HDP2` が、内蔵スロットのカードで復号しているとみられますが、設定の確認はしていません。

cold の機器を、ほかの常駐ソフトが先に見つけて firmware を送ることがあります (検証 VM の Linux では、録画用の常駐エージェントが、cold の `1738:5211` へ firmware を自動で送り、再列挙の後にゲストへ戻らなかった)。UT100B を試すときは、そうしたソフトを止めるか、検証ホストで直接実行してください。

## 64 ビット Windows でのドライバー

付属 CD の BDA ドライバーなどは、32 ビット (x86) だけです。

| ドライバー | 結果 |
|---|---|
| `Quixun_HDTV_N_BDA.inf` / `.sys` (CD の BDA) | Windows のカタログは有効 (Microsoft の署名)。ドライバーストアには追加できるが、`.sys` が x86 で、INF に `NTamd64` の記述もなく、x64 の機器には当たらない (検証 PC の MI_00 は、問題コード 28 のまま) |
| `uusbd64.inf` / `.sys` (SKNET の 64 ビット版同梱、`BonDriver_HDP2` 用) | `.sys` が未署名で、INF にカタログもない。そのままでは、Secure Boot が有効な検証 VM のドライバーストアにも追加できない (「サードパーティの INF にデジタル署名情報が含まれていません」) |
| `uusbd64` を自己署名で導入 (検証 VM) | INF を直し (`CatalogFile`、`SourceDisksFiles` の追加と、INF 自身をコピーする記述の削除)、`.sys` とカタログに px4_drv の自己署名証明書で署名した。検証 VM で Secure Boot を無効、テスト署名モードを有効にすると、ドライバーストアへの追加に成功し、カーネルドライバーとして `RUNNING` になった |

検証 VM に UT100B をつなぐと、MI_00 (`Quixun HDTV`) がテスト署名した `uusbd64` (`oem6.inf`) に当たり、`status=OK`、問題コード 0 になりました。MI_01 (リモコン) には、ドライバーがありません。

検証 PC には、`3275:7020` へ WinUSB を当てる調査用の INF を、起動時の GPIO と B-CAS の読み出しの確認のために入れました (リポジトリには含まれない、自己署名)。この INF が当たると、複合デバイスの子 (MI_00、MI_01) は作られません。

## px4_drv での対応

### 構成

| 項目 | 内容 |
|---|---|
| 共通層 | `driver/common/ut100b/` (`ut100b_core`: 起動、選局、TS の開始と停止、ロックと CNR の読み出し。`ut100b_stream`: TS の復号と境界の整列)。カードは [HZ2W の共通層](hz2w.md) (`hz2w_card`) を使う |
| ホスト | `host/devices/ut100b_device.cpp` (`Ut100bDevice`)。ISDB-T の受信機 1 つ (index 0) と内蔵カードリーダー |
| Linux のカーネルモジュール | `driver/linux/ut100b_device.c`。`/dev/ut100bvideo*` (ISDB-T) と `/dev/px4card/*` (内蔵カード) を作る。手順は `Ut100bDevice` と同じで、周期処理は専用のカーネルスレッドが送る。USB の VID が Siano RIO と同じため、`px4_usb.c` の Siano の分岐で製品 ID を見て振り分け、複合デバイスの MI_00 だけを受け持つ。warm の機器だけが対象で、cold への firmware の送信は、ユーザー空間のホストが行う |
| 機種の識別 | `DriverHost_PX4.ini` の `Type="UT100B"`、`VendorId=0x3275`、`ProductId=0x7020`。warm の機器だけが対象 |
| Windows のドライバー | `winusb/pkg/inf/Quixun-QRS-UT100B.inf`。親デバイス `USB\VID_3275&PID_7020` へ WinUSB を当てる (子の MI_00 と MI_01 は作られない) |
| BonDriver | `BonDriver_UT100B` (`dist/BonDriver_UT100B_32bit`、`_64bit`) |
| カードリーダー | Windows は WinSCard_PX4 経由。macOS と Linux の PC/SC 用 IFD ハンドラーに `Quixun QRS-UT100B Smart Card Reader` を追加 |

TS は、ASIE5606 が 1 パケットごとに DES で暗号化して送ります (ヘッダーの 4 バイトは平文。184 バイトに、固定のパターンとの XOR の後、先頭 128 バイトと残りで別の鍵の DES-ECB)。復号は `ut100b_stream` が行い、先頭の 32 KB は、機器の FIFO に残っていた古いデータとして捨て、188 バイトの境界を 0x47 で合わせ直します。
FIFO (約 260 KB) は TS の開始から溜まるため、`ut100b_stream_start` は、URB を投入する直前にだけ呼びます。選局 (`ut100b_tune`) は、周波数の設定だけで、TS を開始しません。
`ut100b_stream_start` の末尾には、recfriio の選局と同じ 150 ミリ秒の待ちがあります。待ちの間も FIFO に溜まり、約 15 Mbps では FIFO の容量 (約 260 KB とみられる) を超える計算になりますが、読み出しの先頭から数えた連続性エラーは、確認した範囲 (7 チャンネル × 2 周の録画) で 0 件でした。待ちを短くした場合の動作は確認していないため、recfriio の手順のまま置いています。
区切りの確認は、先頭、188、376 バイト後の 3 か所がすべて 0x47 になる位置で行います。確認に使う位置がまだ届いていない候補は、確定せずに持ち越します (一括で渡しても、分けて渡しても、同じ位置に同期します)。

firmware は、cold の `1738:5211` へ、HZ2W の cold の定義 (`DeviceDefinition` の HZ2W) が送ります。UT100B は HZ2W と cold の USB ID が同じため、機器の取り違えを防げません。[firmware の起動](#firmware-の起動) のとおり、HZ2W 用の `0x5583` (`Hz2wBootIndex` の既定値) で UT100B も起動します。ROBRO Origin 版の firmware を使う場合は、`Hz2wBootIndex` を `0x5399` にします。

### 設定項目

| キー | 既定値 | 内容 |
|---|---|---|
| `Ut100bMaxUrbs` | 32 | 同時に投入する bulk の URB の数 (1 本は 16 KB)。`ReceiverMaxPackets` は 16384 |
| `Ut100bLockSettleMs` | 300 | 選局でロックを検出してから TS を開始するまでの待ち時間 (ミリ秒) |

### カード

`hz2w_card` は、HZ2W では ASIE5606B のリセットと TS 設定 (レジスタ 5) を毎回行います。UT100B では、同じ IC が TS の DES の設定を持つため、これらを行うと受信中の TS が壊れます。このため、`keep_ic_state` で IC のリセットとレジスタ 5 の書き込みを省き、代わりに、レジスタ 0 に `0x80`、10 ミリ秒の待ち、レジスタ 0 に `0` の準備だけを行います (recfriio と同じ順)。
IFS (S ブロックで 124) の交渉が必要で、行わないと、[内蔵 B-CAS カードの読み出し](#内蔵-b-cas-カードの読み出し) のとおり、カードによって返り方が分かれます。

### 確認した範囲

Linux は検証ホストで、libusb 版の DriverHost_PX4 (UT100B だけを有効にした定義) と、`px4rec` を使いました。地上波の T27 (アンテナ接続済み) です。

| 条件 | 結果 |
|---|---|
| 20 秒の受信 (生の TS) | 219,614 パケット。同期外れ 0、TEI 0、連続性エラー 0 |
| 30 秒の受信 + B-CAS の復号 | スクランブルのパケット 0。エラー 0 |
| 7 チャンネル × 2 周 (各 6 秒、復号あり) | 全区間でエラー 0 |
| 1 回の接続で、チャンネルを 10 回切り替え (各 5 秒) | TEI 0。最後の区間だけ、連続性エラーが 5 件 (原因は未調査) |
| 120 秒の受信中に、カード命令を 150 回 | TS のエラー 0。カード命令の失敗 0、最大 415 ミリ秒 |
| 10 分の録画中に、カード命令を約 1,400 回 | 6,066,611 パケット (約 1.1 GB)。TS のエラー 0。カード命令の失敗 0 |
| 30 分の録画 (生の TS) 中に、カード命令を 1,700 回 | 18,227,248 パケット (約 3.4 GB)。同期外れ 0、TEI 0、連続性エラー 0。カード命令の失敗 0、最大 297 ミリ秒 |
| 録画中に、USB の認証を取り消して (`authorized` を 0)、6 秒後に戻す | ホストは動作を続け、録画のコマンドは終了。その後の 8 秒の録画は、エラー 0 |

Linux のカーネルモジュールは、検証 VM とは別の、Debian (カーネル 6.12) の仮想マシンに UT100B を USB パススルーでつないで確認しました。27ch (アンテナ接続済み) で、`tools/` の確認ツールを使いました。

| 条件 | 結果 |
|---|---|
| 60 秒の受信 | 600,979 パケット。同期外れ 0、TEI 0、連続性エラー 0 |
| 120 秒の受信中に、カード命令を 0.5 秒間隔で | 1,136,073 パケットでエラー 0。カードの往復 240 回、失敗 0、最大 323 ミリ秒 |

### 実装で分かったこと

- 機器の `GetCusInfo` が `3275 7020` を返さない場合は、`-ENODEV` で開きません。ASIE5606 のレジスタ 9 (identity) の下位 3 ビットが `6` でない場合も同じです。
- 周期処理 (レジスタ 4 の読み出しと要求 `0x22`) は、ホストの別のスレッドが送ります。終了時は、カードの電源を切り、`ut100b_board_close` で閉じる手順を送ってから、周期処理を止めます。
- 選局の直後は、ロックの検出を待ってから TS を開始します。ロックの前に開始すると、ロックしていない間の TS が混ざります。
- 取り外しの確認で、`/sys/bus/usb/drivers/usb/unbind` で機器を外した場合は、`authorized` の場合と結果が違いました。`unbind` は USB の機器そのものを外さず、libusb のホットプラグの通知が出ないため、ホストは再接続を検出しませんでした。また、録画中の `unbind` では、ホストの終了が止まりました (受信機の破棄が、クライアントの Close を待ち、その Close が、カードの切断の応答を待つクライアントから来ないため)。この待ちは、他の機種の `Receiver` の破棄と同じ構造ですが、他の機種で再現するかは確認していません。
