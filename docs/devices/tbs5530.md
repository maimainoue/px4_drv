# TurboSight TBS 5530 の対応計画 (ISDB-T)

TBS 5530 (`734c:5530`) の地上波 (ISDB-T) 受信を、px4_drv へ加えるための設計記録です。
実装前の計画であり、実機で確認した内容は「確認結果」の節へ、確認した順に追記します。

## 対象と範囲

| 項目 | 内容 |
|---|---|
| 対象 | TurboSight TBS 5530 (USB `734c:5530`) |
| 放送 | ISDB-T の 1 チューナー |
| 対象外 | ISDB-S (BS/CS)。衛星側の M88RS6060 は DVB-S/S2 専用のため、このボードでは受信できません |
| 後から追加 | ISDB-C / J.83B。復調器 CXD2878ER は対応しますが、起動手順を別途起こす必要があります。初回の実装では、後から足せる構造だけを用意します |
| 内蔵カードリーダー | なし (対象外) |

TBS 5530 は、衛星用と地上・ケーブル用の 2 つの復調器を持ち、TS は 1 本のバルクエンドポイントへ、ブリッジの GPIO で切り替えて流します。
多重化ではなく切り替えなので、受信できるのは一度に 1 チャンネルです。
このため、px4_drv では 1 チューナー (`TBS5530_CHRDEV_NUM 1`) として公開します。

## 構成

```
USB (Cypress FX2 系ブリッジ、毎回ファームウェアを RAM へ送る)
 ├─ 制御転送: ファームウェア送信、I2C、GPIO、EEPROM
 └─ バルク EP 0x82: TS
      └─ セレクター (GPIO で選択)
           ├─ CXD2878ER (地上/ケーブル、内蔵チューナー)  ← 対象
           └─ M88RS6060 (衛星)                          ← 対象外
```

| 層 | ファイル | 内容 |
|---|---|---|
| 共通 | `driver/common/tbs5530/tbs5530_core.c/.h` | 制御転送の I2C、GPIO、ファームウェア送信 (USB の転送関数を差し込める形にして、模擬 I/O で試験できるようにしています)、CXD2878ER の起動、選局、ロック判定、C/N、強度、内蔵チューナー (ASCOT3 / Freia。実機で読んだチューナー ID で分岐します)、ISDB-C の選局 |
| Linux | `driver/linux/tbs5530_device.c/.h` | `ptx_chrdev` の ops、受信スレッド、寿命管理、ファームウェアの読み込み (`request_firmware`) |
| Linux | `driver/linux/px4_usb.c`、`px4_usb.h`、`driver/Kbuild` | USB ID の登録と、機種別デバイスへの接続 |

WinUSB と macOS への展開は、Linux で受信の確認が済んだあとに、別の変更として行いました (後述の「macOS」「Windows (WinUSB)」)。

## 元資料と出典

- TurboSight の `linux_media` (GPL): `drivers/media/usb/dvb-usb/tbs5530.c` (bridge)、`drivers/media/dvb-frontends/cxd2878.c` (復調器)。
  いずれも GPL (2 以降を含む) の資料で、px4_drv の GPL-2.0 と両立します。出典と著作権表示は、移植したファイルの冒頭へ残します。
- coax (Till0196) の Go 実装は、元資料の読み筋の確認に使い、コードは転記しません。
- [m1tore/TBS6281SEv2_drv](https://github.com/m1tore/TBS6281SEv2_drv) (GPL-2.0-or-later): PCIe の TBS6281SE v2 向けで、同じ CXD2878 を使い、ISDB-T と ISDB-C (64QAM。TSMF のハードウェア分離を含む) を PTX 互換の chrdev で公開しています。
  ISDB-C を後から足すときの、復調器の起動手順、ISDB-C の周波数とゲインの調整値、TSMF の扱いの参考にします。
  ただし作者自身が「ISDB-C 256QAM は不安定、レジスタ設定は手探り」と書いているため、採用する値は TBS 5530 の実機で再確認します。
  USB の TBS 5530 とは、ブリッジ (PCIe の FPGA と FX2)、水晶の周波数、I2C の経路が異なるため、ブリッジ部分は流用できません。
## 維持する契約

- 受信スレッド、受信バッファ、制御ロックへ長時間の待機を持ち込みません。ブリッジの I2C は 1 回の制御転送で完結するため、ロックの保持は転送 1 回分に限ります。
- 抜去時は `available` を落としてから受信スレッドを止め、チューナー、復調器、GPIO、ファームウェアの状態を破棄します。再接続後に古い状態を引き継ぎません。
- 制御転送のバッファは、`kmalloc` した領域を使います。スタック上の配列は、Linux 6.12 の `VMAP_STACK` で `-EAGAIN` になります ([20261113_common_fixes.md](../20261113_common_fixes.md) を参照)。
- 選局時は、前のチャンネルの TS、バッファの端数、連続性カウンターを引き継ぎません。
- 待機時間とバッファ数は、実機で測ってから決めます。元資料の `msleep` は、初期値として扱います。

## ファームウェア

- ブリッジ用の `dvb-usb-id5530.fw` を、起動のたびに送ります。公式のファームウェアで、再配布できません。利用者が自分で用意し、`/lib/firmware/` へ置きます。
- 送信の手順 (`tbs5530.c` から): CPUCS (`0xE600`、`0x7F92`) へ 1 を書いて CPU を止め、0x40 バイトずつベンダー要求 `0xA0` で書き込み、0 を書いて CPU を再開します。
  USB ID は、ファームウェアの前後で変わりません (RAM への送信で、EEPROM の ID のまま動きます)。
- CXD2878ER (地上側) は、ファームウェアを使いません。M88RS6060 のファームウェアは、衛星側のため不要です。

## 試験計画

### 自動試験 (実機不要)

- ブリッジの I2C の符号化 (1 メッセージ書き込み、2 メッセージの書き込み + 読み出し) が、元資料と一致すること。
- 模擬 I/O での起動、選局、ロック判定、C/N の計算、エラー時の状態破棄。
- ファームウェア送信の区切り (0x40 バイト、末尾の端数、サイズ 0、サイズ不正)。

### 実機試験

TBS 5530 の実機で、次を確認します。

1. 内蔵チューナーの種類 (ASCOT3 か Freia) と、チップ ID。
2. UHF のチャンネルで、TS の連続性エラー、TEI、同期ずれ、ヌルパケットの数 (他機種との同時受信での比較を含む)。
3. 選局を繰り返したときの、TS の継続性と、ロックまでの時間。
4. 受信中の抜去、再接続、`rmmod` と `insmod` の繰り返し。
5. 長時間の受信 (数時間以上)。
6. 通常のカーネルと、デバッグ用のカーネル (lockdep、KASAN、kmemleak) の両方。

## 確認結果

### 検証環境

Proxmox 上の Debian 13 の仮想マシン (カーネル 6.12.116、デバッグ無し) へ、TBS 5530 を USB パススルーしました。
確認用ツールは `tools/tbs5530_probe.c` (このリポジトリには含めていません) です (`usbdevfs` だけで動き、ドライバを必要としません)。
ファームウェア `dvb-usb-id5530.fw` (8192 バイト、SHA-256 `b97cf208bb58…d0dc`) は、LibreELEC の `dvb-firmware` が配布しているものを使いました。

### 2026-11-14 ブリッジとチップの確認

| 確認項目 | 結果 |
|---|---|
| ファームウェアの送信 | CPU 停止、0x40 バイトずつ 8192 バイトの書き込み、CPU 再開まで成功 |
| 送信前の I2C 読み出し | タイムアウト (`-110`)。ブリッジのファームウェアが動いていない状態 |
| 送信直後 | USB の番号が変わって再列挙し (デバイス番号が 3 から 4)、製品名 "TBS 5530"、製造元 "TBS-Tech" になる |
| EEPROM | I2C `0x50` の 16〜21 バイト目が `00:22:ab:xx:xx:xx` (TBS の OUI `00:22:AB`。後半 3 バイトは機材ごとの値で、伏せています) |
| 復調器のチップ ID | `0x19C` = **CXD6822 (SiP2)**。素の CXD2878 (`0x396`) ではありません |
| 内蔵チューナーの ID (復調器の初期化の前) | `0xff` (応答なし)。復調器の電源投入の前は、チューナーが応答しません |
| 内蔵チューナーの ID (電源投入の後) | `0xf6` (`&0xfc` で `0xf4`)。I2C リピーターを有効にして、`0x60` のレジスタ `0x7f` を読んだ値です |

分かったこと:

- ファームウェアは、送信後に**再列挙**します。ドライバは、再列挙後のデバイスを待ってから、以降の制御転送を行う必要があります。
  元の `tbs5530.c` は、dvb-usb の `no_reconnect` 指定で、この待ちを任せています。px4_drv では、probe を 2 回に分ける (ファームウェア送信後の再接続で、本番の初期化を行う) か、同じ probe 内で再列挙を待つ設計が必要です。
- チップが CXD6822 のため、元のコードの `CXD6822 || CXD2878A` の分岐 (Freia 型の内蔵チューナー、CXD6866) を実装の対象にします。ASCOT3 の分岐は不要の見込みです。
- 復調器の電源投入の手順 (元の `cxd2878_init` の CXD6822 向けの部分: 水晶 24 MHz、`SLVX` のレジスタ `0x02`、`0x14`、`0x50`、`0x10`、`SLVT` のレジスタ `0x00`=`0x95`・`0x23`=`0x03`、チューナーの I2C バスの有効化) の後に、内蔵チューナーが応答しました。
  元のコードは、この ID を検査せずログに出すだけです。`0xff` 以外の値が返ったことを、応答の確認とします。
  CXD6822 から Freia 型 (CXD6866) へ進む分岐は、元のコードの記述によるもので、ID の値だけでは Freia 型と断定できません。選局の確認で裏付けます。

### 2026-11-14 共通層による選局と TS の受信

共通層 ([driver/common/tbs5530/](../../driver/common/tbs5530/)) を、確認用ツール `tools/tbs5530_tune.c` (このリポジトリには含めていません) から `usbdevfs` 経由で実機に繋いで確認しました。
Proxmox のホスト (xHCI、カーネル 7.0.2) で、デバイスを直接開いて試験し、仮想マシンのパススルー経由でも同じ結果でした。
アンテナの接続は、受信機の地上波の入力へ 1 本です。

| 確認項目 | 結果 |
|---|---|
| 内蔵チューナーの初期化 (Freia 型の手順) | 成功 (CPU の起動を確認、`CPU_STT` が 0) |
| UHF 27ch (557.143 MHz) の選局 | 0.2 秒で完了、ロックまで 0.5〜0.7 秒 |
| C/N | 約 22〜23 dB (元のドライバの補正値 1.5 dB を引いた値) |
| TS の速度 | 約 30 Mbps (ヌルパケットを含む。ヌルは全体の約 4〜5 割) |
| 2 分間の受信 (C/N を読む場合) | 起動直後の 10 秒間に TEI 9、連続性エラー 4、同期ずれ 2。その後は、TEI 0、連続性エラー 0〜1、同期ずれ 0〜1 の 10 秒区間が混じる |
| 2 分間の受信 (C/N を読まない場合) | 同上。C/N の読み出し (I2C の制御転送) が原因ではない |

分かったこと:

- **ファームウェアの送信後に、`SET_INTERFACE` (インターフェース 0、代替設定 0) または `SET_CONFIGURATION` を送らないと、バルク端点 `0x82` の読み出しがすべて `-EOVERFLOW` (長さ 0) で終わります。**
  - 送信後の再列挙の直後でも、そのまま読むと失敗します。`SET_INTERFACE` を 1 回送ると、約 3.7 MB/s の TS が届きます。
  - 復調器を初期化する前に読むと、端点は静か (NAK で待機) で、オーバーフローは、復調器から TS が流れ始めてから起きます。
  - ファームウェアの 8051 コードには、`EP2CFG`=`0xE8` (バルク、512 バイト、4 重バッファ)、`EP2AUTOINLEN`=`0x0200` の設定があり、別の位置に `0x0400` を書く処理があります。
    この処理の呼び出し元は見つけられていません。`SET_INTERFACE` が、どの状態をどう変えるかの断定はできていません。
  - ドライバは、起動のたびに `SET_INTERFACE` を送ります (Linux では `usb_set_interface()`)。
- **ストリームの先頭は、188 バイトの境界とは限りません。** 読み始めの位置が 15 バイトずれた例がありました。ドライバは、0x47 が 188 バイト間隔で並ぶ位置へ同期してから、パケットを数えます。
- 受信中の小さな乱れ (連続性エラー 1、同期ずれ 1 が 10 秒区間に 1 回程度、起動後の 1 分ほどに集中) の原因は未確定です。
  ユーザー空間の読み出しの取りこぼし、FX2 の FIFO の溢れ、アンテナ信号の変動が候補で、他機種 (torne、PX-S1UD V2.0) との同時比較が必要です。

次の確認: カーネルモジュールとして実装して、同じ受信の指標を比べる。他機種との同時比較。長時間の受信。

### 2026-11-14 カーネルモジュール (Linux 6.12.116、仮想マシン)

[driver/linux/tbs5530_device.c](../../driver/linux/tbs5530_device.c) を実装し、`px4_usb` へ接続しました (`/dev/tbs5530video0`)。
検証環境は、Proxmox 上の Debian 13 (通常のカーネル、デバッグ無し) の仮想マシンへ、TBS 5530 を USB パススルーした構成です。
TS の同期は、T230C が使っている同期処理 ([t230c_ts_sync](../../driver/common/ts/t230c_ts_sync.h)) を共有しました。

| 確認項目 | 結果 |
|---|---|
| ビルド | 警告なし (`px4_drv.ko`) |
| 共通層の自動試験 [tests/tbs5530_core_test.c](../../tests/tbs5530_core_test.c) | 205 項目、失敗 0 (AddressSanitizer と UBSan、`-O2` の両方。ISDB-C の選局を足した現在は 312 項目) |
| ファームウェアが動いている状態 (warm) での probe | 登録成功、`/dev/tbs5530video0` |
| ファームウェアが無い状態 (cold) での probe | FX2 の CPU を止めて再現。`request_firmware` でファームウェアを送り、すぐ応答して登録成功 (「firmware downloaded (0 ms)」) |
| ptx 経由の受信 (UHF 27ch) | 約 30 Mbps (10 秒あたり 約 199,000 パケット)。起動直後の TEI は 2〜6 |
| `open` と `close` の 5 回の繰り返し (各 3 秒) | 毎回受信できた |
| 受信中の `unbind` | 受信側は `read: Input/output error` で終了、デバイスファイルが消える。異常終了や警告なし |
| `unbind` の後の `bind` | 再登録でき、受信を再開できた |
| 信号のないチャンネル (UHF 40ch) | `PTX_SET_CHANNEL` が `EAGAIN` で失敗 (ロックしない) |

仮想マシンのパススルー経由では、連続性エラーが 10 秒あたり 20〜80 回出ます。
同じ機材をホストで直接読むと、ほぼ 0 になるため、仮想マシンのパススルー経路が影響していると考えられます。ユーザー空間で読んでも、仮想マシンの中では悪化します。

| 受信の方法 | 環境 | 連続性エラー (10 秒あたり) |
|---|---|---|
| ユーザー空間 (`usbdevfs`、4 KB の URB × 8) | ホストで直接 | 0〜1 (起動直後を除く) |
| ユーザー空間 (同上) | 仮想マシン (パススルー) | 約 780〜850 |
| カーネルモジュール (16 KB の URB × 8) | 仮想マシン (パススルー) | 59〜116 |
| カーネルモジュール (64 KB の URB × 8) | 仮想マシン (パススルー) | 19〜75 |
| カーネルモジュール (128 KB、256 KB) | 仮想マシン (パススルー) | 47〜86 (64 KB より改善しない) |

転送の大きさに応じて損失が減る傾向は、パススルーの経路が転送の間に隙間を作り、FX2 の FIFO (2 KB、約 0.5 ms で溢れる) が溢れる、という説明に合います。
ただし、これは推定で、確定していません。
URB は 64 KB に決めました (128 KB 以上は、仮想マシンでも改善しないため)。

分かったこと:

- ドライバは、probe のたびに `SET_INTERFACE` を 1 回送ります。送らないと、前述のとおり、TS が読めません。
- `tsdev_max_packets` を増やしても、連続性エラーは減りません。受信側の取りこぼしではなく、USB の転送の段階の損失です。
- ファームウェアの送信後の再列挙は、cold の実機で 1 度だけ観察しました (デバイス番号が変わる)。この場合、probe は、新しいデバイスの probe に引き継がれます。
  動作中の機材へ送り直した場合は、再列挙しませんでした。
- **ドライバは、probe のたびに、ファームウェアを送り直します。** 動作中の機材へは送らない設計では、回復できない状態が残りました。
  FX2 の端点の FIFO が、前の利用者の途中終了などで不整合になると、バルク端点の読み出しがすべて `-EOVERFLOW` や `-EPROTO` で終わります (xHCI は「Babble Detected」を報告)。
  `SET_INTERFACE` を送っても直らず、CPU のリセットを伴うファームウェアの送り直しで直ります。
  再接続やモジュールの再読み込みでも機材は通電したままのため、送り直しで起動時の状態へ戻す必要があります。元の dvb-usb のドライバも、probe のたびに送っています。

### 2026-11-14 デバッグ用カーネルでの確認

Proxmox 上の仮想マシン (Debian 13、カーネル 6.12.116。KASAN、lockdep (`PROVE_LOCKING`)、`DEBUG_ATOMIC_SLEEP`、kmemleak、UBSAN を有効にして構築) へ、TBS 5530 をパススルーして確認しました。
ファームウェアは、probe のたびに送り直す版 (前節) です。

| 確認項目 | 結果 |
|---|---|
| 読み込みと 15 秒の受信 | 登録成功。TEI は起動直後の 1 のみ、連続性エラーは 26、10、9 (5 秒ごと) |
| `open` と `close` の 10 回の繰り返し (各 2 秒) | 毎回受信できた |
| 受信中の `unbind` と `bind` (3 回、読み手は別プロセス) | 毎回、読み手が `read: Input/output error` で終了し、再接続でデバイスファイルが戻った |
| `rmmod` と `insmod` の 5 回の繰り返し (毎回 3 秒の受信) | 毎回受信できた |
| ファームウェアが無い状態 (FX2 の CPU を止める) からの `bind` 2 回 | 毎回、ファームウェアを送って登録でき、受信できた |
| デバイスを開いたままの `rmmod` | `Module px4_drv is in use` で拒否され、読み手は影響を受けず受信を続けた |
| kmemleak (2 回の走査) | 検出 0 件 |
| カーネルログの `BUG:`、`WARNING:`、KASAN、lockdep、UBSAN、`sleeping function` | 0 件 |

ここまでで確認できていないこと:

- KASAN の報告は、1 起動に 1 回のため、初回の検出がない、という確認までです。
- 受信中の連続性エラーは、デバッグ用カーネルの仮想マシンで、4 秒あたり 10〜127 回 (カーネルモジュール、ユーザー空間とも) と、通常のカーネルの仮想マシンより増えます。パススルーと、デバッグ用カーネルの遅さが重なった結果で、ドライバー自身の損失かどうかは、仮想マシンを介さない確認が必要です。
- 試験の途中で、前の試験スクリプトが VM 内で動き続け、読み手が `read()` で止まったままのプロセスが溜まる事故がありました (原因は、ネットワーク経由の起動の取り扱いで、ドライバーではありません)。止まった `read()` が、`SIGKILL` で終わることは確認できました。

### 2026-11-14 複数機種の同時受信 (別の仮想マシン、通常のカーネル)

5 機種 (TBS 5530、torne、PIX-DT295 Rev.02、GV-MVP/XZ、PX-S1UD V2.0) を同じ仮想マシンへ USB パススルーし、UHF 27ch を 30 秒、同時に受信しました (15 秒ごとに集計)。

| 機種 | パケット (15 秒) | TEI | 連続性エラー | C/N |

| TBS 5530 | 約 29.9 万 (約 30 Mbps。ヌルを含む) | 起動直後に 5、その後 0 | 12、28 | 20.8〜21.2 dB |
| torne | 約 17.2 万 | 0 | 0 | 21.3〜21.5 dB |

### 2026-11-15 macOS (DriverHost_PX4)

`host/devices/tbs5530_device.cpp` が、共通層 (`driver/common/tbs5530`) を libusb 経由で使います (Windows は次節)。

- ファームウェアは配布物に含めません。INI の `Tbs5530Firmware` (既定は `dvb-usb-id5530.fw`、相対パスは DriverHost_PX4 の場所が基準) で指定します。
- 通電直後の機材は、ファームウェアを送ると再列挙し、その Init は `-ENODEV` で終わります。再列挙後に見える新しいデバイスが改めて Init され、復調器 ID 0x19c を検出して登録されます (root 権限なしで確認)。
- 1 転送の長さ (`Tbs5530UrbBytes`、既定 65536) は、バルク端点の最大パケット長 512 バイトの倍数にします (Linux 版の 64 KB と同じ)。188 x 348 = 65424 バイトは、TBS 5530 だけを有効にして 3 回試験したところ、3 回とも約 8 秒で `libusb` の転送が `status=6` (`LIBUSB_TRANSFER_OVERFLOW`) になり、データ接続が閉じました (パケット 0)。

検証環境: macOS 11.7.10 (x86_64) の MacBook (AC 電源)、TBS 5530 を直接接続、UHF 27ch、`px4rec -i 0 -d 60 T 27`。

#### 受信機の試験で守ること (Mac)

- **スリープを止める。** `sleep 10` の設定だと、ssh の操作や `px4rec` では無操作が解けず、保守スリープ (7〜17 秒) と DarkWake (約 45 秒) を約 1 分ごとに繰り返し、その間は USB が止まります (`pmset -g log` で確認)。`caffeinate -dis` で止めない録画の結果は、機材の性質を表しません。
- **機種を 1 台だけ有効にする。** `px4rec -i 0` は、空いている最初の受信機を選びます。複数の機種を有効にした DriverHost では、別の機種の録画を TBS 5530 の結果と取り違えます。検証用の ini で、他の機種の `ProductId` を `0xffff` にして外します。

#### 連続性エラー (スリープを止め、TBS 5530 だけを有効にした条件、60 秒、連続性エラーはヌルと PID 0x71f を除く)

| 設定 (本数 x 長さ) | 連続性エラー | TEI |
|---|---|---|
| 8 x 65536 (1 回目の 3 回) | 0.898%、0.424%、1.033% | 0、3、0 |
| 8 x 65536 | 0.381%、0.176% | 1、5 |
| 32 x 65536 | 0.241% | 2 |
| 8 x 16384 | 0.292% | 4 |
| 16 x 131072 | 0.123% | 6 |
| 8 x 262144 | 0.094% | 1 |
| 4 x 65536 | 0.101% | 2 |

- 同期の欠落は 0、レートは 29.5〜29.9 Mbps で安定でした。選局は set_ms=230〜235、lock_ms=885〜974、最初の TS まで 903〜993 ms でした。
- **TBS 5530 には、スリープを止めても、0.1〜1% の連続性エラーが残ります。** 設定による差ははっきりせず (同じ 8 x 65536 でも 0.176〜1.033%)、本数が少なく長い転送 (4 x 65536、8 x 262144、16 x 131072) のほうが少ない傾向があるように見えますが、ばらつきの範囲内で、結論にしていません。エラーの大半は 1 パケット分の欠落で、TEI はほとんどありません。
- 同じ条件の PIX-DT295 (連続録画 5 回で 0〜5 件) と Sony CECH-ZD1 J は 0.00x% で、TBS 5530 のほうが明らかに多い状態です。GV-MVP/XZ の連続性エラーは TEI を伴い、受信信号の変動によります。
- 原因は特定していません。候補は、機材の FIFO (FX2、2 KB) の溢れ、復調器の出力、ホストの転送の遅れです。USB の転送の前の生のバイト列と、同期後の TS で連続性エラーを比べる試験が、次の切り分けです。
- ヌルを除く実データのパケット数、C/N、B-CAS (カードリーダーを持たないため対象外)、チャンネル切り替え、長時間の受信は、macOS では未確認です。

### Windows (WinUSB)

macOS と同じ `host/devices/tbs5530_device.cpp` が、WinUSB の制御転送 (`WinUsb_ControlTransfer`、オーバーラップ I/O と期限付きの待機) で、同じ共通層を使います。DriverHost_PX4 の機種表 (`DeviceType::TBS5530`)、`winusb/pkg/inf/TBS5530.inf`、DriverHost_PX4.ini、BonDriver_TBS5530.ini とチャンネル表、`build.ps1` の試験と配布物を追加しました。

- ファームウェア `dvb-usb-id5530.fw` は配布物に含めません。DriverHost_PX4.exe と同じフォルダへ置くか、INI の `Tbs5530Firmware` で指定します (相対パスは DriverHost_PX4.exe の場所が基準)。
- 通電直後の機材は、ファームウェアの送信後に再列挙します。WinUSB の制御転送が、切断されたハンドルのエラー (`ERROR_DEVICE_NOT_CONNECTED` など) を返すため、`-ENODEV` として扱い、その Init を終えます。再列挙後の機材は、デバイスの到着通知で改めて Init されます。動作中の機材へ送り直したときは、再列挙しません。
- ファームウェアの後に、`WinUsb_SetCurrentAlternateSetting` で SET_INTERFACE を送り、バルク端点 0x82 の FIFO の不整合を直します (macOS の `libusb_set_interface_alt_setting` と同じ)。
- 内蔵カードリーダーを持たないため、`WinSCard.dll` は `BonDriver_TBS5530_*` の配布物へ入れません。

確認したこと (2026-11-15、Windows 11 (x64)、Visual Studio 2022 BuildTools の v143):

- **機種表の整合試験:** `device_parity_test` の Windows 版 (`winusb/tests/device_parity_test.vcxproj`。macOS の CMake の同名の試験と同じソースで、DriverHost_PX4 のアプリ固有のファイルを除いた全機種のソースへリンクする) を追加し、`build.ps1` から実行します。x86 と x64 で通り (22 機種、Linux の USB ID 24 件)、`TBS5530.inf` の GUID を一時的に壊すと、`TBS5530.inf does not match the WinUSB device definition` で失敗することを確認しました (元へ戻して再実行し、通ることも確認)。
- **ビルドと自動試験:** x86 と x64 で、DriverHost_PX4 を含むソリューションがビルドでき、`tbs5530_core_test` が両方で 205 項目すべて通りました。署名したカタログ (`sign.ps1`) に `TBS5530.inf` が入り、`verify.ps1` が通ります。`build.ps1` の全体 (x86 と x64 のビルド、全自動試験、配布物の作成) は、終了コード 0 で通りました。ただし、既存の `torne_core_test` が、MSVC 14.44 で `torne_dib.c` の C4127 (コンパイル時に決まる設定のマクロを条件にした `if`) をエラーにして止まるため、そのプロジェクトで `torne_dib.c` に限って C4127 を無効にしました。配布物 `BonDriver_TBS5530_32bit` と `BonDriver_TBS5530_64bit` には、ファームウェアと `WinSCard.dll` は入りません。x64 の配布物へファームウェアだけを足して、27ch と 21ch の切り替え 4 回を受信し、同期エラー、TEI、連続性エラーとも 0 でした。
- **ドライバーの導入:** この PC には、TBS の純正の BDA ドライバー (2.1.0.3、`tbsBDA`) が入っていて、TBS 5530 はそれに結び付いていました。`pnputil /add-driver TBS5530.inf /install` で、このリポジトリの INF (`WINUSB`) に切り替わりました (この INF が優先された理由は調べていません)。純正のパッケージはドライバーストアに残るため、`pnputil /delete-driver <公開名> /uninstall /force` で、純正へ戻せます (往復を 2 回行い、いずれも成功)。
- **受信:** ファームウェアの送信、再列挙、選局、約 30 Mbps (ヌルを含む) の受信、C/N の取得まで、BonDriver 経由で動作しました (`channel_switch_stress`)。27ch と 21ch の交互の切り替え 8 回は、すべて選局に成功しました。21ch の 10 分の連続受信は、11,950,080 パケット (30 Mbps で一定)、TEI 0、同期エラー 52、連続性エラー 8,695、信号 22.57 dB でした。

私たちのドライバーと、純正の BDA ドライバーとの比較 (同じ PC、同じアンテナ、BonDriver_BDA 2019-02-02 の UHF 用のサンプル設定。ツールの「同期エラー」は、先頭が 0x47 でないパケットと、ヘッダーが壊れたパケットの合計です):

| チャンネル | 60 秒 | 私たちのドライバー | 純正 (BDA) |
|---|---|---|---|
| 27ch | パケット | 1,188,864 / 1,189,888 / 1,192,960 | 957,440 / 794,624 / 956,416 |
| 27ch | 連続性エラー | 3,234 / 9,457 / 1,568 | 25,733 / 36,417 / 25,376 |
| 27ch | TEI | 0 / 47,148 / 2 | 30,680 / 41,484 / 28,074 |
| 21ch | パケット | 1,195,008 / 1,195,008 | 1,100,800 / 1,132,544 |
| 21ch | 連続性エラー | 991 / 1,154 | 9,758 / 6,564 |
| 21ch | TEI | 0 / 0 | 25 / 18 |

- 27ch は、どちらのドライバーでも TEI を伴うエラーが多く、電波側の要因 (TEI) が大きいと見ています。21ch は C/N が 21〜22 dB で、エラーが少なくなります。
- どちらのチャンネルでも、私たちのドライバーの連続性エラーは、純正の 3 分の 1 から 10 分の 1 でした。ただし、パケット数 (ヌルの有無)、数え方、BonDriver の違いがあり、厳密な比較ではありません。

**30 分の連続受信 (21ch、BonDriver 経由、Windows のスリープを `SetThreadExecutionState` で止めた条件):** 2 回 (20:25 と 21:00 から) とも、DriverHost_PX4 は同じプロセスのまま (クラッシュなし) で、ワーキングセット 14.7 MB、ハンドル 196、スレッド 10〜12 が 30 分間変わりませんでした (1 分ごとに記録)。受信のレートも一定で、35,851,264 パケットと 35,849,216 パケット (毎秒約 2 万、30 Mbps) でした。一方、エラーは 2 回とも多く、1 回目は TEI 約 25% (9,104,816)、連続性エラー約 7.5%、同期エラー約 2.5%、2 回目は TEI 約 48% (17,273,279)、連続性エラー約 23%、同期エラー約 4.4% でした。2 回目の 10 秒ごとの記録 (180 区間) では、TEI は最初の 1 分から出ており (時間とともに悪化したのではない)、C/N が 20 dB 未満の区間では非ヌルパケットの 82〜97%、20.5〜21.5 dB の区間では約 30%、午後に C/N が 21〜22.6 dB だった受信 (10 分、TEI 0) では 0 でした。エラーは C/N に連動して崖のように増えており、この時間帯は、同じチャンネルで C/N が 18〜20 dB 台に下がっていたことが原因と見ています (同じ時間帯の純正ドライバーでの比較はしていないため、ドライバーに起因する分がないとは言い切れません)。このため、**30 分の受信で、エラーが少ない結果は得られていません** (プロセスとリソースの安定だけを確認)。

**受信中の USB の抜去で DriverHost_PX4 が異常終了した不具合 (修正済み、修正後の抜去で異常終了しないことを確認):** 受信中 (21ch) に手動で USB を抜いたところ、受信が止まった直後に、DriverHost_PX4.exe が `0xc0000409` (`abort`) で異常終了しました (Windows のイベントログの Application Error。フォールトのオフセットを、リンカーのマップで `libucrt` の `abort` へ解決)。BonDriver が新しい DriverHost_PX4 を起動し、機材の挿し直しの後、約 14 秒で受信が復帰しました (最初の復帰は、挿し直しの後の `OpenTuner` の再試行で成功)。原因は、XZ と DT295 で修正済みの不具合と同じ型 (抜去の後に、クライアントの接続が受信機の `Close()` を呼ぶのに、機材の破棄が受信機を先に破棄する) と推定しています (`abort` の呼び出し元までは特定していません)。TBS 5530 の実装は、この修正の入っていない torne をひな形にしていたため、XZ と DT295 と同じ契約 (`client_open_` と `close_cond_` で、受信機の破棄を `Close()` まで待たせ、機材のロックの外で破棄する) を追加しました。修正後のビルドで、選局の切り替えの受信が壊れていないことを確認したうえで、同じ操作 (21ch の受信中に手動で USB を抜き、約 15 秒後に同じポートへ挿し直す) を行ったところ、受信が約 2 秒後に止まり (6 秒で停止を検出)、機材のない間の `OpenTuner` の再試行は失敗し、挿し直した後の再試行で受信が全速 (約 30 Mbps) に戻りました。DriverHost_PX4 は同じプロセスのまま (クラッシュの記録なし) で、復帰後 40 秒間は安定して受信できました (抜去を 1 回だけ確認)。取り外しは、`pnputil /disable-device` では模擬できません。DriverHost_PX4 が機材を開いたまま `QueryRemove` に応じないため、無効化が「再起動が必要」の保留になり (`CONFIGFLAG_DISABLED` が立つ)、機材は取り外されません (保留を戻すには、レジストリの `ConfigFlags` を 0 にする必要がありました)。物理的に USB を抜く確認が必要です。

未確認: 受信中の USB の抜去と挿し直しの 2 回目以降、複数台の同時受信中の抜去、電波の条件が良い (C/N が 21 dB 以上で続く) 状態での 10 分を超える受信 (エラーの少なさ)、複数台の同時受信、`Tbs5530Firmware` の既定のパス以外の指定。

## ISDB-C 対応 (実験的)

ISDB-T の確認が Linux、Windows、macOS で済んだため、ケーブルテレビ (トランスモジュレーション方式の ISDB-C、ITU-T J.83 Annex C) の受信を、実験的な対応として足しました。
2026-11-16 の時点で、実装と自動試験までが済み、**実機では未確認**です。元資料の調査で分かったこと、実装の範囲、試験、未決の事項を記録し、実機で確認した内容は、確認した順に、この節の下へ追記します。

### 範囲

| 項目 | 内容 |
|---|---|
| 対象 | ISDB-C (J.83 Annex C。6 MHz 帯、シンボルレート 5.274 Msym/s、64QAM)。TSMF の TS の選択を含む |
| 後回し | 256QAM (参考にする実装の作者が「不安定」としている)、J.83 Annex B (スカパー！プレミアムサービス光) |
| 対象外 | BS/CS (ISDB-S)。衛星側の復調器が DVB-S/S2 専用のため |
| 公開の形 | 他機種と同じ。`PTX_ISDB_C_SYSTEM`、`BonDriver` の `System="ISDB-C"`、`px4rec C`。仕様は [ISDB-C と J.83 Annex B の選局の仕様](../isdbc_tuning.md) に従う |

### 元資料の調査で分かったこと

- **TBS 純正の `cxd2878.c` (`tbsdtv/linux_media`、GPL) には、ISDB-C 専用の復調器の手順がありません。** 持っているのは、DVB-C (Annex A と Annex C。`SLtoAC`) と J.83 Annex B (`SLtoACC`) の手順です。
  ISDB-C は、チューナーの設定 (Freia の `SONY_FREIA_DTV_CABLE_6`、DVB-C 6 MHz と同じ) と、TS のクロック (ISDB-T と同じく TS レート制御を切る) の 2 か所だけ、ISDB-T 相当の扱いです。
- **ISDB-C の復調器の手順は、[m1tore/TBS6281SEv2_drv](https://github.com/m1tore/TBS6281SEv2_drv) (GPL-2.0-or-later) に `SLtoAIC` と `SLtoAIC_BandAndTSMFSetting` としてあります。**
  同じドライバが、チップ ID が CXD6822 のとき `freia_tune` を使っており、TBS 5530 と同じ復調器とチューナーの組み合わせです。
  `SLtoACC` (J.83 Annex B) と骨格が同じで、IF 周波数 (レジスタ `0xB6`)、補間フィルタ係数 (`0xA6`)、サンプリング (`0xA3`)、シンボルレートの探索範囲 (バンク `0x40` の `0x26`)、QAM の選択 (`0x14`)、TSMF の出力設定 (`0x1E`) を ISDB-C 用の値にしたものです。
- **ISDB-C のロック判定は ISDB-T と違います。** バンク `0x40` のレジスタ `0x88` のビット 0 (AGC 収束) と、レジスタ `0x10` のビット 5 (同期) の両方が立ったときを、ロックと見ています (TSMF をハードウェアで分離するときは、バンク `0x49` の `0x20` のビット 0 も)。
- **参考にする実装の周波数ごとの調整 (IF 利得、BB-AGC の目標、IF 周波数のオフセットを周波数の帯域ごとに変え、選局の結果で学習する仕組み) は、作者が「手探り」としている部分です。** そのまま移すと、根拠のない値が入るため、最初は採用しません。
  最初の実装は、TBS 純正のテーブル (Freia の `CABLE_6`) の固定値で選局し、実機で足りない部分を、測定してから足します。
- **TSMF は、ISDB-C 向けの共通の処理 (`ptx_chrdev` の TSMF の分離、ホスト共通の `receiver_base` の TSMF の処理) で扱います。** 復調器のハードウェアの TSMF 分離は使いません。TBS 5530 の TS は、復調器から FX2 のバルク転送へ流れる 1 本で、他機種 (T230C など) と同じ形のためです。

### 実装の範囲

| 層 | 内容 |
|---|---|

参考にした実装との違い:

- **TS クロックのマスク、`0xA9`、`0xDE`、`0xDA` の再設定は、含めていません。** 起動 (`tbs5530_demod_init`) と `set_ts_clock` で、ISDB-T と同じ値を設定済みのためです。
- **周波数ごとの調整 (IF 利得、BB-AGC の目標値、IF 周波数のオフセットの学習) は、含めていません。** BB-AGC の目標は 0x48、IF 周波数は 3.7 MHz (TBS 純正の DVB-C 6 MHz と同じ) の固定値です。
- **RS エラーのミュートは、切っています (バンク `0x48` の `0xAC` = 0)。** 参考にした実装と同じで、エラーのあるパケットも TS へ出します。

### 未決の事項と危険

- **信号源。** ケーブルテレビの回線は、上のとおり使えました。TSMF で多重された搬送波は、この回線では見つかっていません (macOS の走査で、PID 0x2f の TS は C13〜C63 のどこにもなかった)。256QAM の搬送波は、macOS の回線で見つかりました (次の「macOS の確認」の「256QAM」)。
- **復調器の値の根拠。** ISDB-C の IF 周波数、補間フィルタ係数、AGC の値は、参考にする実装の値です。TBS 5530 の水晶と I2C の経路は、その実装の基板と同じとは限りません。最初の実機の確認で、ロックと誤り訂正の結果から確かめます。
- **Freia の ISDB-C の設定。** TBS 純正の Freia のテーブルは、ISDB-C 専用ではなく、DVB-C 6 MHz の値を借りています。ロックしない、またはエラーが多いときの、最初の切り分けの対象です。
- **C/N。** ISDB-C 用の換算を、一次資料では確認できていません。確認するまでは、他の機種と同じく未対応 (`-ENOSYS`) にします。
- **TSMF の null パケット。** TSMF は、ヘッダーからの位置で TS を選ぶため、null パケットを先に除くと位置が狂います。Linux は `ptx_chrdev` の扱いに従い、ホストは、フィルターを通した後に除く形を確認します。

#### 256QAM (J:COM が BS4K を再配信しているとみられる搬送波)

C13〜C63 を 4 秒ずつ走査したところ (`ExperimentalISDBC=true`、各搬送波の TSID を PAT から読んだ)、64QAM の搬送波は PAT が読めました (C16 は TSID 0x203 (515) で、サービス 430 と 431 の映像は stream_type 0x24 (HEVC)、音声は 0x11)。一方、C19〜C22 は PAT が読めず、毎秒約 2.5 万パケット (約 38 Mbps、256QAM のレート) が出ていました。

- **観察した事実:** C19〜C22 の出力は MPEG-2 TS ではなく、TLV (先頭が `0x7f`、続けて種別 1 バイトと長さ 2 バイト。種別は 0x01、0x02、0x03、0xfe、0xff) でした。C22 は 10 秒 (約 47 MB) の全体が TLV の連鎖としてつながり、壊れた箇所はありませんでした。C19〜C21 は連鎖としてつながるバイトが 10〜48% で、残りは乱数のようなデータでした。
- **推定:** 復調器の `0x14=0x1f` (すべての QAM を追従) のままで 256QAM は復調できており、TLV を TS のパケットではなく、そのまま流しているとみられます。C19〜C21 の乱れの原因は、特定していません (C/N 不足、搬送波の種別の違い、ロック判定の甘さの可能性があります。選局が約 300 ms で「ロック」と判断されるため、ロック判定は壊れたデータを通しています)。
- **未対応:** TLV を TS として扱う処理はなく (BS4K の MMT/TLV の取り出しは対象外)、256QAM のロック判定、C/N、TSMF の確認、時間の経過での安定性は未確認です。

**macOS の回線で、TBS 5530 を戻して再確認した結果 (2026-11-17、DriverHost_PX4、各 10 秒、2 周):** C22 は 2 回とも、全体の 100% が TLV の連鎖としてつながりました。C19、C20、C21 は、どの 1/10 も 9〜13% で、時間がたっても変わらず、2 周とも同じでした (回線の状態が揺れた結果ではなく、搬送波ごとの決まった性質とみられます)。

- **観察した事実:** C19 でつながる区間は、長さ 368 バイトの TLV の null パケット (`7f ff 00 18` と `ff` の列) が、約 6,278 バイトの間隔で並ぶ形でした (間隔の頻度は 6,278 が最多で、1,476、12,556 が続く)。間の約 5,900 バイトは、`0xff` が 9% 程度の高いエントロピーのデータでした。
- **保存したデータの解析 (NAS の回線で受信したままのバイト列、C19〜C22):** 4 つとも、188 バイトの TS パケット (先頭が 0x47、先頭から 188 バイトごとに 20,000 パケットすべてで一致) で、PID は 0x2d (分割 TLV) と 0x2f (TSMF ヘッダー) の 2 つだけでした。TSMF ヘッダーは 53 パケット (9,964 バイト) ごとに現れ、52 スロットはすべて同じ相対 TS 番号 (1) に割り当てられていました。つまり、この 4 つはどれも、TSMF で運ばれた 1 本の分割 TLV です。macOS の DriverHost_PX4 の出力は、共通層の TSMF の処理が分割 TLV を TLV の連鎖へ組み立てたものでした。
- **同じ組み立てを Python で保存データへ当てた結果:** C22 は 99% が連鎖としてつながり、C19、C20、C21 は 10%、23%、18% でした。ホストの処理の誤りではなく、受信した TS パケットの中身の違いです (TEI は 4 つとも 0、TS と TSMF の構造は壊れていません)。
- **TLV-SI (種別 0xfe) の NIT と TSMF ヘッダー:** C22 の NIT (table_id 0x40) は、network_id が 0x0b で、TLV ストリーム ID と編成番号の組を 7 つ (0xb070 は 151、0xb071 は 171、0xb072 は 141、0xb0e0 は 102、0xb110 は 101、0xb111 は 161、0xb112 は 181) 並べていました。NIT のネットワーク名 (記述子 0x40) は UTF-8 で「高度ＢＳデジタル放送」でした。TSMF ヘッダーの TLV ストリーム ID は、C22 が 0xb110 (編成番号 101)、C19、C20、C21 は 3 つとも 0xb0e0 (編成番号 102) でした。C19〜C21 で組み立てた TLV からは NIT が取れず (取れた表は 0x72、0xfe、0x0a が各 1 個)、3 つの搬送波が同じ TLV ストリーム ID を名乗っています。
- **分割 TLV のパケットの並び (NAS の回線で受信した C19〜C22 の保存データ):** 開始パケット (PUSI) のポインターが指す位置に `0x7f` と有効な種別がある割合は、C22 が 14,186 件中 14,186 件、C19 が 11,975 件中 11,974 件、C20 が 14,483 件中 14,478 件、C21 が 14,064 件中 14,062 件で、4 つとも 99.9% 以上でした。52 スロットの割り当ては、400 フレームすべてで 4 つとも全スロットが相対 TS 番号 1 でした。違いは、開始パケットと継続パケットの並びです。C22 は `cccSSSccccccSS…` のように、TLV の長さに応じて継続パケットが 1〜6 個続きます。C19〜C21 は `SccSccScc…` と、ほぼ 3 パケットごとに開始パケットが現れ、TLV の長さ (ヘッダーの長さの欄) と、次の開始位置までの間隔が合いません (C19 は 11,975 件中 8,596 件が不一致で、差は 370 バイト (継続パケット 2 個分) と 526 バイトと 896 バイトに集中)。
- **libaribtlv (別の実装) での確認:** [makeding/libaribtlv](https://github.com/makeding/libaribtlv) (MIT、コミット f4a603b、macOS 11 の Intel Mac で静的ライブラリとしてビルド) へ、macOS の DriverHost_PX4 が出力した TLV (各 10 秒) を通しました。C22 は、サービス 2 つ、トラック 5 つ (HEVC 映像 1、AAC-LATM 48 kHz 2ch の音声 2、TTML の字幕 2、いずれも日本語)、IP データフロー 1、TLV-NIT 1 を読み取りました (エラー 44 件は、先頭の中途半端な断片とタイムスタンプ記述子の待ちで、すべて回復可能)。C19、C20、C21 は、トラックが 0 で、`lost TLV synchronization` と `discarded bytes while searching for a validated TLV boundary` が 36〜52 件続きました。私の手書きの解析とは別の実装でも、C19〜C21 は TLV として読めないことが確認できました。ただし、映像のアクセスユニットは 10 秒の録画では C22 でも出なかったため、映像の復号までは確認していません。
- **推定 (未確認):** C19〜C21 では、継続パケットの 370 バイトの塊が、前の TLV の長さと合わないまま挿入されています。null の TLV (長さ 24〜180 バイト) が、別の TLV の途中へ挿入された形にも見えますが、確認できていません。ACAS (B-61) のスクランブルは、MMTP のペイロードだけにかかり TLV のヘッダーは読めるため、この不一致の説明にはなりません。原因は未特定です。C22 は、ショップチャンネル 4K などの無料の編成とみています (一覧とは未照合)。


**NAS の回線での比較 (2026-11-17、ユーザー空間のツール、`TBS_RAWOUT=1` で受信したままのバイト列を保存):** C19、C20、C21、C22 を各 10 秒受信したところ、4 つとも約 38.9 Mbps が流れ、約 0.02〜0.03 秒で「ロックした」と判定されました。保存したデータは、TS パケット (TSMF の PID 0x2f と分割 TLV の PID 0x2d) のまま 188 バイトごとに 0x47 が並んでおり、macOS の回線と同じ形でした。TLV の連鎖として読んだときの割合は、macOS の DriverHost_PX4 の出力と同じ傾向 (C22 が高く、C19〜C21 が低い) でした。

- **訂正:** この節の最初の版は、TS のヘッダー (4 バイト) を取り除かずに TLV の連鎖を読み、NAS の回線では 4 つとも壊れたデータと書いていました。誤りです。NAS の回線と macOS の回線は、同じアンテナの分岐で、C19〜C22 の結果に差は見つかっていません。
- **試験の注意:** NAS の `/tmp/tbs_w` (tmpfs、64 MB) が満杯になると、保存したファイルが 0 バイトになります。録画を残す試験は、1 回ごとに消してください。
