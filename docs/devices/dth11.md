# BUFFALO DT-H11/U2

## 対応範囲

DT-H11/U2 は USB `0411:01da` の、地上デジタル (ISDB-T) チューナー1基と、内蔵の B-CAS カードスロットを持つ USB 機材です。
USB ブリッジは EVA01 系 (ファームウェアは機材に内蔵)、復調器は PN2031 (レジスターの配置は富士通 MB86A20S と同じとみられます)、チューナーは MaxLinear MxL135RF (復調器の I2C ゲートの先) です。

Windows と macOS では、ユーザー空間のホスト `DriverHost_PX4` が受信を提供します ([Windows と macOS、Linux のユーザー空間のホスト](#windows-と-macos-linux-のユーザー空間のホスト) を参照)。
Linux のカーネルモジュール (`px4_drv`) は、この機種に未対応です。

受信の方式は、機材内蔵のカードで復号する **device モードだけ**です ([受信の方式](#受信の方式))。
内蔵カードをホストへカードリーダーとして見せる経路は見つかっていないため、`HasCardReader()` は偽で、PC/SC と WinSCard へは何も出ません。

対象外は次のとおりです。

- BS / CS (この機種は地上波専用です)
- 復号しない raw モード (この機体のファームウェアが受け付けません)
- 内蔵カードの PC/SC 経由での利用
- 複数台の同時接続 (1台だけで確認しました)

この対応は実験的です。実機での確認は Windows 11、macOS 11.7、Linux (WSL2 の USB/IP 経由) で行い、確認した範囲は後述します。macOS では連続性エラーが出るため、録画の用途には、Windows だけを推奨できます。

## 受信の方式

ストリームを有効にする要求 (`wValue 0xCBDA / wIndex 2`) の最初のバイト `mode` が、機材の出力を決めます。

| `mode` | 出力 | この機体での結果 |
|---|---|---|
| 0 (device) | 番組の PID リストに従い、内蔵カードで復号した TS。ホストとの間でだけ暗号化される (CEPM) | 動作します |
| 1 (raw) | 放送波のままの、スクランブルされた TS | 要求を拒否します (STALL) |

raw は、割り込みエンドポイントの読み出し、PID フィルターの先送り、ストリームの入れ直し、要求のフラグ、ペイロードの形を変えても、同じ結果でした。
参考実装 ([実装元と権利](#実装元と権利)) も、同じファームウェア (1.0.18) で raw を拒否されて、「このファームウェアに raw モードはない」と判定します。
参考実装の表では DT-H11/U2 が検証済みとされていますが、検証した個体のファームウェアの版が異なる可能性があります。

device モードの TS は、放送された番組のうち、PID リストに指定した 1 番組 (と PSI、ワンセグ) だけが出ます。
ホストがそのために PAT と PMT を読んで PID リストを作り、機材へ送ります。

## 資格情報 (利用者が用意するファイル)

device モードのリンク暗号は、機材とホストが ECDSA と ECDH (secp160r1) で相互に認証します。
ホスト側の証明書と秘密鍵、コンテンツ鍵を開く CBC の IV は、純正のアプリケーション (PCastTV3) の `CoBDACom.dll` の中にあります。
これらの値はリポジトリに含まれません。**利用者が自分で用意した `CoBDACom.dll` から、`DriverHost_PX4` が起動時に読み出します。**

- 入手元の一つは、BUFFALO の「PCastTV HD Lite 2.03 更新」(`pcastlite-203.exe`) です。更新の中の `PCastTVHD_203_Update.exe` が Inno Setup の形式で、`app/Cobalt/CoBDACom.dll` が入っています。この DLL は 351,232 バイト、SHA-256 は `7f4cabfd0b104c0e739f1172a10a98fcf24377c6947e3ab6ac0fa856353bcc15` です (参考実装が要求する値と一致します)。
- DLL は実行しません。コード領域の、データ領域へバイトごとに即値を書き込む命令 (`mov byte ptr [addr], imm8` など) の並びを走査し、書き込まれる内容を再生して、証明書 (自己署名の検証で確認) と秘密鍵 (公開鍵との対応で確認) を見つけます。IV は、コードがスタックに組み立てる 16 バイトの候補のうち、最初のコンテンツ鍵のブロックの CMAC が一致するものを採ります。どの値も、機材の応答か検証で正しさを確かめてから使います。
- 配置は `DriverHost_PX4.exe` と同じフォルダが既定です。別の場所は INI の `Dth11AppKeys` で指定します。
- ファイルが無い、読めない、純正の `CoBDACom.dll` でないときは、この機材の初期化を断ります (鍵がないまま受信すると、ワンセグ以外が暗号化されたまま届くためです)。

## 仕組み

### ホストからの操作

ベンダー要求だけで操作します。`bmRequestType` は、WinUSB で通るように、受け取り先を機器 (device) にした `0x40` (OUT) と `0xC0` (IN) です。
`bRequest` は、IN だけの要求が `0x01`、OUT (データなしを含む) が `0x02` で、`bit7` が 1 の要求はチューナー #1 の経路を指します。
`wValue` の上位バイトが種別です。

| `wValue` | 内容 |
|---|---|
| `0x0000` | システム。機器情報 TLV (`wIndex 0xC0DE`)、ファームウェアの版 (`0x0000`)、起動 (`0x0010`)、GPIO (`0x1004`、`0x1006`) |
| `0x2B00` | I2C のバッチ書き込み (1 件 6 バイト、全体 256 バイトまで) |
| `0x2C00` + アドレス | 生の I2C (`wIndex 0x30` が書き込み、`0x33` が読み出し) |
| `0x2D00` + アドレス | レジスター付きの I2C (`wIndex` がレジスター) |
| `0xCBDA` | ストリーム。有効化と無効化 (`wIndex 2`)、番組の PID リスト (`wIndex 0x1000`) |
| `0xDEAF` | リンク暗号の相互認証 (`wIndex 1..6`) |

OUT のデータは、書き込み可能な一時バッファへ複写してから転送へ渡します。WinUSB は OUT のデータにも書き込み可能なメモリを要求し、読み取り専用の表を渡すと失敗するためです (実機の WinUSB で確認しました)。

機器情報の TLV には、キット名 (`PN2031_MxL135RF`)、GPIO のマスク、チューナーのアドレス (0x60)、水晶 (16 MHz)、IF (4 MHz) などが入ります。
復調器の設定は IF 4 MHz 固定のため、別の値、チューナーを復調器のゲートの外に置く構成、別のキット名は、この層で断ります。

### 起動と選局

起動は、GPIO の電源投入、復調器の設定 (約 12 回のバッチ書き込み)、チューナーの初期化とスタンバイ、**チューナーの起床**、機器の起動 (`wIndex 0x0010`) の順です。
起動の後の最初のチューナーへの書き込みは、この機体で要求が拒否されたため、起床を先にしています。
選局は、復調器の前処理、チューナーの周波数設定 (6 MHz 帯域、UHF 13〜62ch の中心周波数)、復調器の後処理です。ロックは復調器の同期状態 (レジスター `0x0A` の下位 4 ビット) が 9 になった時点で、27ch では約 1.2 秒でした。

C/N は、復調器が約 1 秒ごとに測る値 (レジスター `0x46` と `0x47`) を、純正の表で換算します。選局の後に最初に完了する測定は、実機で実際と懸け離れた値になったため (30.0 dB の上限や数 dB の誤差)、読み捨てます。信号強度は、純正の式の単位を確認していないため、未対応です。

### ストリーム

TS は、`bulk IN 0x81` から、256 バイトのスロット (先頭の 188 バイトが TS パケット、残りは詰め物) の並びで届きます。
先頭が `0x47` でないスロット (ストリーム開始直後の、TS ヘッダーが 0 のもの) と、詰め物のパケット (`47 9F FF 1F …`) は捨てます。
`DriverHost_PX4` は、32 KiB の読み出し (128 スロット) を 16 本並べます。

### リンク暗号と番組の選択

選局してストリームを始めるまでの流れは次のとおりです。

1. **相互認証** (初回だけ、約 5 秒): #1 の経路 (`bRequest` の `bit7`) で 1 回、続けて #0 の経路で 1 回行います。新しく電源の入った機材は #1 の経路だけが応答し、#0 は #1 の後で応答するためです。各段の IN の前に 400 ms 待ち、機器が ECDSA を計算する間の STALL は、4 秒を上限に 50 ms 間隔で再試行します。結果は、機材の電源が切られる (または `DriverHost_PX4` が終わる) まで使います。
2. **番組表の学習** (約 1 秒): ストリームを有効にして、復号を通した PAT と PMT を読みます。CRC32 の合わないセクションは採用しません。上限は 4 秒です。
3. **PID リストの送信**: 選んだ番組の PID (PMT、ECM、PCR、ES) を、ストリームの無効の間と、有効にした後の 2 回送ります。機材は番組 1 つ分だけを保持し、無効にすると忘れます。
4. **受信**: ストリームを入れ直し、復号した TS を受信機のバッファへ渡します。

復号は、`transport_scrambling_control` が 0 でないパケットの、ヘッダー以降の 184 バイトを AES-128-CTR で行います。鍵はストリームの中の鍵パケットで届きます。0xEC はセッションの通知、0xC0〜0xCF は 64 バイトのコンテンツ鍵のブロックで、CBC と CMAC で開きます。

機材が自分のものでないセッションを続けて通知したとき (電源の入れ直しの後、カードの抜き差しの後など) は、新しい相互認証が必要になります。受信のスレッドを数秒止めないよう、復号器は要求を立てるだけにして、別のスレッドが相互認証をやり直し、ストリームを入れ直します (機材は、ストリームを有効にした時点のセッションで鍵を包み続けるためです)。要求の間隔は 10 秒以上空けます。

PAT が複数の番組を持つとき (この機体の 27ch では 4 番組) は、INI の `Dth11Program` で選びます。既定の `first` は、PAT で番号が最小の番組です。

## 実装の構成

OS に依存しない共通層は `driver/common/dth11/` にあり、機材とのやり取りは、制御転送と時刻のコールバックだけを受ける形です (`dth11_ops`)。ホストと自動試験 (模擬機材) が同じコードを使います。

| ファイル | 内容 |
|---|---|
| `dth11_core.c/h` | 機器情報 TLV、起動、選局、ロックと C/N、ストリームの有効化と PID リスト、スロットから TS の取り出し |
| `dth11_tables.h` | 復調器と MxL135RF のレジスター表 (参考実装の表の移植) |
| `dth11_crypto.c/h` | SHA-1、AES-128 (CBC 復号、CTR)、AES-CMAC |
| `dth11_ec.c/h` | secp160r1 の ECDSA (SHA-1) と ECDH |
| `dth11_appkeys.c/h` | 利用者の `CoBDACom.dll` からの資格情報の読み出し |
| `dth11_cepm.c/h` | 相互認証と、TS の復号器 |
| `dth11_psi.c/h` | PAT と PMT の収集、番組の PID リスト |
| `host/devices/dth11_device.cpp/hpp` | `DriverHost_PX4` の機種クラス (受信機、ストリーム、再認証のスレッド) |

## 設定

`DriverHost_PX4.ini` の機種定義 (`Type="DTH11"`) の設定です。

| キー | 既定 | 内容 |
|---|---|---|
| `Dth11AppKeys` | `CoBDACom.dll` | 資格情報を読むファイル。相対パスは `DriverHost_PX4` の実行ファイルの場所が基準 |
| `Dth11Program` | `first` | 復号する番組。`first`、`all` (最後に送った 1 つだけが有効)、サービス ID (`0x0400` など) |
| `Dth11MaxUrbs` | 16 | bulk の読み出しの本数 (1〜64) |
| `ReceiverMaxPackets` | 16384 | 受信機のバッファの大きさ (パケット数) |

BonDriver の INI は `BonDriver_DTH11.ini` と `BonDriver_DTH11-T.ChSet.txt` です (地上波の UHF 13〜62ch)。

## Windows と macOS、Linux のユーザー空間のホスト

- **Windows**: WinUSB の INF は `winusb/pkg/inf/BUFFALO-DT-H11U2.inf` です。BonDriver は `BonDriver_DTH11.dll` (`BonDriver_PX4.dll` の別名) で、配布物 `BonDriver_DTH11_32bit` と `BonDriver_DTH11_64bit` に、INI と ChSet、`DriverHost_PX4.exe` が入ります。`CoBDACom.dll` は入りません。
- **macOS と Linux (libusb)**: 同じ機種クラスを libusb でビルドします。macOS 11.7 (Intel) では、実機で受信できましたが、連続性エラーが出ます ([確認できたこと (macOS)](#確認できたこと-macos))。Linux (libusb) は、WSL2 の USB/IP 経由で 10 分の受信まで確認しました ([確認できたこと (Linux、ユーザー空間のホスト)](#確認できたこと-linux-ユーザー空間のホスト))。
- **Linux のカーネルモジュール**: 未対応です。相互認証と復号をユーザー空間の層に置いたためです。

## 実装元と権利

機材の操作手順 (起動、レジスター表、選局、スロットの形式、リンク暗号の手順と鍵の導出、番組の PID リスト) は、i4M1k0SU 氏の [DTH10-series-driver](https://github.com/i4M1k0SU/DTH10-series-driver) (MIT License、Copyright (c) i4M1k0SU) の実装と記述を、参考にして C に移したものです。
レジスター表は参考実装の表をそのまま移し、各ファイルの冒頭に出典を記しています。

リポジトリに入る値は、機材が公開している情報 (機器情報 TLV) と、参考実装に公開されているレジスター表だけです。純正のアプリケーションの証明書、秘密鍵、IV は含まれません。

## 検証

### 環境

次の構成で確認しました。

- 機材: DT-H11/U2 1台 (ファームウェア 1.0.18、ハードウェア 0x102)。B-CAS カードを挿入
- ホスト: Windows 11 (x64)、MSVC (v143)、WinUSB。DriverHost_PX4 と BonDriver を x64 でビルド
- 受信するチャンネル: UHF 27ch (557.142857 MHz)。C/N は 20〜22 dB
- 検査: `channel_switch_stress` (選局を繰り返し、同期エラー、transport error、連続性エラーを数える) と、1 秒ごとに信号レベルと TS の誤りを読む簡易のツール

### 確認できたこと (Windows 11)

- **10 分の連続受信** (`BonDriver_DTH11`、27ch、`DriverHost_PX4` の統計と、1 秒ごとの信号レベルの読み出し): 6,149,120 パケット (約 14〜16 Mbps)。同期エラー 0、TEI 0、連続性エラー 0。C/N は 19.0〜22.9 dB (平均 21.3 dB)。ストリームの最大の間隔は 265 ms でした。
- **選局の繰り返し** (`channel_switch_stress`、27ch へ 3 回、各 6 秒): 選局の失敗 0、空の区間 0、同期エラー 0、TEI 0、連続性エラー 0 (合計 160,768 パケット)。
- **所要時間** (`Tune timing`): 初回の選局は、相互認証 (約 5.05 秒) を含めて、最初の TS まで約 8.2 秒でした (ロックの確認は約 0.34 秒)。2 回目以降は、番組表の学習 (約 1.1 秒) を含めて約 2.7 秒でした。
- **番組表**: 27ch の PAT は 4 番組で、PMT をすべて読めました (学習 1.1〜1.4 秒)。復号した 1 番組のビットレートは、10 分の間 13.9〜16.4 Mbps でした。
- **共通層の自動試験**: 上の 6 つが、Windows (x86 と x64、MSVC `/W4 /WX`) と Linux (gcc) で通ります。`dth11_appkeys_test` は、実物の `CoBDACom.dll` からも、証明書と秘密鍵、1951 個の IV の候補を読み出せました (参考実装と同じ数です)。
- **この確認で見つけて直した不具合**:
  - OUT のデータに読み取り専用の表を渡すと、WinUSB が失敗しました (`dth11_core` が複写してから転送します。試験を足しました)。
  - 選局の後に最初に完了する C/N の測定が、30.0 dB (表の上限) のような値になりました (読み捨てます)。

### 確認できたこと (Linux、ユーザー空間のホスト)

Ubuntu 24.04 (WSL2、カーネル 6.18) で、`DriverHost_PX4` と `px4rec` を libusb 1.0 でビルドして確認しました。機材は Windows 側の `usbipd` で WSL へ渡しています (USB/IP 経由であり、Linux へ直接つないだ実機ではありません)。root で起動し、`DriverHost_PX4.ini` で他の機種の `ProductId` を `0xffff` にして、この機材だけを見せています。

- **自動試験**: 6 つとも通ります (`ctest`)。
- **10 分の連続受信** (`px4rec -i 0 -d 600 T 27`): 6,391,163 パケット (約 17.1 Mbps)。同期ずれ 0、TEI 0、連続性エラー 0 でした。ホストの統計 (`cc_gaps`) も 0 です。
- **所要時間**: 相互認証 約 5 秒、番組表の学習 約 1 秒、初回の選局から最初の TS まで 約 7.6 秒でした。
- **診断プログラム**: 共通層を libusb の同期転送で直接動かすと、セッションの通知 (0xEC) の ID が相互認証の結果と一致し、番組表をそろえて読めました。

アンテナ線がゆるんで C/N が 8.0 dB まで落ちたときは、本放送が出ず (8 秒で約 98 KB)、復号も始まりませんでした。アンテナを挿し直すと、C/N 18.9 dB で上のとおりに受信できました。受信の品質が悪いときの症状は、Windows でも同じでした (C/N が約 7.5 dB で、番組表が最後まで読めませんでした)。

### 確認できたこと (macOS)

macOS 11.7 (Intel)、root なし、libusb 1.0.27、Apple clang で、`DriverHost_PX4` と `px4rec` をビルドして確認しました。試験の間は `caffeinate -dis` でスリープを止め、`DriverHost_PX4.ini` で他の機種の `ProductId` を `0xffff` にして、この機材だけを見せています。

- **自動試験**: 6 つとも通ります。`dth11_appkeys_test` は、実物の `CoBDACom.dll` でも通りました。`device_parity_test` も通ります。
- **相互認証、番組表の学習、復号**: Windows と同じ手順で通りました (相互認証 約 5.1 秒、番組表の学習 0.6〜3.4 秒)。復号の失敗は 0、鍵が無くて捨てたパケットは 10 分で 1 でした。
- **受信**: 27ch を `px4rec -i 0 -d <秒> T 27` で録画できました。同期ずれ 0、TEI 0 です。

**Windows と違う点 (未解決)**: 連続性エラーが出て、実行ごとにばらつきます。

| 条件 | 録画 | 連続性エラー |
|---|---|---|
| 読み出し 16 本、10 分 | 5,719,450 パケット | 18,045 (0.32%) |
| 読み出し 16 本、30 秒を 3 回続けて | 約 28 万パケットずつ | 5、165、43 |
| 読み出し 16 本、40 秒を 3 回続けて | 約 31〜40 万パケットずつ | 190、4,678、41,831 |
| 読み出し 48 本、4 分 | 2,530,409 パケット | 1,238 (0.05%) |
| 読み出し 64 本、4 分 | 2,114,327 パケット | 149,393 (7%) |

- 読み出しの本数を増やしても改善は一定せず、本数が原因とは言えません。
- 受信のスレッドの処理は、1 回の読み出し (32 KiB) あたり最大 3 ms で、復号の失敗は 0 です。復号器の取りこぼしが原因ではありません。AES-CTR の復号は、この Mac で約 26 万パケット/秒です (必要なのは約 1.1 万パケット/秒)。
- 同じ Mac で、他の機種 (PIX-DT295) の受信では連続性エラーが出ていません。原因は未調査です。試験の間に Spotlight の索引付け (`mdworker_shared`) が動いていたため、Mac の負荷の影響を疑っています。
- 初回の起動で、`libusb_claim_interface` が一度だけ `LIBUSB_ERROR_NOT_FOUND` で失敗し、`DriverHost_PX4` を起動し直すと再現しませんでした。

### 未確認のこと

- Linux (libusb) に機材を直接つないだ実機 (確認したのは WSL2 の USB/IP 経由)
- macOS での連続性エラー (上の表) の原因と、Windows と同じ品質にする方法
- 10 分を超える連続受信と、スリープからの復帰
- 受信中の機材の抜去と、カードの抜き差し (新しい相互認証の経路は、模擬機材の自動試験だけで確認しました)
- 複数のチャンネルの切り替え (確認した範囲では 27ch だけを受信できる環境でした)
- TVTest での視聴 (参考実装の `dth` と TVTest の組み合わせでは視聴できましたが、この実装そのものでは未確認です)

## 試験の手順

共通層の自動試験は、次の 6 つです (Windows は `winusb/build.ps1` が x86 と x64 で実行し、macOS と Linux は `macos/` の CMake の `ctest` で実行します)。

| 試験 | 内容 |
|---|---|
| `dth11_core_test` | 模擬機材で、機器情報 TLV、起動の順序、選局、C/N の換算、スロットの取り出し、転送の失敗の伝播を確認する |
| `dth11_crypto_test` | SHA-1、AES、CBC、CTR、CMAC を、規格の例の値で確認する |
| `dth11_ec_test` | 機材が実際に返した証明書と署名の検証、署名の往復、ECDH を確認する |
| `dth11_appkeys_test` | 合成した PE 画像から、証明書、秘密鍵、IV を取り出せることを確認する。環境変数 `DTH11_TEST_COBDACOM` に純正の DLL のパスを指定したときは、その実物でも確認する |
| `dth11_cepm_test` | 機材側を模擬して、相互認証の 6 段、再試行と期限、不正な応答の拒否、鍵パケットの処理、復号、再認証の要求の間隔を確認する |
| `dth11_psi_test` | PAT と PMT の解析、複数のパケットにまたがるセクション、CRC の検査を確認する |

実機の試験は、`BonDriver_DTH11.dll` を `channel_switch_stress` で読み込んで行いました。

```
channel_switch_stress.exe BonDriver_DTH11.dll 0 14 14 3 6000
```

引数は、チューニング空間 (0)、チャンネル (27ch は ChSet の 14 番目)、同じチャンネルへの再選局の回数、1 回あたりの測定のミリ秒です。
