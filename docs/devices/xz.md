# I-O DATA GV-MVP/XZ2

## 対応範囲

GV-MVP/XZ 系は USB `04bb:0530` で、GV-MVP/XZ、XZ2、XZ3 が同じ ID を使います。
この資料の実機の結果は、すべて **GV-MVP/XZ2 の 1 台**で得たものです。XZ と XZ3 の機材は確認していません。

機材は地上デジタル (ISDB-T) チューナー1基と、内蔵の B-CAS カードスロットを持ちます。
USB ブリッジを兼ねる SoC は Fujitsu MB86H58A (チップ ID `MB8AC018`、FR30 系の CPU)、復調器は TOSHIBA TC90512 (TC90522 系の I2C。`0x18` が地上波、`0x19` が衛星)、チューナーは復調器の中継 (`0xFE`) の先 (I2C `0x60`) にあるモジュールです。
チューナーのモジュールは、型番が Sony の「SMT-LJ100」です (基板上のモジュールの表記です。モジュール内部の IC の型番は特定していません)。

Linux の `px4_drv` が、地上デジタルを `/dev/xzvideoN`、内蔵カードを `/dev/px4card/<ID>` として公開します。
Windows と macOS では、ユーザー空間のホスト `DriverHost_PX4` が受信とカードを提供します ([Windows と macOS](#windows-と-macos) を参照)。
映像デバイスは `px4video*` と同じ ptx ioctl と read API で、カードは他機種と同じ `px4_card` の ioctl です。

対象外は次のとおりです。

- BS / CS (ISDB-S) と LNB 給電。復調器の `0x19` 側の初期化の列は記録してありますが、受信は確かめていません
- GV-MVP/XZ と GV-MVP/XZ3 の機材 (USB ID は同じで、`probe` が boot0 の署名で識別して、違えば断ります)

この対応は実験的です。実機での確認は Linux、Windows、macOS で行い、確認した範囲は後述します。

## 起動直後の機材だけを対象にする

ホストから SoC を直接操作します。
機材の ROM (boot0) が処理する状態を前提にするため、`probe` は次を全て確かめてから何かを書きます。

| 確かめる内容 | 満たさないときの結果 |
|---|---|
| チップ ID (`0xF00000` が `MB8A`) | `-ENODEV` (別の機種) |
| boot0 の署名 (`0xE9CE8` の 8 バイトが `b4 27 9f 8d 00 0c 46 00`) | `-ENODEV` (別の版の boot0。hook の位置と出口が違い、書くと機材が止まるおそれがある) |
| 窓の即値 (`0xE9A2C`、`0xE9D78`) が既定の `0x00F00000` | `-EBUSY` |
| 状態の語 (`0x82008`) が 0 | `-EBUSY` |
| boot0 の hook (`0xE9F48`) が元の値 (`c4 0d 02 a0 a8 10 e3 0e`) | `-EBUSY` |

`-EBUSY` のときは「機材を挿し直す」のログを出します。他のドライバやツールが hook を使った後、異常終了した後は、USB の抜き差しが必要です。
`px4_drv` は受信を止めるときと、モジュールの取り外し (`rmmod`、unbind) のときに、hook を元へ戻します。このため、取り外した後の再読み込みは、そのまま受信できます。
USB の切断のときは機材へ書けないため、戻す操作は行いません。

## 仕組み

### ホストからの操作

ホストは、ベンダー要求 `0xBC` で、機材のメモリとレジスタを 24 ビットのアドレスで直接読み書きします。
アドレスの上位 8 ビットが `wValue` の上位バイト、下位 16 ビットが `wIndex` です。

- 読み出しは 1 回 64 バイトまでです。
- 書き込みは **1 回 4 バイトまで**です。64 バイトの書き込みは XZ2 で失敗しました (PIX-DT295 は 64 バイトまで書けるので、共通層を流用せず、別に作っています)。

取り込みブロック (`0xD00000`) は 24 ビットの範囲内にあるので、PIX-DT295 のような boot0 のアドレス変換 (窓) の書き換えは使いません。

### 起動と選局

1. SoC の初期化: クロック、PLL、I2C コントローラの端子を、ファームウェアの常駐プログラムが使う表の順序で書きます。表は 27 件 + 永続の 8 語ありますが、実機の試験 (ddmin) で、地上波の受信に必要だった **9 件**に絞っています (`xz_board.c`)。
2. 前面の初期化: 復調器 `0x18` と `0x19` へ、ファームウェアが送った I2C の書き込みを、記録どおりの順序で再生します (初期化 58 件)。
3. 選局: 続く 18 件を再生します。このうち、チャンネルで変わるのは 1 件の 2 バイトだけで、チューナーのレジスタ `0x14` (下位) と `0x15` (上位) に、`周波数 [MHz] × 64` の整数部を書きます (13ch、25ch、30ch の記録の比較で確認)。
4. ロックの判定: 復調器の `(0x80 & 0x28) == 0` かつ `(0xB0 & 0x0F) >= 8` (他機種の `tc90522_is_signal_locked` と同じ判定)。選局の書き込みの後、約 0.4〜0.5 秒でロックします。

前面の表 (76 件) は `driver/common/xz/xz_fe_tables_gen.h` で、`tools/xz_fe_trace.inc` (ファームウェアの動作を観察した記録) から `tools/gen_xz_fe_tables.py` で生成します。

**前面の項目を減らす最小化は成立しませんでした。** 経緯を「この確認で見つけて直した不具合」に書きます。

### TS の経路

取り込みブロックは、TS を SDRAM のリング (`0x8138EC00`、192 KiB) に、192 バイトのユニット (4 バイトのタイムスタンプ + 188 バイトの TS) で書きます。
機材内の自作プログラム (FR30、368 バイト) が、リングから bulk IN `0x81` へ、512 バイトのパケットで TS を送ります。

- **hook:** boot0 の `0xE9F48` (8 バイト) を書き換えて、本体 (`0xE1000`) へ飛ばします。書き込みが 1 回 4 バイトまでなので、2 回に分けます。hook の位置は、次の書き込みの要求自身が通る経路なので、実機で通った順序だけを使います (導入は前半 → 後半、復元は後半 → 前半。逆順は試していません)。
- **郵便受け:** 引数と結果は、本体の領域内の郵便受け (`0xE1180`) に 4 バイトずつ書き、起動は別の 4 バイトの書き込み (`wValue` の下位が `0x7D`、アドレス `0xE11FC`) で出します。PIX-DT295 の作業領域 (`0xC4620`) と違い、要求と応答の組の間に別の制御転送が入っても壊れません。このため、カードの転送が、ポンプの組の完了を待ちません。
- **取り込みの順序:** 取り込みブロックの設定 → 機材内プログラムの導入 → bulk IN の URB (8 KiB × 16 本) → ポンプのスレッド → ライタの開始。ライタは、読み出し側が動いてから開始します (先に開始すると、約 50 ms でリングが 1 周して、未読のデータを上書きします)。
- **読み出し位置:** 送り終えた位置を 192 バイトの倍数へ切り下げて、読み出し位置 (`0xD0202C`) に書きます。
- **開始前の読み捨て:** 前回の受信が URB を先に止められて終わると、機材の送信バッファに最後の数パケットが残るため、受信の開始の前に読み捨てます。

ホストのスレッドは、書き込み位置 (`0xD02028`) を読み、溜まった分を 16 パケットの倍数 (最大 128) で送らせます。

### カード

UART のレジスタの配置 (`0xFEA000`〜) は PIX-DT295 と同じなので、FIFO の読み取り、送信、速度設定は `torne_card` のものを使います。XZ2 で違う点は次の 3 つです。

- 検出: `0xFEA01C` の bit10 が立っていれば挿入あり (PIX-DT295 のように端子の語とは XOR しません。カードなしの状態で bit10 が 0 になることは、実機で確かめていません)。
- 電源投入: 17 段の列で、途中の線の値が 0、最後が 6 です (PIX-DT295 の極性 0 の手順は 8)。端子の語は読まず、定数で持ちます。
- 電源切断: PIX-DT295 と同じ 5 段。

T=1 のフレームの完了判定は、カーネルにも `px4_card` にもなく、フレーム単位で read / write する側が担当します。
実機の試験では、「受信が途切れるまで待つ」方式は、受信中に応答の途中で 60 ms を超える隙間ができて、60 秒に 1 回失敗しました。**3 バイトのヘッダ (NAD、PCB、LEN) の長さと、INF、EDC の 1 バイトを足したフレーム長で完了を判定する**方式にすると、往復は約 90 ms から約 30 ms に短くなりました。

## ロックと寿命

PIX-DT295 の構成に倣い、`operation_lock` → `card_uart_lock` → `control_lock` の順に取ります。ポンプのスレッドは `control_lock` だけを取り、制御転送は 1 つずつ完結させます。
`control_lock` は `mutex_lock_interruptible()` で眠って待ちます。待ち時間は、ロックを持つ側の転送の期限で抑えられます。

`probe` が失敗した機材 (`-EBUSY`、`-ENODEV`) は、何も公開しません。
切断または unbind では、カードを外し、ポンプのスレッドと URB を止め、hook と本体の領域を元へ戻し、復調器を休止させてから、受付を閉じます。クロック系のレジスタは元へ戻しません (前面が動作中に戻すと、周辺のレジスタブロックが応答しなくなった事故があったためです)。
受信中の unbind では、止められる最中のポンプが待ち時間切れになるのは想定内で、切断処理に入った後は、そのエラーを記録しません。

## 実装元と権利

- コードは `px4_drv` の GPL-2.0-only の新規ファイルです (`driver/common/xz/`、`driver/linux/xz_device.[ch]`)。機材内の FR30 のプログラムも、この実装のために書いたもので、機械語は `tools/fr30/xz_e3.s` から生成します (`tools/fr30/gen_xz_program.py`)。
- SoC の初期化の値と、前面の I2C の列は、ファームウェア (mAgicVISION が再配布する `firmware.bin`) の動作を、実機で観察して得た**事実** (アドレス、値、順序) です。観察の方法は 2 つで、(a) 常駐プログラムのレジスタの表のデータを読む、(b) 常駐プログラムの RAM 上のコピーに記録の処理を足して、I2C の通信を記録する、です (機材の ROM とファームウェアの配布物は変更していません)。**ファームウェアの機械語は取り込んでいません。**
- boot0 の署名の位置と、窓の即値の位置は、mAgicVISION の MIT ライセンスの部分と、実機の boot0 の逆アセンブルで確認しました。GPL の部分は、事実の確認にとどめています。
- 取り込みブロックの設定は `torne` の実装 (GPL) の配置を出発点にし、ファームウェアの設定関数の値 (`0xD01004 = 0x04000000`、`0xD0108C = 0xFFFFFFFF`) に合わせました。`torne` 流の値では、TS ではないデータが流れました。
- 値の意味は、特定できていません。観察した値のままです。

## Windows と macOS

Windows と macOS では、Linux のカーネルモジュールの代わりに、ユーザー空間のホスト `DriverHost_PX4` が、同じ共通層 (`driver/common/xz`) を USB 越しに動かします。
ホストの機種クラスは `host/devices/xz_device.cpp` です。この節は、GV-MVP/XZ2 に必要な部分だけをまとめます。

| | Windows | macOS |
|---|---|---|
| 受信のソフト | `DriverHost_PX4` と `BonDriver_XZ.dll` | `DriverHost_PX4` と `px4rec` |
| USB の層 | WinUSB (INF は `winusb/pkg/inf/GV-MVP-XZ.inf`) | libusb |
| 設定 | `BonDriver_XZ.ini` と `BonDriver_XZ-T.ChSet.txt`、`DriverHost_PX4.ini` の DeviceDefinition18 | `macos/DriverHost_PX4.ini` (同じ定義) |
| 機種クラス | `host/devices/xz_device.cpp` (共通) | 同左 |

Linux と同じく、起動直後の機材だけが対象です。ホストは、hook を元へ戻せなかった (抜去の後など) 機材を、挿し直すまで受信に使いません。

### 確認できたこと

Windows 11 (x64) と Intel Mac (macOS 11.7) で、**GV-MVP/XZ2 の 1 台**を、地上波のアンテナ付きで確認しました。

| 環境 | 条件 | 結果 |
|---|---|---|
| Windows | 同一チャンネルの再選局 8 回と、2 チャンネル間の切り替え 8 回 | 同期ずれ、TEI、連続性エラーとも 0 |
| Windows | 10 分の連続受信 (ch21) | 6,888,448 パケット、同期ずれ、TEI、連続性エラーとも 0 |
| Windows | 受信中のカード通信 (WinSCard、200 ms と 20 ms の間隔、各 60 秒) | カードの失敗 0、受信は連続性エラー 0。`winscard_api_test` も通過 |
| Windows | 受信中の USB の抜去と挿し直し | ホストは落ちず、新しい機器として登録され、再び受信できた |
| macOS | 3 台 (XZ2 と DT295 の 2 台) の同時受信 (60 秒と約 11 分) | 予定の時間を最後まで受信 (約 11 分は 7,577,301 パケット)。11 分の受信は、ch21 の電波の乱れとみられる TEI を含む |
| macOS | XZ だけを有効にした DriverHost での連続録画 (60 秒 + 20 秒 x 4、27ch) | 5 回とも成功。連続性エラーは 0.005〜0.200% |
| macOS | `px4rec --b25` (40 秒) | スクランブルのパケットが 94.8% から 0.0% (23 パケット) になり、復号できた |
| macOS | 受信と同時のカード通信 (APDU、計 719 回) | APDU の失敗 0 件、遅延は平均 70 ms、最大 105 ms |
| macOS | 受信中の USB の抜去と挿し直し | ホストは落ちず、挿し直した XZ で再び受信できた |

確認の途中で見つかった事項は次のとおりです。

- **スレッドの優先度 (Windows):** ポンプとストリーム読み出しのスレッドを高い優先度にしないと、連続性エラーが出ます。詳細は「Windows での確認の条件」を参照してください。
- **同一チャンネルの再選局 (Windows):** BonDriver の `NumberOfBuffersToIgnoreAfterPurge` を 0 にすると、パージ直後の先頭に古いデータが残り、連続性エラーが出ます。`BonDriver_XZ.ini` は 1 にしています。
- **抜去の後の受信機の破棄:** クライアントの `Close()` が戻るまで受信機を破棄しないと、抜去の後にホストがクラッシュします。ホストの機種クラスは待つ作りにしてあります。
- **macOS の連続性エラー:** XZ は、同じ録画でも時間によって大きく変わります (0.005〜3.161%)。カードの APDU を送らない対照でも同程度なので、APDU は原因ではありません。アンテナの分配や XZ のチューナーの感度が原因かは、アンテナを分けた比較をしていないため、特定していません。
- **macOS のスリープ:** Mac がスリープすると、受信中の USB が止まります。受信の試験は `caffeinate` でスリープを止めて行います。

### 未確認のこと (Windows と macOS)

- GV-MVP/XZ と GV-MVP/XZ3 の機材、BS / CS (対象外)。
- Windows の x86 ビルドでの実機の受信、カード、抜去 (x86 のビルドと、共通層の自動試験は通過。実機の試験は x64 だけ)。
- Windows の他の機材 (PX-S1UD など) との同時使用、カード通信中のカードを開き直す処理。
- XZ の `ReadStat` (C/N)。換算を確認していないため未対応で、試験ツールの `signal` は常に 0 です。
- macOS の root での起動、`launchd` への登録、Apple Silicon、macOS 11 以外。
- macOS の長時間の受信と、PC/SC (Apple の IFD ホスト) を通した受信との同時利用。

## 検証

### 環境

この資料で「検証環境」と呼ぶのは、次の仮想マシンです。USB 機材はパススルーで接続しました。

- 通常のカーネル: Debian 13 (Linux 6.12.116、デバッグ無し)。
- デバッグ用カーネル: 同じ版のカーネルに、lockdep (`PROVE_LOCKING`)、`DEBUG_MUTEXES`、`DEBUG_SPINLOCK`、KASAN (generic)、`DEBUG_KMEMLEAK`、UBSAN を足したもの。`DEBUG_ATOMIC_SLEEP` は無効でした。

機材は GV-MVP/XZ2 の 1 台です。B-CAS カードは内蔵スロットに 1 枚入れました。受信したチャンネルは UHF 25ch が中心です。

### 確認できたこと

| 試験 | 結果 |

| `probe` | `/dev/xzvideo0` と `/dev/px4card/<ID>` を公開する |
| 25ch の受信 (20 秒、60 秒) | 同期ずれ 0、TEI 0、連続性エラー 0 (17.2 Mbps) |
| 起動と停止の繰り返し (5 秒 × 12) | すべて欠落 0 |

抜き差し直後の機材では、25ch の 10 秒の受信で、TEI は開始直後の 1 秒目に 3 個 (ロック直後の復調の安定前の誤りと推定) で、2 秒目以降は 0 でした。ロックの後に 0.5 秒待ってから受信を始めます。

カードの往復が約 91 ms と長い行は、試験ツールが「途切れるまで待つ」方式のためで、ドライバの値ではありません。

共通層は、機材を模擬した自動試験 (`tests/xz_core_test.c`、`tests/xz_card_uart_test.c`) で、識別 (別の版や使用済みの機材に何も書かない)、書き込みが 4 バイト・読み出しが 64 バイトを超えないこと、SoC の値、I2C の通信と失敗、前面の表と周波数の差し替え、取り込みの書き込み順序、hook の導入と復元 (どの転送が失敗しても元へ戻る)、ポンプの引数と結果の判定を確認しています。コードを意図的に壊した変異 (23 通り) を、すべて検出できることも確認しました。

### この確認で見つけて直した不具合と、訂正

- **前面の最小化が成立しなかった。** 実機の試験 (ddmin) で前面の項目を絞ったところ、最初の結果 (8 件) は、TS のパケット数が全再生の約 1.73 倍 (null パケットの増加、30.6 Mbps) でした。合格の基準が「欠けがない」だけで、全再生との同一性を見ていなかったためです。基準にパケット数 (全再生の ±7%) を加えてやり直した結果 (別の 8 件) は、パケット数は同じでも、**TEI が約 18% 出ました**。試験の間のリセット (静止 + クロックの復元) が、復調器とチューナーの内部状態を戻さず、前の試行の設定が落とした項目を補っていたためと考えられます。前面は記録どおりの全項目 (76 件) を使います。SoC のレジスタは、復元で起動直後の値へ戻ることを読み戻しで確認していますが、SoC の 9 件の確認は、抜き差し直後で 25ch の 10 秒を 1 回行ったのが最初です。
- 復元でクロック系のレジスタを戻したとき、前面が動作中だと、周辺のレジスタブロック (`0xF00000`〜`0xF1FFFF`) が応答しなくなった事故が 1 回ありました (抜き差しで復旧)。このため、通常の経路ではクロックを戻しません。
- ホストが機材の bulk IN を先に止められる unbind では、機材の送信バッファに最後の数パケットが残ります (PIX-DT295 と同じ現象)。受信の開始の前に読み捨てます。

### Windows での確認の条件

Windows 11 (10.0.26200) に GV-MVP/XZ2 を直接接続し、試験用の INF (リポジトリの INF ではない。`Include=winusb.inf` の最小の INF) で WinUSB を導入して、ユーザー空間の試験ツール (共通層をそのまま使う。このリポジトリには含めていません) を実行しました。ビルドは、WSL (Ubuntu 24.04) の mingw-w64 (gcc 13、posix スレッド) です。この確認は、ユーザー空間の試験ツールによるものです。製品としての Windows の経路 (DriverHost_PX4、BonDriver) の確認は、前の「Windows と macOS」の節に記載しています。

Windows の USB 層 (WinUSB) は、書き込み (OUT) の制御転送でも書き込み可能なメモリを要求します。共通層は const のデータ (機材内プログラム) をそのまま渡すので、Windows の `ops` で、転送の前に書き込み可能なバッファへコピーしました (コピーしないと、エラー 998 で機材内プログラムを導入できません)。カーネルモジュールは bounce バッファを使うので、影響を受けません。

**Windows の連続性エラーの原因は、ポンプとストリーム読み出しのスレッドのスケジューリング遅延でした。** 600 秒の試験 (スレッドの優先度は通常) では、連続性エラーが 14〜32 個出て、リングの最大のバックログは 154〜181 KB (192 KiB の約 80〜92%) に達しました (Linux のカーネルモジュールでは、最大 約 26 KB で、連続性エラー 0)。ポンプのループが 30 ms 以上遅れた周期が 11〜12 回あり (最大 71〜88 ms、ポンプ要求 1 回が最大 62〜81 ms)、連続性エラーは、その直後の約 40〜120 ms 以内に、同じ時刻にまとまって (1 回のバーストに 6〜16 個) 出ました。リング (192 KiB) は、約 85 ms 分の TS しか保てないため、遅れが約 80 ms を超えると、一周して未読のデータが上書きされると考えられます。

切り分けの結果は次のとおりです (いずれも 25ch、600 秒)。

| 条件 | 連続性エラー | ポンプのループの遅れの最大 | バックログの最大 |
|---|---|---|---|
| カードあり、優先度は通常 | 14 | 71 ms | 161 KB |
| カードなし、優先度は通常 | 32 | 88 ms | 154 KB |
| カードあり、プロセスを HIGH、メインを TIME_CRITICAL、リーダーを HIGHEST | 0 | 7.2 ms | 21 KB |
| カードあり、**スレッドだけ** (メインとリーダーを HIGHEST、プロセスは通常) | 0 | 12.5 ms | 34 KB |

カードの転送は原因ではなく (カードなしでも発生)、プロセス全体の優先度を変えなくても、ポンプとリーダーのスレッドの優先度を上げるだけで解消しました。Windows のホストでは、ポンプのスレッドとストリームの読み出しのスレッドを、高い優先度にする必要があります。別の対策として、SDRAM のリングを大きくする方法が考えられますが、リング以外の SDRAM の使用領域を確認していないため、試していません。

### 実機のホストでの追加確認 (2026-11-21)

Debian 13 (カーネル 6.12.117、デバッグ用の設定なし) の実機のホスト (仮想マシンを使わない) で、このリポジトリの `px4_drv` をビルドして読み込み、GV-MVP/XZ2 1 台を確認しました。
共通層の自動試験は、Linux (gcc)、Windows (MSVC v143 の x64 と x86) とも通り、`xz_core_test` は 718 件、失敗 0 でした。

- probe が通り、`/dev/xzvideo0` として登録されました。
- UHF 13、16、21、22、25、27、30ch で選局でき、約 17.2 Mbps、同期ずれ、TEI、連続性エラーとも 0 でした。
- PIX-DT295 Rev.02、PX-Q3U4 (ISDB-T の 4 ノード)、Sony CECH-ZD1 J 2 台、PX-S1UD V2.0 と同時に 120 秒受信しました (3 回)。XZ2 は 3 回とも、同期ずれ、TEI、連続性エラーとも 0 でした。同時に受信した PX-Q3U4 には、断続的に TEI と連続性エラーが出ました (1 回は 4 ノードすべてで TEI 約 5,800〜8,500 件、連続性エラー 74〜96 件)。PX-Q3U4 だけの 4 ノードの受信でも TEI 418 件が出たことがあり、XZ2 を加えたことによるとは言えません。

### Linux の PC/SC 経路での確認 (2026-11)

`pcscd` の IFD ハンドラーの修正 (挿抜の監視で、カード I/O の期限を渡す) の前後で、この機種のカードは、次のとおりでした。

- 修正前: `pcscd` に登録されるが、起動の約 1 秒後から「Status unavailable」になる (検出がすべて `ETIMEDOUT`)。
- 修正後: 「Card inserted」、B-CAS (地上デジタル) と識別され、初期化コマンドを 10 回送って、10/10 成功 (SW=9000、71〜88 ms)。DT295 の TS (158,044 パケットのスクランブル) を、このカードで復号して、残りは 20 パケットでした。

自機の TS の受信と、受信しながらのカード通信は、USB の物理的な抜き差しをした後の機材で確認しました。

- 最初に、別のツール (Mirakurun の `recisdb`) が使い、止まった後の機材が、「起動直後」の状態に戻らず、`XZ board setup failed: -110` でドライバーの初期化に失敗しました。ホストでの USB の再列挙や、ドライバーの再 probe では回復せず、USB の物理的な抜き差しで回復しました (前述の、起動直後の機材だけを対象にする制約のとおり)。

| 確認項目 | 結果 |
|---|---|
| 自機の TS (UHF 27ch、20 秒、228,678 パケット) を、自分のカードで復号 | スクランブル 209,362 パケット (91.6%) が **0**。`put` と `get` のエラー 0 |
| 単独で 30 秒の受信 (`pcscd` の動作中、検出あり) | TEI 0、連続性エラー 0 |
| 単独で 30 秒の受信 (`pcscd` の停止中) | TEI 0、連続性エラー 0 (検出の有無で差なし) |
| 5 機種の同時受信 60 秒と、3 つのカードへの APDU の連続送信 (毎秒 5 回) | XZ の TEI 0、連続性エラー 0。XZ のカードへの APDU は 255 回すべて成功、最大遅延 97 ms |

`pcscd` のエラーとカーネルログの `BUG` や `WARNING` は、0 件でした。

## 試験の手順

自動試験は、機材なしで実行できます。

```bash
gcc -Wall -Wextra -fsanitize=address,undefined -I driver/common/xz tests/xz_core_test.c \
    driver/common/xz/xz_{link,board,frontend,program}.c -o xz_core_test && ./xz_core_test
gcc -Wall -Wextra -fsanitize=address,undefined -I driver/common/torne -I driver/common/xz tests/xz_card_uart_test.c \
    driver/common/xz/xz_card.c driver/common/torne/torne_card.c -o xz_card_uart_test && ./xz_card_uart_test
```

機材内プログラムと前面の表の元は、次のとおりです。

| ファイル | 用途 |
|---|---|
| `tools/fr30/xz_e3.s` | 機材内のプログラム (FR30) の元。`fr30-elf-as` などで組み立てた機械語が `xz_program_gen.h` |
| `tools/fr30/gen_xz_program.py` | 組み立てた機械語を、`xz_program_gen.h` の C の配列にする |
| `tools/xz_fe_trace.inc` | mAgicVISION ファームウェアが前面へ送った I2C の通信の記録 (観察した事実) |
| `tools/gen_xz_fe_tables.py` | 上の記録の書き込みから、前面の表 `xz_fe_tables_gen.h` を作る |

受信は、`PTX_SET_CHANNEL` の `freq_no` に、UHF の物理チャンネル + 50 を渡します (例: UHF 25ch は 75)。
