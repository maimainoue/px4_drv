# PIXELA PIX-DT295

## 対応範囲

PIX-DT295 は USB `06b8:103b` (Rev.01) と `06b8:105c` (Rev.02) の2種類があり、どちらも地上デジタル (ISDB-T) チューナー1基と、内蔵の B-CAS カードスロットを持ちます。
USB ブリッジを兼ねる SoC は Fujitsu MB86M01 (FR30 系の CPU)、復調器は TC90522 系 (I2C `0x10`)、チューナーは MaxLinear MxL603 系 (復調器の中継経由) とみられます。

Linux の `px4_drv` が、地上デジタルを `/dev/dt295videoN`、内蔵カードを `/dev/px4card/<ID>` として公開します。
Windows と macOS では、ユーザー空間のホスト `DriverHost_PX4` が受信とカードを提供します ([Windows と macOS](#windows-と-macos) を参照)。
映像デバイスは `px4video*` と同じ ptx ioctl と read API です。カードは他機種と同じ `px4_card` の ioctl です。

対象外は次のとおりです。

- BS / CS (ISDB-S) と LNB 給電
- 公式のファームウェアを使う方式。ファームウェアは暗号化された約 1.8 MB の画像で、扱っていません

この対応は実験的です。実機での確認は Linux、Windows、macOS で行い、確認した範囲は後述します。

## Rev.01 と Rev.02 の見分け方 (Linux)

2 つの版の違いを示す情報は、USB の製品 ID だけです (`103b` が Rev.01、`105c` が Rev.02)。デバイスファイル名 (`/dev/dt295videoN`) には、版が入りません。

- **カーネルログ**: 接続のたびに、`px4_usb 3-3:1.0: DT295 Rev.02 (06b8:105c) receiver registered (bulk IN 0x81)` のように、版と USB ID が出ます。行頭の `3-3:1.0` が、USB のポートです。
- **使用中のデバイスから**: `/sys/class/dt295/` のデバイスから、親の USB デバイスの `idProduct` を読めます。

  ```sh
  for n in /sys/class/dt295/dt295video*; do
    d=$(readlink -f "$n")
    echo "$(basename "$n"): $(cat "$d/../../../idVendor"):$(cat "$d/../../../idProduct")"
  done
  ```

- **udev**: `udevadm info -a /dev/dt295video0` の `ATTRS{idProduct}` に、同じ値が出ます。版ごとの別名が欲しいときは、次のルールで、シンボリックリンクを作れます (`%n` はデバイスファイルの番号。Linux 6.12 で、`dt295-rev02-0` が `dt295video0` を指すことを確認しました)。

  ```
  SUBSYSTEM=="dt295", ATTRS{idProduct}=="103b", SYMLINK+="dt295-rev01-%n"
  SUBSYSTEM=="dt295", ATTRS{idProduct}=="105c", SYMLINK+="dt295-rev02-%n"
  ```

  このルールは、リポジトリの `etc/99-px4video.rules` へ入れていません。別名が利用者向けの契約になるためです。
- Windows と macOS のホスト (`DriverHost_PX4`) は、この Linux の変更の対象外です。別の変更として、[Windows と macOS](#windows-と-macos) の節に記載しています。

## 起動直後の機材だけを対象にする

公式のファームウェアも、機材内のプログラムも使わずに、ホストから SoC を直接操作します。
機材の ROM (boot0) が処理する状態を前提にするため、`probe` は次の2つを確かめて、満たさなければ `-EBUSY` と「機材を挿し直す」のログで断ります。

- 状態の語 (`0x82008`) が 0
- boot0 の hook (`0xEA6FC`) が元の値 (`c4 6d 02 b0 a8 10 e3 2b`)

他のドライバやツールが hook を使った後、異常終了した後は、USB の抜き差しが必要です。
`px4_drv` は受信を止めるときと、モジュールの取り外し (`rmmod`、unbind) のときに、hook と窓を元へ戻します。このため、取り外した後の再読み込みは、そのまま受信できます。
USB の切断のときは機材へ書けないため、戻す操作は行いません。

## 仕組み

### ホストからの操作

- ホストは USB ベンダー要求 `0xBC` で、機材のメモリとレジスタを24ビットのアドレスで読み書きします。
- **1回の要求は64バイトまでです。超えると機材が固まり、抜き差しが必要になります。** 共通層は、すべての転送を64バイトずつに分けます。
- wValue の下位バイトが1のとき、boot0 はマスク付き書き込み (`*a = (*a & ~mask) | (value & mask)`) を行います。
- boot0 のアドレス変換 (`0x80000`〜`0x9FFFF` を `(アドレス & 0x3FFFF) + 即値` へ変換。即値の既定は `0x00F00000`) の即値を、RAM 上で書き換えて、24ビットを超える領域 (取り込みブロックの `0x1900000` など) を標準の読み書きで扱います。即値は2か所 (`0xEA3D8`、`0xE9EBC`) にあり、両方を書き換える必要があります。

### 起動と選局

チップ側の設定は4つ、I2C コントローラの準備は8つ、復調器とチューナーの設定は4つの書き込みだけです (最小化の結果)。以下はチップ側の4つです。

| 書き込み | 値 | 意味 |
|---|---|---|
| `0xF10118` | `0xFFFF` | クロックのゲート。bit4 が取り込みブロックのクロック。起動直後は `0x9000` |
| `0xF10014` | `0xD082` | 汎用ポートの出力許可。bit1 を落とすと復調器が I2C に応えない |
| `0xF10018` | `0x0002` | 汎用ポートの出力値。bit1 を落とすと復調器が I2C に応えない |
| `0xF10114` | `0x8020` | bit5 は I2C の動作側のクロックの許可。落とすと I2C の転送が終わらない |

`0xF10014` と `0xF10018` の bit1 は、両方が立っているときだけ、読み出し用の `0xF1001C` の bit1 が立ちます。
復調器の許可またはリセットの線とみていますが、基板上の線までは確認していません。`0xF10114` の bit5 も、I2C の動作のクロックの許可という推定で、直接の証拠はありません。

復調器とチューナーは I2C (`0x10`、チューナーは `[0xFE, 0xC0, レジスタ, 値]` の中継) で、次の設定で動きます。選局は 90〜770 MHz で、周波数は MHz の1/64の単位でチューナーに渡します。

| 対象 | 設定 |
|---|---|
| 復調器 | `0x0E = 0x71` (T の出力をバスへ)、`0x1D = 0x02` (TS の出力ピンの許可) |
| チューナー | `0x03 = 0x01` (水晶の校正)、`0x05 = 0x1B` (IF のスペクトラム反転なし、利得)、`0x08 = 0x05` (C/N を上げる) |
| 選局 | 復調器 `0x01 = 0x40` (選局直後の乱れを抑える)、チューナー `0x12 = 0`、`0x0B = 1`、`0x10/0x11` に周波数、`0x31/0x7C` (700 MHz 未満は `0x81/0x1F`、以上は `0x91/0x9F`)、`0x12 = 1` |

チューナー `0x08 = 0x05` と復調器 `0x01 = 0x40` は、実機の最小化で得た最初の4つの設定には含まれず、公開された別実装 (`soralis0912/MB8AC031-CFW` の `fe_dt295.h`、MIT) の記述を手掛かりに足しました。
実機 (Rev.01 と Rev.02、UHF 13/16/21/30/37ch) で、足す前と後を比べた結果は次のとおりです。

| 設定 | 効果 | コスト |
|---|---|---|
| チューナー `0x08 = 0x05` | C/N の生値 (小さいほど良い) が約 5,400 (ch13、21) と約 4,700 (ch30) から、約 3,300 前後に下がる。チューナーをリセットすると元に戻る | なし |
| 復調器 `0x01 = 0x40` | チャンネル切り替え直後の最初の約 0.4 秒に出ていた TEI (3,000〜18,000) と連続性エラーが 0 になる | `PTX_SET_CHANNEL` の所要時間が約 80 ms から約 440〜660 ms に伸びる |

別実装が挙げる、復調器 `0x1C = 0x20` や、`0x03` と `0x23` の下位ビットの消去、チューナーのリセット (`0xFF`) は、足しても、この環境では目に見える差がなかったため、入れていません。別実装は、他のソフトが設定を残した状態からでもロックするための書き込みとして挙げています。

ロックの判定は、復調器 `0x80 & 0x28 == 0` かつ `0xB0 & 0x0F >= 8` で、`px4_drv` の TC90522 ドライバと同じです。
ロックの直後は TMCC が確定するまで TEI 付きのパケットが出るため、ロックを検出してから 0.5 秒待って、受信を始めます。
C/N は復調器 `0x8B` からの3バイトの生の値で、dB への換算は未確認です。信号強度は未対応 (0 を返す) です。

I2C の転送が失敗すると、バスが数秒から十数秒詰まることがあるため、失敗の直後に再試行せず `-EIO` などで返します。

### TS の経路

TS は取り込みブロック (ベース `0x1900000`) が SDRAM のリング (物理 `0x0138EC00`、`0x30000` バイト) へ書き、192バイトの単位 (先頭4バイトのタイムスタンプ + 188バイトの TS) で並びます。
取り込みブロックの設定の配置は、`torne` の `stream_setup()` と同じです (リセット解除の列の値は別。後述)。同じ TS 取り込みの回路で、192バイトの単位から188バイトの TS への整形は `torne_framer` をそのまま使います。

リングから bulk IN (EP `0x81`) への送出は、機材内に置く小さな FR30 のプログラム (288バイト、`tools/fr30/dt295_pump.s`) が行います。

- ホストは、boot0 の hook を、RAM 上の本体 (`0xE1000`) へ分岐する命令に書き換え、制御転送で「このリングの位置から N パケット送れ」という要求を出します。要求と応答は同じ64バイト (`0xC4620`) を通るので、組の間は他の制御転送を止めます。
- 要求の単位は512バイトのパケットを16の倍数 (最大128) にします。受信側は 8 KiB の非同期 URB を16本使います。512バイトずつの同期読み出しは約29 Mbps で頭打ちになり、リングが溢れます。
- ホストは、書き込み位置 (`0x1902028`) を読み、溜まった分だけを要求して、送り終えた位置を192バイトの倍数に切り下げて読み出し位置 (`0x190202C`) へ書きます。
- **リングは約50 ms で1周します。** ライタ (`0x1902010`) の開始は、ポンプが動き出した後にします。先に開始すると、読み出される前に1周して、未読のデータが上書きされます。

機材内のプログラムから、取り込みブロックと `0xF10118` へ書くと、機材が止まります。これらの書き込みは、ホストの標準の経路 (窓) で行い、機材内のプログラムは読み出しと送出だけを行います。

取り込みブロックの設定で、実機で意味が分かったことは次のとおりです。

- `0x1900000` は、エンジン中核のリセットです。保持されるのは bit17 だけです。
- `0x1900004` は、サブブロックのリセットです。bit18 と bit19 を書くと、8つ上の bit26 と bit27 が読み出し専用のフラグとして立ちます。bit24 は bit23 の反転です。
- `0x1900020` は、ホストから書いても保持されず、書かなくても受信できます。このため書き込みません。

### カード

カード UART (`0xFEA000`〜`0xFEA03F`) は torne と同じ配置で、`torne` のカード層をそのまま使います。
T=1 の処理は `px4_card` 側です。各操作の直前に、`PX4_CARD_SET_TIMEOUT` で残り時間を指定します (`px4_card` の契約です)。受信と同時に使えます (200 ms ごとの往復を受信中に続けて確認しています)。

## ロックと寿命

| ロック | 守るもの |
|---|---|
| `operation_lock` | `ptx_chrdev` の open、release、tune、set_capture、read の直列化 |
| `control_lock` | USB 制御転送 (1転送、またはポンプの要求と応答の組) |
| `card_uart_lock` | カード UART のレジスタ1回分の組 |
| `stream_lock` (spinlock) | 整形のバッファと出力。スリープしない |

取得順は `operation_lock`、`card_uart_lock`、`control_lock` です。ポンプのスレッドは `control_lock` だけを取ります。
制御転送のロックは `mutex_lock_interruptible()` で眠って待ちます。`mutex_trylock()` と `msleep(1)` の繰り返しにすると、`msleep(1)` が1ジフィー (4 ms) 眠るため、カードの転送と衝突するたびにポンプが遅れ、リングが溢れて TS が欠けました。

USB の unbind は、USB コアが `disconnect` の前に URB を止めます。受信中の unbind では、止められる最中のポンプが待ち時間切れになるのは想定内で、切断処理に入った後は、そのエラーを記録しません。
前回の受信が URB を先に止められて終わると、機材の送信バッファに最後の数パケットが残るため、受信の開始の前に読み捨てます。

## 実装元と権利

- コードは `px4_drv` の GPL-2.0-only の新規ファイルです (`driver/common/dt295/`、`driver/linux/dt295_device.[ch]`)。機材内の FR30 のプログラムも、この実装のために書いたもので、機械語は `tools/fr30/dt295_pump.s` から生成します (`tools/fr30/gen_dt295_program.py`)。
- 取り込みブロックの設定は `torne` の実装 (GPL) と、`px4_drv` の TC90522 ドライバを参照して、同じ配置と、大半の値を使っています。チューナーの `0x03` と `0x05` は、MaxLinear が公開している MxL603 の API の資料と、レジスタの意味を照合しました。
- 公開されている別の実装 (`denpa`、AGPL-3.0-or-later) の動作を外から観測して、次の値の手掛かりを得ています。それらのコード、レジスタ表、機械語は転記していません。
  - チップ側の `0xF10014`、`0xF10018`、`0xF10114` の値
  - 取り込みブロックのリセット解除の列 (`0x19000C4`、`0x1900000`、`0x1900004`)
  - カードの電源投入と切断の順序と待ち時間 (`dt295_card.c`)。動作は2台の実機で確認していますが、各段の必要性は確かめ直していません
- 上の値の意味は、実機の読み戻しと bit ごとの試験で絞り込みました。「汎用ポートの bit1」と「I2C の動作のクロック」が、基板上のどの線かは確認していません。

## Windows と macOS

Windows と macOS では、Linux のカーネルモジュールの代わりに、ユーザー空間のホスト `DriverHost_PX4` が、同じ共通層 (`driver/common/dt295`) を USB 越しに動かします。
ホストの機種クラスは `host/devices/dt295_device.cpp` です。この節は、PIX-DT295 に必要な部分をまとめます。

| | Windows | macOS |
|---|---|---|
| 受信のソフト | `DriverHost_PX4` と `BonDriver_DT295.dll` | `DriverHost_PX4` と `px4rec` |
| USB の層 | WinUSB (INF は `winusb/pkg/inf/PIX-DT295.inf`) | libusb |
| 設定 | `BonDriver_DT295.ini` (Rev.01 と Rev.02 の受信機の定義) と `BonDriver_DT295-T.ChSet.txt`、`DriverHost_PX4.ini` の DeviceDefinition19 (Rev.01) と 20 (Rev.02) | `macos/DriverHost_PX4.ini` (同じ定義) |
| 機種クラス | `host/devices/dt295_device.cpp` (共通) | 同左 |

Linux と同じく、起動直後の機材だけが対象です。
Windows の INF は、Rev.01 と Rev.02 で装置インターフェースの GUID を分けています。`libwdi` (Zadig など) で WinUSB を導入している機材を、この INF へ切り替えると GUID が変わり、`pix-userland` や `denpa` など、別のソフトで同じ機材を使っている場合は、影響が出ます。元へ戻すときは、`pnputil /delete-driver` でこの INF を削除します。
BonDriver は、空いている最初の受信機を選びます。Rev.01 と Rev.02 の特定の 1 台を使うときは、受信機の定義を 1 つにした `BonDriver_DT295.ini` の複製を使います。

### 確認できたこと

Windows 11 (x64) と Intel Mac (macOS 11.7) で、**Rev.01 と Rev.02 を 1 台ずつ**、地上波のアンテナ付きで確認しました。

| 環境 | 条件 | 結果 |
|---|---|---|
| Windows | 2 台の同時受信 (40〜70 秒) と、再選局 4 回 × 3 回 | 同期ずれ、TEI、連続性エラーとも 0 |
| Windows | Rev.02 だけの約 11 分 (ch21) | 13,146,112 パケット、同期ずれ、TEI、連続性エラーとも 0 |
| Windows | 2 台同時の約 11 分 (ch21) を 3 回 | Rev.01 は 2 回が全部 0 で、1 回は TEI 3 と連続性 2 の 1 か所。Rev.02 は 3 回のうち 2 回、約 1 秒の範囲に TEI と連続性エラーが集中 (TEI 283 と 383)。同時に受信した他の機材には出ておらず、電波の乱れとみられるが、確認していない |
| Windows | 他機種 1 台を加えた 3 台 (DT295 は 2 台) の受信中に全リーダーのカード通信 (100 ms 間隔、50 秒) | 失敗 0、最大 107 ms |
| Windows | 受信中の USB の抜去と挿し直し (Rev.01 と Rev.02 を 1 回ずつ) | ホストは落ちず、新しい機器として登録され、再び受信できた |
| macOS | 他機種 1 台を加えた 3 台 (DT295 は 2 台) の同時受信 (60 秒と約 11 分) | 予定の時間を最後まで受信 (DT295 は約 11 分に 13,146,19x パケット)。TEI は、3 台とも最後の数分に同時に増えており、電波の乱れとみられる |
| macOS | `px4rec --b25` (3 台、各 12 秒) | スクランブルのパケットが 0 になり、復号できた |
| macOS | 受信中の USB の抜去と挿し直し (Rev.01) | ホストは落ちず、他の 2 台は 400 秒の全体を、エラー 0 で受信できた |

確認の途中で見つかった事項は次のとおりです。

- **同一チャンネルの再選局 (Windows):** BonDriver の `NumberOfBuffersToIgnoreAfterPurge` を 0 にすると、パージ直後の先頭に古いデータが残り、連続性エラーが出ます。`BonDriver_DT295.ini` は 1 にしています。
- **抜去の後の受信機の破棄:** クライアントの `Close()` が戻るまで受信機を破棄しないと、抜去の後にホストがクラッシュします。ホストの機種クラスは待つ作りにしてあります。
- **macOS のスリープ後の選局の失敗 (原因は未確定):** Mac のスリープからの復帰後に、DT295 の 2 台で、選局のたびに `DT295 I2C 0x10: transfer failed (-60)` となり、ロックできない状態が続きました。`DriverHost_PX4` を再起動すると、機材を挿し直さずに回復しました。3 回の発生は、いずれもスリープの後でした。受信の試験は `caffeinate` でスリープを止めて行います。

### 未確認のこと (Windows と macOS)

- Windows の x86 ビルドでの実機の受信、カード、抜去 (x86 のビルドと、共通層の自動試験は通過。実機の試験は x64 だけ)。
- 2 台同時の長時間の受信で出た、短い範囲のエラーが、電波の乱れだけによるかの切り分け (USB の共有の影響の否定)。
- Windows の他の機材 (PX-S1UD など) との同時使用、カード通信中のカードを開き直す処理。
- DT295 の `ReadStat` (C/N)。換算を確認していないため未対応です。
- macOS の Rev.02 の USB の抜去、待機中の DT295 の抜去、root での起動、`launchd` への登録、Apple Silicon、macOS 11 以外。
- macOS のスリープ後の選局の失敗の原因と、ホストを再起動せずに回復する方法。

## 検証

### 環境

- 仮想マシン: Proxmox 上の Debian 13 (カーネル 6.12.116)。USB 機材はパススルーです。
- 通常のカーネル: `linux-image-amd64` (6.12.116+deb13-amd64、デバッグ無し)。`dkms add`、`build`、`install` で導入しました。
- デバッグ用カーネル: 同じ版のカーネルに、lockdep (`PROVE_LOCKING`)、`DEBUG_ATOMIC_SLEEP`、`DEBUG_MUTEXES`、`DEBUG_SPINLOCK`、KASAN (generic)、`DEBUG_KMEMLEAK`、UBSAN を足して構築しました。
- 受信したチャンネルは UHF 25ch です。B-CAS カードは、2台に1枚ずつ入れました。

### 確認できたこと (Rev.01 と Rev.02)

| 試験 | 結果 |
|---|---|
| 2台同時 60 秒 + カードの往復 (通常のカーネル) | どちらも約30 Mbps、1,195,008 パケット、同期ずれ 0、TEI 0、連続性エラー 0。カードは272往復で失敗 0 (平均 81 / 86 ms) |
| 同上 (デバッグカーネル) | 同じ結果。カードは平均 95 / 102 ms |
| 2台同時 300 秒 + カードの往復 (ロックの修正後) | 各5,976,064 パケット、同期ずれ 0、TEI 0、連続性エラー 0。カードは1,400往復前後で失敗 0 |
| Rev.01 の 600 秒 | 11,951,616 パケット、同期ずれ 0、TEI 0、連続性エラー 0 |
| 開始と停止の繰り返し (各2秒、2台で8周ずつ)、読み手の強制終了 | 失敗 0、飛び 0 |
| 受信中とカード中の unbind と再接続 (2台同時、3周) | 最初の受信を含めて、飛び 0 |
| `rmmod` と `insmod` | 取り外し後の再読み込みで、そのまま受信できる |
| DKMS での導入、udev ルールとファームウェアの配置 | 警告なしでビルドでき、2台とも probe できる |
| デバッグカーネルでの全試験 | lockdep、KASAN、UBSAN の指摘と、kmemleak の検出は 0 件 |

表の 300 秒と 600 秒の行は、ライタの開始の順序などを変える前の版の結果です。それ以外の行は、最終版の結果です。

共通層は、機材を模擬した自動試験 (`tests/dt295_core_test.c`、`tests/dt295_card_uart_test.c`) で、起動直後の判定、書き込みの順序、64バイトの上限、窓の設定と復元、hook の導入と復元、I2C とポンプの失敗の注入を確認しています。

### この確認で見つけて直した不具合

- カードの往復と受信を同時に動かすと TS が欠けた (制御転送のロックの取り方。上述)。
- ロックの直後の約1秒に TEI と連続性エラーが集中した (TMCC の確定前)。ロックの後に0.5秒待つようにした。
- 受信を開始した直後にライタが先にリングを1周し、中断後の最初の受信で連続性エラーが出た。ライタの開始をポンプの後へ移した。
- 受信中のデバイスの取り外しの後に、開いたままのファイルを閉じると、`cdev` の解放済みの領域を参照した (KASAN で検出)。DT295 に限らない `ptx_chrdev` の共通の不具合で、[20261113_common_fixes.md](../20261113_common_fixes.md) に記録しています。

### Linux の PC/SC 経路での確認 (2026-11)

Rev.02 の 1 台 (Rev.01 は、この確認の時点で、バスにありません) を、Linux 6.12.116 (仮想マシンへ USB パススルー) で、`pcscd` 2.3.3 と IFD ハンドラー (`pcsc/`) を通して確認しました。
復号には、libaribb25 0.2.10 を使いました (手法は、[torne の別紙](torne.md) と同じ)。

| 確認項目 | 結果 |
|---|---|
| `pcscd` の読み取り機の登録とカードの状態 | `PIXELA PIX-DT295 Smart Card Reader [ID: …] (シリアル)` として登録され、「Card inserted」、B-CAS (地上デジタル) と識別された |
| B-CAS の初期化コマンド (`90 30 00 00 00`) を 10 回 | 10/10 成功、応答 61 バイト、SW=9000、61〜66 ms (T=1) |
| 自機の TS (UHF 27ch、20 秒、397,399 パケット) を、自分のカードで復号 | スクランブル 210,527 パケット (53.0%) が **0** |
| 受信しながらのカード通信 (4 機種の同時受信 60 秒と、APDU を毎秒 5 回) | DT295 の TEI 0、連続性エラー 0。APDU は 270 回すべて成功、最大遅延 92 ms |
| `pcscd` の動作中と停止中の受信 (各 4 回、10 秒) | すべて TEI 0、連続性エラー 0 (別の 1 回だけ、動作中の最初の 10 秒に TEI 3201 と連続性エラー 241 が出たが、再現しなかった) |

また、`pcsc/Info.plist` に、この機種 (2 つの版) が載っていなかったため追加しました。載っていないと、`pcscd` が、カードを認識しません。

### チューナー `0x08` と復調器 `0x01` を足した確認 (2026-11)

「起動と選局」の表の `0x08 = 0x05` と `0x01 = 0x40` を足した版を、Proxmox 上の Debian 13 の仮想マシン (カーネル 6.12.117、DKMS の `px4_drv` 0.7.1 を入れ替え) で確認しました。
Rev.01 と Rev.02 を同時に開き、アンテナの分岐から UHF 13/16/21/30/37ch を受信しています。

| 確認項目 | 結果 |
|---|---|
| ch21 の 600 秒 (2 台同時) | 各 11,951,616 パケット、同期ずれ、TEI、連続性の飛びとも 0 (10 秒区間 59/59 がクリーン) |
| ch30 の 600 秒 (2 台同時) | 同上 |
| ch13、16、21、30、37 の切り替え 6 周 (各 8 秒、2 台同時) | 切り替え 60 回すべて、同期ずれ、TEI、連続性エラーとも 0 |
| 足す前 (同じ機材) の切り替え直後 | 最初の約 0.4 秒に TEI 3,000〜18,000、連続性エラー 300〜3,400 |
| C/N の生値 | ch13、21 は約 5,400、ch30 は約 4,700 から、約 3,300 前後 (ch30 は約 2,800) に下がる |

- 足した設定の組み合わせは、`0x08` と `0x01` のほか、`0x1C = 0x20`、`0x03` と `0x23` の下位ビットの消去、チューナーのリセットを、モジュールパラメーターで切り替えて測りました (2 周)。TEI が 0 になるのは `0x01 = 0x40` を書いたとき、C/N が下がるのは `0x08 = 0x05` を書いたときで、残りの 3 つには差がありませんでした。
- 測定の途中で、1 回だけ、`0x08` を書いた直後に、ch13 で TEI が約 58%、続く約 3 分間の選局の失敗が出ました。起動直後の状態から測り直した 4 回では出ず、原因は未確認です (アンテナ側の一時的な不具合の可能性が残ります)。
- C/N の生値は、dB への換算式がないため、「約 40% 減」としか言えません。別実装は、`0x08 = 0x05` で「C/N が 2〜4.7 dB 上がる」としていますが、この値との対応は確認していません。

### 実機のホストでの追加確認 (2026-11-21)

Debian 13 (カーネル 6.12.117、デバッグ用の設定なし) の実機のホスト (仮想マシンを使わない) で、このリポジトリの `px4_drv` をビルドして読み込み、Rev.01 と Rev.02 を 1 台ずつ確認しました。
共通層の自動試験は、Linux (gcc)、Windows (MSVC v143 の x64 と x86) とも通り、`dt295_core_test` は 220 件、失敗 0 でした。

- 2 台とも probe が通り、Rev.02 は `/dev/dt295video0`、Rev.01 は `/dev/dt295video1` として登録されました。
- **Rev.02**: UHF 13、16、21、22、25、27、30ch で選局でき、約 29.9 Mbps、同期ずれ、TEI、連続性エラーとも 0 でした。
- **Rev.01**: 試した UHF 13〜30ch (7 チャンネル) のすべてでロックしませんでした (`EAGAIN`)。アンテナの接続を確認していないため、機材と配線のどちらの問題かは未確認です。
- Rev.02 を、PX-Q3U4 (ISDB-T の 4 ノード)、Sony CECH-ZD1 J 2 台、PX-S1UD V2.0 と同時に 120 秒受信しました (2 回)。Rev.02 は 2 回とも同期ずれ、TEI、連続性エラーとも 0 でした。同時に受信した PX-Q3U4 の 1〜2 ノードに、断続的な TEI (8〜453 件) と連続性エラー (最大 180 件) が出ましたが、DT295 を加えない同時受信でも、2 台目の PX-Q3U4 に同様の誤りが 1 回出ており、DT295 を加えたことによるかは切り分けていません。
- 別のプロセスがデバイスファイルを開いたまま unbind すると、unbind は閉じるまで待たされ、強制終了の 1 秒後に完了しました。再接続後に、Rev.02 を再び約 29.9 Mbps で受信できました (Rev.01 は、再接続後の登録まで)。`dmesg` に警告はありませんでした。
- 確認できていないのは、B-CAS カードの通信、30 分以上の受信、Rev.01 の受信、USB の物理的な抜去です。

### 未確認のこと (Linux)

- 24時間級の連続受信
- `0x08` と `0x01` を足した版の、10 分を超える受信、弱い電波や強い電波でのロックと TEI、700 MHz 以上 (UHF 51ch 以上) の選局。足した設定は、Windows と macOS のホスト (同じ共通層を使う) の実機では、確認していません。自動試験 (`dt295_core_test`、x64 と x86) は通っています。
- `0x01 = 0x40` で選局の所要時間が約 0.5 秒に伸びたことが、受信ソフトの選局に影響しないか。
- 6.1、6.8、6.12 以外のカーネル版でのビルドと動作 (6.1.0-56 と 6.8.0-151 は、DT295 Rev.02 の 10 分の同時受信まで確認。[20261121_linux_other_kernels_validation.md](../20261121_linux_other_kernels_validation.md))
- Rev.01 は、NAS の USB では、試した全チャンネルでロックしませんでした。Proxmox 上の仮想マシンでは、Rev.02 と同じチャンネルでロックしたため、NAS 側の配線かアンテナの条件の可能性があります。確認はしていません。
- PX-W3U4 など他機種との同時使用
- BS / CS (対象外)
- 物理的な切断と再接続は、ライタの開始の順序を変える前の版で確認しました。最終版では再確認していません。

## 試験の手順

自動試験は、機材なしで実行できます。

```bash
gcc -Wall -Wextra -I driver/common/dt295 tests/dt295_core_test.c \
    driver/common/dt295/dt295_{link,board,frontend,program}.c -o dt295_core_test && ./dt295_core_test
```

実機の試験ツールは次のとおりです。

| ツール | 用途 |
|---|---|
| `tools/dt295_chrdev_test.c` | `/dev/dt295videoN` で選局して受信し、同期、TEI、連続性エラーを数える |
| `tools/dt295_card_chrdev_test.c` | `/dev/px4card/<ID>` で、電源投入、ATR、19200 bps への切り替え、T=1 の S ブロックの往復を、200 ms 間隔で繰り返す |
| `tools/dt295_mem_dump.c`、`tools/dt295_mem_mwrite.c` | `px4_drv` を読み込まない機材の、メモリとレジスタの読み書き (libusb) |
| `tools/dt295_i2c.c` | 復調器とチューナーの I2C を直接叩く (libusb) |
| `tools/dt295_ts_live.c` | カーネルモジュールを使わずに、ユーザー空間だけで受信する (libusb) |

受信は、`PTX_SET_CHANNEL` の `freq_no` に、UHF の物理チャンネル + 50 を渡します (例: UHF 25ch は 75)。
