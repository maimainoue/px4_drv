# I-O DATA GV-MVP/HZ2W 対応の実装資料

## この資料の位置づけ

GV-MVP/HZ2W は、Windows と macOS のユーザー空間のホストで、内蔵カード (B-CAS) だけを実装済みです。
地上波の受信 (復調器、チューナー、TS) と、Linux のカーネルモジュールは未対応です。
この資料は、対応を実装する開発者に向けて、メーカー製ドライバーの解析で分かったこと、firmware の取り出し方、実機で確かめるべきこと、実装の段階と各段階の完了条件をまとめたものです。

受信の実装に向けて用意できているのは **firmware の取り出しツール** (`fwtool/asv5211fw`) です。
実機では、取り出した firmware を送って warm (`04bb:0526`) へ起動できることと、基板の識別情報、I2C の一部の応答を確認しました (「[実機で分かったこと](#実機で分かったこと)」)。
復調器とチューナーの型番、TS の形式は、まだ確定していません。
確定していない事項は「[未確認の事項](#未確認の事項)」に分けて記載します。

## 機器の概要

| 項目 | 内容 | 根拠 |
|---|---|---|
| 製品 | I-O DATA GV-MVP/HZ2W。地上デジタル (ISDB-T) のみ、2 系統 | メーカー製ドライバーの INF が、Capture0 / Capture1 と Tuner0 / Tuner1 を定義する |
| USB ブリッジ | ASICEN ASV5211 (8051 系のマイコンを内蔵) | firmware の起動前の USB ID が `1738:5211` で、ローダーが ASICEN のもの (PDB のパスに `asicen_usbloader_driver`) |
| 起動前 (cold) の USB ID | `1738:5211` | ローダーの INF |
| 起動後 (warm) の USB ID | `04bb:0526` | BDA ドライバーの INF |
| 同系統の機種 | PLEX PX-S3U、PX-W3U3 など (ASV5211 を使う機種) | Till0196/coax の `px3` の資料 |

HZ2W は、メーカー製ドライバーでは、firmware を送るローダー (`IODATA_AS11Loader.sys`) と、BDA ドライバー (`IODATA_GV-MVP-HZ2W_HDTV_BDA.sys`) の 2 段で動きます。
BDA ドライバーにはチップ名の文字列がなく、チューナーと復調器の型番は、ドライバーのファイルだけからは確定できていません。

## 解析した配布物

解析に使ったのは、I-O DATA の「GV-MVP/HVX シリーズ サポートソフト」(`gvmvphvx419.exe`) です。
内部に CAB を持つ自己展開形式で、HZ2W のドライバーは `Drivers\HZ2W\` の `x86` と `x64` にあります。

| ファイル | 内容 |
|---|---|
| `IODATA_AS11Loader.inf` / `.sys` | cold の `1738:5211` 用。firmware を送るローダー (版 1.12.04.19、2012-04-19) |
| `IODATA_GV-MVP-HZ2W_HDTV_BDA.inf` / `.sys` | warm の `04bb:0526` 用の BDA ドライバー |

同じ配布物には、NXP SAA7164 系の機種 (GV-MVP/HZ や VZ など) と、XZ 系のドライバーも入っています。
NXP SAA7164 系は USB ブリッジが別物で、HZ2W には当てはまりません。

## firmware の仕組みと取り出し

### ローダーの firmware

ローダーは、16 KB (0x4000 バイト) の firmware を、`.data` に **2 つ**持ちます。

| 版 | 起動アドレス (wIndex) | SHA-256 | 備考 |
|---|---|---|---|
| 主 | `0x5583` | `39428b362d6be2284814d418e57ad86274749973eaf4c68d459c02b072488e41` | HZ2W に送られる版。x86 と x64 のローダーで同一 |
| 古い版 | `0x515f` | `d134890df91427d405ad5619588e63e3220e21f972ede18a9701fec5686b4816` | 送られない。Quixun と PLEX のローダーにも含まれる版 |

ほかのローダーの版は次のとおりです。

| 版 | 起動アドレス (wIndex) | SHA-256 | 備考 |
|---|---|---|---|
| SKNET | `0x55d8` | `f4848c8c091634897f9829e50d2ff8e5dc28792c6b20cf095d38d40379518c7a` | `QRS-UT100B.zip` 同梱の `SKNET_AS11Loader.sys` (x64) の 2 つ目。起動アドレスは、ローダーが各イメージの直前に持つ値と、coax の既知の値の一致による。実機で起動できるかは未確認 |

`QRS-UT100B.zip` の中身は、Quixun ではなく SKNET (BonDriver は HDP2、ini は `Products=3275:7020`) のドライバーでした。
このため、Quixun QRS-UT100B の 2 版 (`0x5399`、`0x53e4`) を、実物のローダーで確かめた記録はありません。
UT100B の実機で、どの版が起動するかは、USB ID と合わせて確認が要ります。

ローダーの中での並びは x86 と x64 で異なります (x86 は主が先、x64 は古い版が先)。
ツールは位置ではなく、復号した内容の SHA-256 で版を識別します。

firmware は、各バイトに 1 を足してから AES-128-ECB で暗号化されています。
鍵と方式は、waya0125/recfriio (MIT、`internal/firmware/firmware.go`) が公開している値で、Quixun のローダーと同じものが HZ2W のローダーでも使えました。
16 KB のうち `0x0c00-0x2000` と `0x2400-0x2800` は、どの firmware でも 0 で埋まっており、ブート ROM へは送りません。
ツールは、この 2 か所が復号後に 0 になる位置を、firmware の候補とします。

### 起動アドレスについて

起動アドレスは、firmware の版で決まり、機種では決まりません。
違うアドレスで起動すると、USB の抜き差しが要ります。
HZ2W の主の版が `0x5583` であることは、x86 のローダーで、firmware の 8 バイト前に格納された 2 バイトの値から確認しました。
この値は、coax が知っているアドレス (`0x5399`、`0x55d6`、`0x55d8`、`0x515f`) にはありません。

### 取り出し方

ビルドは、`fwtool` と同じ手順です。

```bash
make -C fwtool        # fwtool と asv5211fw ができる
```

取り出しは、ローダー (`IODATA_AS11Loader.sys`) を渡します。

```bash
./fwtool/asv5211fw -l IODATA_AS11Loader.sys                       # 候補を一覧する
./fwtool/asv5211fw IODATA_AS11Loader.sys asv5211-firmware.bin     # 主の版を書き出す
```

実行例 (x86 のローダー):

```text
[0] offset 0x5558  sha256 39428b36…488e41
    起動アドレス (wIndex) 0x5583  I-O DATA GV-MVP/HZ2W 用ドライバー 1.12.04.19 (2012-04-19) の firmware
[1] offset 0x9560  sha256 d134890d…4b4816
    起動アドレス (wIndex) 0x515f  古い版 (…) [古い版]
[0] を asv5211-firmware.bin へ書き出しました (16384 バイト)
起動アドレス (wIndex): 0x5583
```

オプションは次のとおりです。

| オプション | 意味 |
|---|---|
| `-l` | 候補の一覧だけを表示し、書き出さない |
| `-n NUMBER` | 書き出す候補の番号 (一覧の左端、0 から)。省略時は、既知で古い版でない最初の候補 |
| `--selftest` | AES-128 と SHA-256 の自己検査だけを行う (FIPS-197 と FIPS 180-4 の試験値) |

終了コードは、成功が 0、firmware が見つからない、または入出力に失敗が 1、使い方の誤りが 2 です。
ツールは起動のたびに自己検査を行い、AES-128 または SHA-256 の実装に誤りがあれば、何も書き出さずに止まります。

### 検証

SHA-256 が、上の表の値と一致することが、取り出しの成功の条件です。
x86 と x64 のどちらのローダーからも、同じ主の版 (`39428b36…`) が取り出せることを確認しました (MSVC と gcc 13 でビルド)。
未知のローダーで firmware が取り出せても、SHA-256 が表にない場合は、ツールが「未知の版」と表示し、起動アドレスを示しません。
その場合は、起動アドレスを推測せず、ローダーの解析で確かめてください。

### 配布について

firmware は I-O DATA の著作物であり、このリポジトリには含めません。
利用者が、自分で入手したドライバーから取り出します。
配置先は、coax との互換のため、ファイル名 `asv5211-firmware.bin` を推奨します。

## 実機で分かったこと

次の確認は、HZ2W の 1 台で、2 つの環境に接続して行いました。

- **検証 PC**: Windows 11 の PC です。機器に WinUSB を割り当てる調査用の INF を使い、制御転送を自作の調査プログラムから送りました。
- **検証ホスト**: Linux のホストです。USB のバスを `usbmon` で記録でき、機器を Windows 10 の仮想マシンへパススルーできます。ベンダーのドライバーは、この仮想マシンで読み込みました。ホストから機器を一時的に仮想マシンから外し、`usbfs` の制御転送で調査プログラムを実行することもできます。

調査プログラムと INF は、このリポジトリには含めていません。
調査は、firmware の送信、GPIO、I2C のレジスタ読み出しと、読み出し準備の書き込みの範囲です。選局、カードの交換、TS の受信の試験は、後の節に記載し、検証ホストで行いました。

### 起動と USB の識別情報

- 取り出した主の firmware (`39428b36…`) を、起動アドレス `0x5583` で、vendor 要求 `0xab` (3 回) と `0xac` (1 回) に分けて送ると、4 回の転送がすべて成功し、約 4 秒後に cold の `1738:5211` が消えて、`04bb:0526` (名称 `GV-MVP/HZ2W`) として現れました。
  転送は、`bmRequestType` が `0x40` で、`wValue` が firmware の中のオフセット、`wIndex` が起動アドレスです。coax と recfriio の記述と一致しました。
- firmware は機器の RAM に送られるだけで、USB を抜く、または電源を切ると cold に戻ります。接続のたびに送る必要があります。
- cold のディスクリプターは、USB 2.0、製造元 `ASICEN`、製品名 `AUSBDTV`、シリアル番号なしです。インターフェースは 1 つ (クラスはベンダー定義) で、バルク OUT `0x01` (512 バイト) だけを持ちます。
- warm のディスクリプターは、製造元 `I-O DATA`、製品名 `GV-MVP/HZ2W` です。インターフェースは 1 つで、バルク IN `0x81` と `0x82` (各 512 バイト) を持ち、OUT の端点はありません。2 本の IN は、2 系統の TS に当たると推測しますが、確かめていません。

### 基板の情報 (GetCusInfo、要求 `0x0c`)

応答は、状態の 1 バイトに続く 57 バイトで、次の内容でした。

| 位置 | 内容 |
|---|---|
| `+0x00` | `ae 36` (意味は不明) |
| `+0x02` | `04 bb 05 26` (ベンダー ID と製品 ID、ビッグエンディアン) |
| `+0x06` | `"I-O DATA  "`、`"GV-MVP/HZ2W     "`、`"GV-MVP/HZ2W IR "` (各 16 バイト) |
| `+0x36` | `03 ff 0e` (最後の `0e` の上位 2 ビットが筐体内の位置で、0) |

この内容は、I2C のアドレス `0xa8` (基板の EEPROM とみられる) の先頭と一致します。

### 基板の写真

基板の写真 (2 枚) から、次のチップが読み取れました。ASV5211 の本体は、この 2 枚には写っていません。

| 位置 (基板のシルク) | 刻印 | 数 |
|---|---|---|
| `TUNER1`、`TUNER2` | `Sony Corp` `SMT-MJ110` `W8L12AB` (ソニー製のモジュール。内部の構成は、写真からは分からない) | 2 |
| `IC1`、`IC2` | `ASICEN` `ASIE5606B` `815517` `0840` `B2` | 2 |
| (基板の名前) | シルクに `KURIHIME-1` | - |

ASIE5606B が 2 個あることから、TS はチューナー系統ごとに ASIE5606 を通るとみられます。
「ASIE5606B の確認」のとおり、2 個とも coax と同じアドレス (`0x4a` と `0x4c`) で応答しました。
SMT-MJ110 は、DTH10-series-driver の資料に、復調器が `0x30`、チューナーが `0xC6` (復調器のレジスタ `0xFE` の中継の先) の構成として載っています (「参考資料とライセンス」)。HZ2W の `0x30` と一致します。

### BDA ドライバーの静的解析

BDA ドライバー (x64) を逆アセンブルして調べました (実行はしていません)。

- USB の制御転送を 1 か所の関数が送り、先頭の 5 バイトが「要求番号、`wValue`、`wIndex`」です。応答の 1 バイト目が状態で、1 が成功です。
- 要求番号は、coax の `asv5211` と同じ系統です。`0x02` (レジスタ読み出し)、`0x06` と `0x07` (ストリームの開始と停止)、`0x08` と `0x10` (GPIO)、`0x0d` と `0x0e` と `0x19` (I2C の書き込み、確定、読み出し) を確認しました。ほかに、`0x03`、`0x04`、`0x05`、`0x09`、`0x0a`、`0x0f`、`0x13`、`0x16`、`0x17`、`0x18`、`0x21`、`0x23` を使いますが、意味は未確認です。
- 論理ターゲット `0xf0` は、書き込みの先頭バイトを I2C の 8 ビットのアドレスとして扱う、生の I2C です。ドライバーは `0x30` (7 ビットで `0x18`) と `0x34` (7 ビットで `0x1a`) を、2 系統の機器として使います。
  - レジスタの書き込み: `[0x30, reg, value]`
  - 読み出し: `[0x30, reg]` を stop なしで書き、続けて `0x19` で読む
  - 複数バイトの書き込み: `[0x30, 0xfe, 0xc0, データ…]`
  - 状態の確認: レジスタ `0x80` と `0xb0`
- ドライバーの初期化関数が、coax の `px3/tschip.go` と同じ手順で、ASIE5606 系のカードインターフェース IC を探します。GPIO (`0x08`) でリセットのパルスを出し (1 系統目は mask `0x11`、2 系統目は `0x80`、値は `0xff`、`0x00`、`0xff` の順で、待ちは 25、25、50 ミリ秒)、レジスタ `0x09` を `0x5a` と `0x4a` (2 系統目は `0x5c` と `0x4c`) から読んで、`(値 >> 1) & 0x0f` が `0x0b` 以下であることを確かめます。

### coax の TC90522 との照合

ドライバーが `0xf0` の `0x30` と `0x34` に行う操作は、Till0196/coax の `demod/tc90522/tc90522.go` が TC90522 (東芝の復調器) に行う操作と、次の点で一致します。

| ドライバーの `0x30`、`0x34` への操作 | coax の TC90522 |
|---|---|
| 初期化の書き込み `0x25=0x00`、`0x23=0x4d` または `0x4c`、`0x01=0x40` | 地上波の停止と再開の列 (`{0x25, 0x00, 0x23, 0x4d}`、`{0x01, 0x40, 0x23, 0x4c}`) |
| レジスタ `0x1c`、`0x1e`、`0x1f` の操作 | `0x1c` を読んで `0x30` のビットを立てる、`0x1e` のマスク書き込み、`0x1c` と `0x1f` の組 |
| 複数バイトの書き込みの先頭 `[0xfe, 0xc0, …]` | 中継のレジスタ `0xfe` の先に、チューナー (`0xc0`) がある |
| 状態の確認にレジスタ `0x80` と `0xb0` | 同期の状態に `0x80`、ビタビの状態に `0xb0` |

waya0125/recfriio の `docs/QRS-UT100B.md` でも、UT100B の復調部は東芝の TC9050x/TC9051x 系で、`0x1c`、`0x1e`、`0x1f`、`0x9d` を使い、チューナーは `0xfe` の中継の先 (`0xc0`、8 ビットのレジスタ) にある、と書かれています。

このため、HZ2W の `0x30` と `0x34` は、TC90522 系の復調器で、SMT-MJ110 の中にあるとみられます (TUNER1 と TUNER2 の 2 系統)。
ただし、レジスタの値の読み出しで、TC90522 の値と確認できたものはなく、型番の確定ではありません。
HZ2W のブリッジの firmware では、coax が使う論理ターゲットの割り当て (`0x30` と `0x32`) が通らず、`0xf0` の生の I2C 経由で応答する点も、coax の `px3` と違います。

### ベンダーのドライバーの起動時の通信 (usbmon)

検証ホストで、ベンダーの BDA ドライバーを入れた Windows 10 の仮想マシンへ機器をパススルーし、ドライバーを再起動 (デバイスの再起動) する間のバスを、`usbmon` で記録しました。
記録から機器の分だけを取り出した結果は、34 パケットで、ディスクリプターの取得に続き、次の要求でした。選局と受信は含まれません。

| 順 | 要求 | 内容 | 応答 |
|---|---|---|---|
| 1 | `0x0c` (58 バイト) | GetCusInfo | 上の「基板の情報」と同じ |
| 2 | `0x17`、`wValue` = 2 (3 バイト) | 意味は未確認 | 状態 1 に続けて `11 52` |
| 3 | `0x08`、`wValue` = `0xfb07` | 主 GPIO を、値 `0x07`、mask `0xfb` で書く。ビット 0 と 1 を High、ビット 3 から 7 を Low にし、ビット 2 は変えない | `0x07` |
| 4 | `0x10`、`wValue` = `0x0200` | 拡張 GPIO を、値 `0x00`、mask `0x02` で書く。ビット 1 だけを Low にする | `0x0d` |

ファームウェアを送った直後の GPIO は、主が `0xff`、拡張が `0x0f` です。ドライバーは、起動時にこの状態を `0x07` と `0x0d` へ変えます。
主のビット 4 と 7 は、下のリセットの線で、起動時に Low (リセットを掛けた状態) になります。

### ASIE5606B の確認

検証ホストで、機器を仮想マシンから外し、ベンダーのドライバーと同じ順序を `usbfs` の制御転送で再現しました。

1. 上の表の 3 と 4 の GPIO を書く。
2. 1 系統目は mask `0x11`、2 系統目は mask `0x80` で、主 GPIO に `0xff`、`0x00`、`0xff` の順でパルスを出す (待ちは 25、25、50 ミリ秒)。リセット後の主 GPIO は `0x97` になる。
3. レジスタ `0x09` を、要求 `0x02` で `wIndex` 0 として読む。

結果は、`0x4a` と `0x4c` の 2 つのアドレスで `0x06` (coax が想定する B 版の値) が返り、レジスタ `0x00` は `0x00` でした。`0x5a` と `0x5c` は応答しません。
このため、ASIE5606B は、基板の写真のとおり 2 個あり、coax の `px3` と同じアドレス (`0x4a`、`0x4c`) にあります。1 系統目が `0x4a`、2 系統目が `0x4c` に当たります。

これまで応答しなかったのは、主 GPIO が `0xff` のまま (ドライバーの起動時の `0x07` を書いていない状態) で、リセットのパルスだけを出していたためです。
リセットの線が High のままだった可能性や、`0x07` の書き込みと拡張のビット 1 が電源に当たる可能性が考えられますが、どのビットの効果かは、切り分けていません。

要求 `0x02` を、アドレス `0x00` から `0xfe` の偶数と、レジスタ `0x00` と `0x09` について読み出しだけで走査しました (リセット後)。
応答があったのは、`0x4a`、`0x4c`、`0xa8` (EEPROM) だけです。`0x00` から `0x0e` と `0xf0` から `0xfe` は `0xff` を返す領域で、チップではありません。
`0x30` と `0x34` は、`0x02` の読み出しでは見えません。

この走査の直後に、`0x4a` と `0x4c` のレジスタ `0x00` から `0x1f` を読んだところ、すべて応答しませんでした。
走査の途中で状態が変わった可能性がありますが、原因は確認していません。

### 実機での応答

次の表のうち、ASIE5606 と `0xf0` の行は、GPIO の状態をドライバーの起動時の値にしていない条件 (主 `0xff`、拡張 `0x0f`) での結果です。
ASIE5606 は、上の「ASIE5606B の確認」の条件で応答します。

| 操作 | 結果 |
|---|---|
| GPIO のリセット (上の手順) | 成功。応答 (GPIO の現在値) は、`0x00` を出した直後に、1 系統目が `0xee`、2 系統目が `0x7f` で、信号線が実際に動く。リセット後の待ちを、High の後に 2000 ミリ秒へ延ばしても、結果は変わらない |
| GPIO の現在値 (mask を 0 にして読む) | firmware を送った直後は、主が `0xff`、拡張が `0x0f` |
| GPIO 拡張を 1 ビットずつ Low にする | ビット 0 と 1 は出力として動く (読み戻しが `0x0e` と `0x0d`)。ビット 2 と 3 は、Low にしても `0x0f` のまま。いずれの場合も、ASIE5606 と `0xf0` の応答は変わらない |
| カードインターフェース IC (レジスタ `0x09`) | 主 GPIO が `0xff` のままの条件では、`0x5a`、`0x4a`、`0x5c`、`0x4c` のすべてで応答なし (`wIndex` は 0 と 1 の両方を試した)。ドライバーの起動時の GPIO にしてリセットを出すと、`0x4a` と `0x4c` が `0x06` を返す |
| `0xf0` に、`0x02` でレジスタを読む | `ef 0b d3 b0 ff f1 bf 26 …` の乱雑な値で、レジスタの表には見えない (アドレスの下位ビットが無視され、`0xf2` も同じ先頭) |
| `0xf0` に、アドレス `0x30` と `0x34` で、`[addr, reg]` を書いて読む | `0x30` と `0x34` は同じ応答。レジスタ `0x00` から `0x1f`、`0xc3`、`0xfe` は、1 バイト目がレジスタ番号と同じ値で、2 バイト目は常に `0xa2`。レジスタ `0x80` と `0xb0` は `a2 a2` |
| 同じ読み出しを、`0x20`、`0x32`、`0x36`、`0x40`、`0x70` に | 読むたびに乱雑な値で、規則がない |
| 中継を開く読み出し: `[0x30 または 0x34, 0xfe, 0xc1]` を stop なしで書き、`0x19` で 6 バイト読む | 書き込みも読み出しも成功 (状態 1) だが、データは `fe ef 8b c3 90 ff` (`0x30`) と `fe f1 ff 26 ae c9` (`0x34`) で、UT100B のチューナーが返す `0xc8` の繰り返しではなく、上の乱雑な値に近い。1 バイト目は、書いた 2 バイト目 (`0xfe`) と同じ |
| 同じ読み出しを、SMT-MJ110 のチューナーのアドレス `0xc7` (書き込みは `0xc6`) で | 書き込みも読み出しも成功 (状態 1)。2 バイト目以降は読むたびに変わり、存在しない `0x32` と区別できない。1 バイト目は、`0x30` と `0x34` で `0xfe`、`0x32` では不定 |

読み取れることは次のとおりです。

- `0x30` と `0x34` には、何かが応答しています。ほかのアドレスの乱雑な値とは、明らかに違います。
- 「レジスタ番号と同じ値が返る」形は、通常のレジスタの表ではありません。読み出しの形式が違うか、レジスタ番号の反響なのかを、まだ区別できていません。2 バイト目の `0xa2` は、状態か ID の値の可能性があります。
- TC90522 の想定アドレス (`0x20`、`0x22`、`0x30`、`0x32` を、`0x02` で読んだ) には、期待した応答がありませんでした。一方、上の生の I2C の形式では、`0x30` と `0x34` が応答します。ドライバーのレジスタの操作が coax の TC90522 と一致するため (「coax の TC90522 との照合」)、HZ2W の復調器は、`0x02` の論理ターゲットではなく、`0xf0` の生の I2C で制御する配置とみられます。
- 中継を通したチューナーの読み出しでは、UT100B の `0xc8` の繰り返しは得られませんでした。`0xf0` の生の I2C の読み出しが、チップの値を返しているのか、ブリッジの内部のバッファを返しているのかが、区別できていません (読み出しの先頭の 1 バイトが、書いたバイトの反響に見えるため)。`0x30` と `0x34` が TC90522 系という見立ては、操作の一致によるもので、読み出した値によるものではありません。
- ASIE5606B は、ドライバーの起動時の GPIO にしてリセットを出すと、coax と同じアドレスで応答しました (「ASIE5606B の確認」)。以前の「応答なし」は、アドレスの違いではなく、GPIO の状態の違いによります。
- 復調器 (`0x30` と `0x34`) は、GPIO をドライバーの起動時の値にしても、`0xf0` の読み出しが `a2 a2` のままで、読み出しの形式は分かっていません。ドライバーの選局時の書き込みを記録する必要があります。

### ベンダーのドライバーの動作環境

I-O DATA のローダー (`IODATA_AS11Loader.sys`) と BDA ドライバーは、検証 PC (Windows 11) では、どちらも読み込まれませんでした (問題コード 39)。
署名は有効ですが、2012 年版のクロス署名で、Windows のコード整合性の検査 (イベント ID 3077、3004) に拒否されます。

Windows 10 (19045) の仮想マシンでは、次の手順で読み込めました。

1. I-O DATA DEVICE, INC. の署名証明書を、ローカルコンピューターの「信頼された発行元」に追加する。追加しないと、`pnputil /add-driver` が「カタログの発行者が信頼されていない」と拒否する。
2. `pnputil /add-driver <INF> /install` で、ローダーと BDA ドライバーを導入する。

導入後は、cold の機器がローダーで warm になり、BDA 装置として認識されました。
この証明書は 2012 年に期限が切れていて、Windows の信頼設定を変える操作です。検証用の環境に限って行ってください。

通信記録は、仮想マシンのホストで `usbmon` を使って取りました。

### 選局 (ホストからの再現)

検証ホストで、ベンダーのドライバーが機器を開くときの要求を、記録と同じ順序と間隔で再現し (起動時の GPIO、復調器 `0x30`、`0x34` の初期化表、ASIE5606 のフィルター設定まで)、続けて DTH10-series-driver の MJ110 の手順で選局しました。
手順は、チューナーの中継 (復調器のレジスタ `0xfe` の先、チューナーのアドレス `0xc0`) を使います。

1. 復調器 `0x30` に、レジスタ `0x25` = `0x00`、`0x23` = `0x4d` を書く。
2. チューナーに、レジスタ `0x11` = `0x00`、`0x13` = `0x15`、`0x14` と `0x15` に周波数のワード (1/64 MHz 単位、下位、上位の順)、`0x11` = `0x02` を、中継経由で書く。
3. 復調器に、レジスタ `0x01` = `0x40`、`0x23` = `0x4c` を書く。
4. 約 250 ミリ秒おきに、復調器のレジスタ `0x80` と `0xb0` を読む。

地上波 27ch (557.142857 MHz、周波数のワード `0x8b49`) で、レジスタ `0x80` が `0x00`、`0xb0` が `0xa9` になり、ロックの条件 (`0x80 & 0x3f == 0`、`0xb0 & 0x0f >= 8`) を満たしました。
`0x30` と `0x34` は、TC90522 系の復調器として動作しています。選局の記録も、上の手順と一致しました。

### カードインターフェース (ASIE5606B)

ASIE5606B の 1 系統目 (`0x4a`) にだけ B-CAS カードを挿し、ベンダーのドライバーの順序を、ホストから再現しました (2 系統目の `0x4c` にはカードがなく、再現していません)。

**書き込みの形**

- 要求 `0x03` (レジスタの書き込み) と `0x1c` (ガード付き書き込み) は、**`wLength` を 2 にする**必要があります。応答は、状態と、書いた値の反響です。`wLength` を 1 にすると、書き込みは成功と応答されますが、カードの電源が入りません (レジスタ `0x04` のビット 7 が立たない)。
- レジスタ `0x05` に、ベンダーのドライバーは `0xa0` を書きます (coax の revision 3 の経路は `0x20`)。カードの検出には、これを先に書く必要があります。

**ガード付きの読み書き**

要求 `0x1a` は、呼ぶたびに新しい 16 バイトの乱数 (nonce) を返します。ガード表は、coax の `asv5211/card.go` と同じです (`39 72 30 c3 ad d4 46 36 ba e5 5f 48 ae 14 06 c1`)。

| 要求 | 形 |
|---|---|
| `0x1c` (書き込み) | `wValue` = アドレス \| レジスタ << 8。`wIndex` = `e` \| (`r` ^ `e`) << 8。`e` = 値 ^ guard[`r` & 15] ^ nonce[`r` >> 4]。`r` は任意の 1 バイト (ベンダーは、タイマーの値 ^ `0xcd`) |
| `0x1b` (読み出し) | 応答は 3 バイトで、状態、`b1`、`b2`。`c` = `b1` ^ `b2`、値 = `b2` ^ guard[`c` & 15] ^ nonce[`c` >> 4]。nonce は、直前の `0x1a` の値 |

カードのバッファ (ASIE5606 のレジスタ `0x40` から) には、ビット順が反転した (LSB 先頭の) バイトが入ります。読んだ値は、1 バイトごとにビットを反転すると、ISO 7816 のバイト列になります。書くときも同じです。

**手順** (ベンダーの記録と同じ。いずれも `0x4a`)

1. 主 GPIO を、mask `0xd5` で `0x00`、続けて `0xff` にする (結果は `0xd7`)。1 系統目のリセットのパルス (mask `0x11`) を出す。要求 `0x23` (値 `0x004a`)、`0x21` (値 `0x0100`) を送る。
2. レジスタ `0x05` = `0xa0`、`0x04` = `0x00`、`0x00` = `0x00` を書き、約 100 ミリ秒待って、`0x04` を読む (`0x01`、カードあり)。
3. GPIO を、値 `0xff`、mask `0x01` で書く。`0x00` = `0x08`、`0x04` = `0x80` を書き、約 200 ミリ秒待つ。`0x00` = `0x09` を書き、約 60 ミリ秒待つ。
4. レジスタ `0x39`、`0x03`、`0x04` をポーリングする。`0x04` が `0x81` (カードあり、電源 on) になり、`0x03` に応答の長さ (ATR は `0x0d`) が入る。
5. レジスタ `0x40` から 13 バイトを読み、ビットを反転すると、ATR (`3B F0 12 00 FF 91 81 B1 7C 45 1F 03 99`) になる。
6. 命令の送信 (ガード付き): `0x00` = `0x0c`、`0x01` = `0x01`、`0x02` = フレーム長、`0x38` = 0、`0x3a` = 0、`0x40` から フレーム (NAD、PCB、LEN、INF、EDC。ビットを反転して書く)、最後に `0x00` = `0x0a`。
7. 応答は、`0x03` に長さが入り、`0x40` から読む。

**前提**

- 先に、firmware の送信 (warm への起動)、起動時の GPIO (主 `0x07`、拡張 `0x0d`、「ベンダーのドライバーの起動時の通信」)、1 系統目のリセットのパルス (「ASIE5606B の確認」) を済ませておく。起動時の GPIO を送らずに手順 1 から始めると、`0x23` が応答しない。
- 機器を落とさないために、周期的な処理 (「周期的な処理と、機器が消える現象」) を、カードの手順の間も続ける。

**書き込みの種類** (手順 2 以降の ASIE5606 のレジスタ)

- 電源投入までの、レジスタ `0x00`、`0x04`、`0x05` の書き込みは、通常の書き込み (`0x03`) を使う。
- ATR を読む前の `0x3a` = `0x00` から後の書き込みと、読み出しは、すべてガード付き (`0x1c`、`0x1b`) を使う。ただし、命令の送信中の `0x01` = `0x01` だけは、通常の書き込みを使う。
- ガード付きの書き込みと読み出しの前に、`0x1a` で nonce を取り直す。ベンダーは、各命令の前に取り直す。

**命令のフレーム** (レジスタ `0x40` から書く値。ビットを反転する前の ISO のバイト列と、書く値の両方を示す。カードに依存しない固定の値)

| 命令 | `0x02` (長さ) | ISO のバイト列 | `0x40` から書く値 |
|---|---|---|---|
| T=1 の S ブロック (IFS の要求、INF = `FE`) | 5 | `00 C1 01 FE 3E` | `00 83 80 7F 7C` |
| カード情報の問い合わせ (I ブロック、INF = `90 32 00 00 00`) | 9 | `00 00 05 90 32 00 00 00 A7` | `00 00 A0 09 4C 00 00 00 E5` |

フレームは、NAD、PCB、LEN、INF、EDC (LRC。NAD から INF までの XOR) です。ベンダーは、命令の間に約 100 ミリ秒から 150 ミリ秒待ってから、レジスタ `0x03` (応答の長さ) を読みます。
カード情報の問い合わせの応答は、NAD = `00`、PCB = `00`、LEN = `0x13`、INF が 19 バイト (終わりは SW `90 00`) で、全体は 23 バイトです。INF の中身は、カードごとに異なります。

**バッファのページ** (ホストの実装で分かったこと)

カードのバッファは、レジスタ `0x40` から `0x7f` までの 64 バイトが 1 ページで、レジスタ `0x3a` でページを切り替えます (`0` が先頭の 64 バイト、`1` が次の 64 バイト)。
65 バイト以上のブロックは、`0x3a` を `0` にして先頭の 64 バイトを読み、`0x3a` を `1` にして、同じ `0x40` から続きを読みます。ページを切り替えずに読むと、65 バイト目の読み出しがレジスタ `0x80` (状態) になり、B-CAS の初期化命令 (`90 30`) の 65 バイトの応答で、LRC が合わなくなります (`0x87` のはずが `0x10`)。
書き込みも同じです。74 バイトの命令を、64 バイトで `0x3a` を `1` に切り替えて書いたところ、カードが整合した応答を返しました。3 ページ目以降は未確認です。

**応答の長さ (レジスタ `0x03`)**

- レジスタ `0x00` へ `0x0c` を書くと、`0x03` が `0` に戻ります。命令の送信は、この書き込みから始まるため、前の応答の長さは残りません。
- 電源投入の直後は、`0x03` が `0x01`、中間の値、ATR の長さ (`0x0d`) の順に増えます。前回の値が残る場合があり、長さが安定しているだけでは完成を判定できないため、ATR は構造 (TS、T0、TDi、履歴バイト、TCK) が長さと一致するまで待ちます。

**電源の入れ直し**

命令を実行した後は、電源を入れ直しても ATR が正しく受け取れません (文字化けする、または先頭の 7 バイトが欠ける)。レジスタ `0x01` を `0` に戻しても直りません。1 系統目のリセットのパルス (GPIO の mask `0x11`)、要求 `0x23` (値 `0x004a`)、要求 `0x21` (値 `0x0100`) を送り直すと、命令と電源の入れ直しを 4 回繰り返しても、毎回 ATR が完全に取れました。

**終了**

最後に、`0x00` = `0x0c` (ガード付き) を書き、約 100 ミリ秒待ち、通常の書き込みで `0x80` = `0x00`、`0x04` = `0x00`、`0x00` = `0x00` を順に書きます。レジスタ `0x04` が `0x01` (カードあり、電源 off) に戻ります。

ホストから、ここまでの全体を再現でき、カードの検出、電源、ATR、T=1 の交換が成功しました。
2 系統目 (`0x4c`) には、カードスロットがつながっていないとみられます (製品のスロットは 1 つ)。1 系統目と同じ手順 (2 系統目のリセットのパルスは mask `0x80`、要求 `0x23` の値は `0x004c`) を試した結果は、次のとおりです。

| 項目 | 1 系統目 (`0x4a`、カードあり) | 2 系統目 (`0x4c`) |
|---|---|---|
| レジスタ `0x09` (版) | `0x06` | `0x06` |
| 電源投入の前のレジスタ `0x04` | `0x01` (カードあり) | `0x00` |
| 電源投入の後のレジスタ `0x04` | `0x81` | `0x00` のまま (ビット 7 が立たない) |
| レジスタ `0x03` (応答の長さ) | `0x01`、続いて `0x0d` (ATR) | `0x00` |
| バッファ (`0x40` から 13 バイト) | ATR | 意味のある内容にならない |

2 系統目の ASIE5606B 自体は応答します (版を読める) が、カードを検出せず、電源も入りません。ただし、2 系統目の電源に当たる GPIO (1 系統目では、値 `0xff`、mask `0x01`) は、2 系統目の分を特定しておらず、試していません。

### TS の受信 (ホストから、未達成)

選局してロックした状態で、ストリームを開始して端点 `0x81` から読む試験を、次の変えかたですべて試しましたが、**受信は 0 バイト**でした。

- 同期の読み出し (64 KB) と、非同期 URB を 8 本ずつ並べる方式。
- ストリーム開始 (`0x06`) の前に、フィルターの実行ビットを立てる方式 (CF レジスタ `0x40` の |= `0x09` または `0x08`)。
- coax の `px3` の順序 (TS ピンの設定、レジスタ `0x05`、ガード付きで 16 バイトのストリーム設定、ResetFilter (`0x09`)、CF レジスタ `0x41` と `0x43` = `0x1fff`、入力ビット `0x03`、実行ビット `0x08`、`0x06`)。
- レジスタ `0x05` を `0xa0` と `0x20` にした場合。
- TS ピンの設定の変えかた (複数)。

要求はすべて成功と応答され、ロックも保たれましたが、バルク転送のデータは来ませんでした。
ベンダーのドライバー自身も、標準のグラフではストリームを始められておらず (後の節)、ストリーム開始の順序は、記録として得られていません。

### 周期的な処理と、機器が消える現象

ベンダーのドライバーを入れた仮想マシンで、機器を開いている間の通信を `usbmon` で測ると、グラフを止めた後でも、次の要求が周期的に送られていました。

| 要求 | 周期 | 内容 |
|---|---|---|
| `0x02` (`wValue` = `0x044a`) | 437.5 ミリ秒 | ASIE5606 の `0x4a` のレジスタ `0x04` の読み出し (カードの状態) |
| `0x22` (`wValue` = 0、続けて 1) | 6.25 秒 | 意味は未確認。応答は `01` |

(GV-MVP/XZ の実装には、周期的な処理に当たるものがなく、ストリーム開始後に書き込みポインターを監視するスレッドだけです。)

ホストからの試験では、機器が、操作の後に USB のバスから消える現象が、繰り返し起きました。消えた機器は、物理的に挿し直さないと戻りません。ベンダーのドライバーで使っているときは、起きていません。
段階を分けて調べた結果は、次のとおりです (いずれも B-CAS カードを挿した状態)。

| 試験 | 結果 |
|---|---|
| firmware を送った直後から、周期的な処理 (上の表の 2 つの要求) だけを 240 秒送り、止めて 150 秒放置 | 消えない |
| ベンダーの記録の再現 (起動時の GPIO、復調器とチューナーの初期化表、ASIE5606 のフィルター設定。「選局」の前まで) を送り、周期的な処理を送らずに終了 | 終了後 20 秒以内に消える (選局、ストリームの開始、停止は不要) |
| 同じ再現のあと、周期的な処理を 200 秒続ける (458 回の読み出しと、要求 `0x22` を 32 回) | 続けている間は消えない |
| 上の続きで、周期的な処理を止める | 止めて 20 秒以内に消える |

このため、再現の書き込みのどれかが、機器側の監視 (ウォッチドッグとみられる) を働かせ、周期的な読み出しが途切れると、機器が落ちるとみられます。
周期的な処理を止めた直後ではなく、20 秒以内に消えるので、監視の期限は、数秒から 20 秒の範囲です。
**閉じる手順**

ベンダーのドライバーは、機器を閉じるとき (デバイスの停止) に、次の要求を、この順に送ります (`usbmon` の記録)。

| 順 | 要求 | 内容 |
|---|---|---|
| 1 | `0x07` (値 0、1) | ストリームの停止 |
| 2 | `0x03` (`0x4c`、レジスタ `0x80` = 0)、`0x21` (値 1) | 2 系統目のカード側 |
| 3 | `0x03` (`0x4a`、レジスタ `0x80` = 0、レジスタ `0x04` = 0、レジスタ `0x00` = 0) | 1 系統目のカード側 |
| 4 | `0x21` (値 0) | 開くときの `0x21` (値 `0x0100`) と対 |
| 5 | `0x08` (値 `0x00`、mask `0xd4`)、`0x08` (値 `0x08`、mask `0x08`) | 主 GPIO |

ホストで、再現を送り、周期的な処理を 10 秒続けたあと、この手順を送ってから周期的な処理を止めたところ、**120 秒、機器は消えませんでした**。周期的な処理を止めるだけの場合は、20 秒以内に消えます。
ホストの実装は、処理を終えるとき、この手順を送ってから周期的な処理を止めると、機器を残せます。
手順のうち、どの要求が効いているか (とくに、`0x21` の値 0 の要求) は、切り分けていません。

### 標準の DirectShow グラフ

仮想マシンで、標準のフィルターだけを使うグラフ (DVB-T のネットワークプロバイダー → `Digital Tuner_0` → `Digital Capture_0` → ヌルレンダラー) を組み、`usbmon` で通信を見ました。

| 段階 | 結果 |
|---|---|
| フィルターの追加、ピンの接続、`put_TuneRequest` | 成功。`Tuner` から `Capture_1` への接続は、`0x80040207` で拒否される |
| グラフの `Pause` | 成功 (`S_FALSE`、続く状態は `0x40268`) |
| チューナーの `Run` | 成功 |
| **キャプチャの `Run`** | **`0x8007001F` (ERROR_GEN_FAILURE) で失敗** |

- 新たに機器を開いた直後の最初の `Run` も、B-CAS カードの有無にかかわらず、同じ結果でした。通信は、機器の初期化 (GPIO、復調器の初期化表、ASIE5606 のフィルター設定、CF レジスタ `0x40` = `0x07`、`0x41` と `0x43` = `0x1fff`、要求 `0x0a`、レジスタ `0x05` = `0xa0`、要求 `0x21`) までで、**ストリーム開始 (`0x06`) とバルク転送は送られません**。失敗した転送や、応答のない転送はありませんでした。
- カードがあるときは、初期化の後に、上の `90 32` の交換まで進んでから失敗します。
- チューニングスペースを ISDB-T 風 (`ISDB_Terrestrial`) にしても、結果は変わりませんでした。
- 同じ機器を開いたまま `Run` を繰り返した場合、2 回目以降は、通信なしで即座に同じ結果になります。最初の失敗が、機器ごとの「開始済み」フラグを立てたまま戻さないためです (後述)。このため、**機器を開き直した直後の最初の `Run` だけ**が、試験として意味を持ちます。
- BonDriver_BDA が出す `RunGraph Failed` も、同じ、キャプチャの `Run` の失敗です。

### BDA ドライバーの Run の経路 (静的解析)

ドライバーを逆アセンブルして、キャプチャの `Run` が失敗する経路を調べました (実行はしていません)。

1. キャプチャピンの状態遷移の関数が、機器ごとの「開始済み」フラグが立っていれば、失敗 (`STATUS_UNSUCCESSFUL`、`ERROR_GEN_FAILURE` に対応) を返す。フラグを立てて、ストリーム開始の関数を呼び、戻り値が 0 以下なら失敗を返す (フラグは立てたまま)。
2. ストリーム開始の関数は、URB とバッファの確保 (戻りが非 0 なら、`0x06` を送らずに失敗)、続いて `0x06` の送信、の順に進める。
3. 確保の関数は、機器の異常ラッチが 1 のとき、またはメモリの確保に失敗したとき、失敗を返す。
4. 異常ラッチは、次の場合に立つ。
   - 制御転送がタイムアウト (`0x102`) したとき。これが立つと、以降の制御転送はすべて失敗する。**今回の記録には、該当する転送がなく、否定された。**
   - URB の完了処理で、機器のフラグ (チップの識別などから計算する値) のビット 7 が立っているとき。
   - ストリームの監視スレッドが、PID ごとのカウンターの不一致を続けて検出したとき。まだストリームが動いていないため、可能性は低い。

ストリーム開始の関数の手前には、別の分岐があります。機器ごとのモード (`+0x1953c`) が 1 のとき、ストリーム開始の関数を**呼ばずに**、失敗を返します。新しく開いた機器は、この分岐に当たったとみられます。ストリームの開始 (`0x06`) も、URB の確保も、送られない記録と合います。
モードを 0 にするのは、ドライバー固有の制御要求 (長さ 32 バイトの入力) を処理する関数だけです。この関数は、次の処理をします。

- 32 バイトの入力を受ける。関数の中に、16 バイトの定数が 2 つ埋め込まれている。
- 機器ごとの 16 バイトのバッファ (`+0x19580`) を、ASIE5606 のレジスタへ 16 バイトずつ書き込む (「TS の受信」の、ストリーム設定の 16 バイトに当たるとみられる)。
- 5 バイトの設定を ASIE5606 に書き、モードを 0 にする。

このため、ベンダーの BDA ドライバーは、ベンダー自身のユーザーモードの部品が、この制御要求で「解除」しないと、標準のグラフの `Run` を受け付けないとみられます。標準のグラフ (BonDriver_BDA を含む) が失敗するのは、この解除がないためと考えられます。
この要求を送る部品は、ベンダーのインストーラー (InstallShield の cab) の中にあるとみられますが、取り出して確認していません。ベンダーのドライバーで受信できたときの通信記録が、まだありません。
機器のフラグのビット 7 (前述) は、この件と別に、ストリームの停止を表すフラグとみられます。

ドライバーには、デバッグ出力の文字列がなく、ログからは原因が見えません。上の分岐は、静的な解析での推定で、実行時の値では確かめていません。

## cold の USB ID、個体の識別、cold への復帰

### cold の USB ID と機種

cold の USB ID から、機種や送るべき firmware の版は決まりません。次の表は、手元の INF と coax の資料で確認できた範囲です。

| cold の USB ID | 根拠 | 該当する機種 |
|---|---|---|
| `1738:5211` | I-O DATA のローダーの INF (`IODATA_AS11Loader.inf`、x86 と x64)、coax の `px3` の INF | GV-MVP/HZ2W (実機で確認)。PLEX の PX-S3U、PX-W3U3 など (coax の資料による。実機では未確認) |
| `1738:5216` | coax の INF と docs だけ | 資料に機種の記載なし |

warm の USB ID は、HZ2W が `04bb:0526`、coax の `px3` が扱う PLEX の機種が `0b06:0001`、`0003`、`0004`、`0005`、`0006` です。
Quixun と SKNET の cold の USB ID は、INF が手元になく確認できていません。

このため、HZ2W の firmware (起動アドレス `0x5583`) を `1738:5211` の機器へ送ると、他社の機器に当たる可能性があります。ホストの `Hz2wFirmware` を置いた利用者だけが対象になる設計は、この理由によります。

### cold の機器から読める情報

2026-11-24 に、cold の HZ2W (`1738:5211`) へ、読み取りだけの要求を送りました。

| 要求 | 結果 |
|---|---|
| `0x0c` (GetCusInfo) | EPIPE (STALL) |
| `0x17` (値 2) | EPIPE |
| `0x02` (I2C `0xa8`、`0xa0`、`0x4a` のレジスタ 0 と 1) | EPIPE |

cold のブートローダーは、firmware の送信 (`0xab`、`0xac`) 以外のベンダー要求を実装していないとみられます。cold の段階で、基板が HZ2W かどうかを機器から読んで確かめる手段は見つかっていません。標準のディスクリプターにも、基板固有の値はありません (製造元 `ASICEN`、製品名 `AUSBDTV`、`bcdDevice` が `0001`、シリアル番号なし)。

### 個体の識別

warm の EEPROM (I2C `0xa8`、256 バイト) を、2 回読んで同じ内容であることを確かめました。

| 範囲 | 内容 |
|---|---|
| `0x00`〜`0x35` | `ae 36`、VID/PID `04bb 0526`、`"I-O DATA  "`、`"GV-MVP/HZ2W     "`、`"GV-MVP/HZ2W IR "` |
| `0x36`〜`0x38` | `03 ff 0e` (最後の `0e` の上位 2 ビットが筐体内の位置で、値は 0) |
| `0x39`〜`0xbf` | すべて `0x00` |
| `0xc0`〜`0xff` | すべて `0xff` (未書き込み) |

先頭 57 バイトは、`GetCusInfo` の応答と一致します。シリアル番号や製造番号に当たる値はなく、読んだのは 1 台だけですが、個体で変わりうる場所は `0x00` か `0xff` で埋まっています。warm のディスクリプターにもシリアル番号がありません。
複数台の接続を区別できる値は、USB のポート位置 (デバイスパス) だけです。ホストのリーダー名の ID は、デバイスパスのハッシュで作るため、ポートを差し替えると変わります。

### cold へ戻す手段

warm の機器を、USB の抜き差しなしで cold に戻す手段は、見つかっていません。

| 手段 | 結果 |
|---|---|
| `USBDEVFS_RESET` (usbfs の `ioctl`、ポートのリセット) | 実機で試験した。ioctl は成功し、dmesg に `reset high-speed USB device` が出たが、機器は同じアドレスの warm (`04bb:0526`) のまま。20 秒後も変化なし。firmware は RAM に残る |
| ウォッチドッグを働かせて周期処理を止める | 約 20 秒で機器が USB から消える。cold にも戻らず、抜き差しが要る (「周期的な処理と、機器が消える現象」) |
| 自然な復帰 | 2026-11-23 に 1 回だけ、warm が cold に戻った。原因は不明 |
| ハブのポートの電源の操作 | 試験した。検証ホストのハブ (`05e3:0610`) は ganged power switching で、ポート単位では VBUS が切れず、機器は warm のまま残った |

GV-MVP/VZ (NXP SAA7164 系) の資料 (waya0125/recgvmvp の `docs/GV-MVP-VZ.md`) でも、`--reset` (同じ `USBDEVFS_RESET`) は、`kill -9` などでウォッチドッグがロックした状態からの復帰用です。cold に戻す手段としては書かれていません。VZ の cold は `bcdDevice` が `0x0100` 以外の DFU モードで、電源投入直後と USB の抜き差しの直後にだけ現れます。

## 内蔵カード (B-CAS) だけの実装

TS の受信が未達成のため、1 系統目の内蔵カードだけを、ユーザー空間のホスト (`DriverHost_PX4`、WinUSB と macOS) に実装しました。Linux のカーネルモジュールは対象外です。

| 層 | ファイル | 内容 |
|---|---|---|
| 共通層 | `driver/common/hz2w/hz2w_core.c`、`hz2w_card.c` | firmware の送信、起動時の GPIO、周期処理の要求、閉じる手順、ASIE5606B のカード手順 (上の「カードインターフェース」の再現) |
| ホスト | `host/devices/hz2w_device.cpp` | `Type=HZ2W`。受信機の定義を持たない (定義があると起動を拒否する)。周期処理のスレッドと、カード API |
| 試験 | `tests/hz2w_core_test.c` | 模擬機材 (ASV5211 と ASIE5606B の 0x4a) による 122 項目。要求の符号化、ATR、T=1 の交換、バッファのページ、電源投入の失敗と復旧 |

**動作**

- cold (`1738:5211`) の定義は、firmware (`Hz2wFirmware`、既定は `asv5211-firmware.bin`) を送ります。機器が再列挙するため、この定義の `Init()` は `-ENODEV` で終わり、ログに失敗が 1 行出ます。約 4 秒後に warm (`04bb:0526`) の定義が改めて `Init()` されます。
- warm の `Init()` は、`GetCusInfo` の VID/PID の確認、起動時の GPIO、リセットのパルス、ASIE5606B の版の確認、カード検出の準備までを行い、直ちに周期処理 (437.5 ミリ秒ごとのレジスタ `0x04` の読み出しと、6.25 秒ごとの要求 `0x22`) のスレッドを始めます。周期処理は、カードを開いていない間も続けます (止めると約 20 秒で機器が USB から消えるため)。
- 終了時は、カードの電源を切り、ベンダーの閉じる手順を送ってから周期処理を止めます (逆順にすると機器が消える)。
- SCARD の `Reset` は、電源投入と ATR の受信です。`Transmit` の T=1 ブロックは、1 ブロックごとに ASIE5606B のバッファへ書き、実行し、応答を読んで受信バッファへ入れます。UART の FIFO は無いため、`smart_card.cpp` からは「書き込みが終わると読み出せる」装置に見えます。
- リーダー名は `I-O DATA GV-MVP/HZ2W Smart Card Reader (ID: …)` です。2 系統目 (`0x4c`) のスロットはつながっていないとみられるため、リーダーは 1 つだけです。

**DriverHost が強制終了されたとき**

DriverHost_PX4 を `TerminateProcess` や、ログオフに伴うプロセスの終了で止めると、閉じる手順が送られず、機器が約 30 秒で USB から消えます (確認済み。復帰は、USB の抜き差し)。通常の終了 (アイドル終了、シャットダウン) では閉じる手順が走り、機器が残ります。強制終了の後に機器が見えなくなったときは、USB を挿し直してください。

**未確認の条件** (自動試験は実機の代用ではありません)

- cold からの firmware 送信と再列挙は、Windows 版でだけ確認しました (Linux 版と macOS 版は未確認)。
- macOS 版の実機での動作。Linux (libusb) 版と Windows 版は、上のとおり確認しました。Windows の WinSCard 経由は、上の「WinSCard 経由の確認」で確認しました。x86 版の DriverHost は未確認です。
- 受信との同時利用 (受信が未達成のため、対象がない)、数時間以上の動作、USB の抜き差し中のカード操作、カードの抜き差し、複数台の接続。
- B-CAS の ECM 用の命令 (`90 34`) は、保存した TS の復号 (上の「レビュー指摘への対応後の確認」、先頭 40 MB) で、HZ2W のカードでも成功しました。復号しながらの長時間の動作と、受信と同時の復号は未確認です。
- バッファの 3 ページ目 (128 バイトを超えるブロック)。1 ブロックは 128 バイトまでに制限しています。
  ホストは `CardDevice::MaxCardBlockSize()` でこの上限を T=1 層へ伝え、IFSD を LRC で 124、CRC で 123 に下げて通知します。
- 応答の長さ (レジスタ `0x03`) の待ち方は、T=1 の応答では「命令の実行の 120 ミリ秒後から、4 バイト以上で 2 回同じ値」です。ベンダーは固定の待ちで読むため、この判定は実装側の設計です。
- cold の USB ID (`1738:5211`) は、ASV5211 を使う他社の機器と共通の可能性があります (「cold の USB ID と機種」)。cold の段階では、機器から基板の種類を読めません。`Hz2wFirmware` のファイルが置かれている間、その機器にも HZ2W の firmware を送るため、他の ASV5211 機器を同じ PC で使うときは、ファイルを外してください。
- WinUSB の INF (`I-ODATA-GV-MVP-HZ2W.inf`) は、`sign.ps1` で `px4_drv_winusb.cat` を再生成して含めました (`verify.ps1` が全 INF で通る)。このカタログでの導入は、Windows 10 の仮想マシンでは、同じ INF だけの試験用カタログで確認しました。再生成したカタログ自体の導入は未確認です。

## 実装の段階

AGENTS.md の方針どおり、受信結果の維持と、長時間の安定を完了条件に含めます。
各段階は、前の段階の確認が済んでから進めます。

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0 | firmware の取り出し | 済み。`asv5211fw` が x86 と x64 のローダーから、SHA-256 `39428b36…` の firmware を取り出す |
| 1 | cold から warm への起動 (vendor 要求 `0xab` を 3 回、`0xac` を 1 回、wIndex は起動アドレス) | 実機 (WinUSB、検証 PC) で、cold の `1738:5211` が `04bb:0526` に出直すことを確認済み。送る手順は coax と recfriio の記述と一致した。ホスト (Windows、macOS) への組み込みは、内蔵カードのためのものとして実装済み (「[内蔵カード (B-CAS) だけの実装](#内蔵カード-b-cas-だけの実装)」)。失敗時 (誤ったアドレスなど) の抜き差しでの回復の確認は未実施 |
| 2 | 調査 (`GetCusInfo` `0x0c`、I2C 読み出し、GPIO) | 一部済み。`GetCusInfo`、GPIO、ドライバーの起動時の GPIO の再現、ASIE5606B の応答 (`0x4a`、`0x4c`) を確認した。復調器 (`0x30`、`0x34`) の読み出しの形式と、チューナーの型番は未確定。I2C への書き込みは、レジスタのポインターの設定を超えるものを行っていない (1 バイトの書き込みで受信が止まる例が UT100B にあるため) |
| 3 | 復調器とチューナーの初期化と選局 | 地上波のチャンネルで、ロック (復調器の状態レジスタ) と C/N の値が得られる |
| 4 | TS の受信 (ブリッジの TS 出力、同期バイト、ヌルパケットのフィルター) | 地上波の 10 分以上の受信で、ドロップ 0、TEI、連続性エラー、同期ずれを数える |
| 5 | カード (スロットがある場合) | 内蔵カードで、B-CAS の APDU と復号。TS の受信と同時に実行する |
| 6 | 配布 (Linux のカーネルモジュールか、ユーザー空間のホストか) | 他機種との整合 (機種の識別は `DeviceDefinition` と USB の VID/PID の組、ほかの機種との共有は電源と TS の形式を確認してから) |

段階 1 の前提として、Linux のカーネルドライバーに ASV5211 を加えるか、ユーザー空間のホスト (`DriverHost_PX4`) に加えるかを決める必要があります。
既存の方針では、ブリッジごとの差を機種別デバイスに閉じ込めます。
ASV5211 は IT930x と別系統のため、`driver/common/bridge/` に別のブリッジ実装を置く構成が、既存の構造に近いと考えられます。

## 実機で最初に取るデータ

実装の前に、次を取ると、未確認の事項の多くが確定します。

1. **基板の写真**: 主要チップの刻印 (ASICEN の ASV5211 のほか、復調器、チューナー、ASIE5606 の有無)。
2. **USB の識別情報**: 済み (cold と warm のディスクリプターは、「[実機で分かったこと](#実機で分かったこと)」に記載)。`lsusb -v` の形式の記録が要る場合は、Linux で取り直してください。
3. **通信記録** (純正ドライバーの、選局と受信): 起動時の記録は済み (「[ベンダーのドライバーの起動時の通信 (usbmon)](#ベンダーのドライバーの起動時の通信-usbmon)」)。残りは、選局と受信の開始までの記録です。I2C の書き込みの列、`0x30` と `0x34` への初期化、TS のストリームの開始が読み取れます。
   純正ドライバーは、古いクロス署名のため、Windows 11 では読み込めません。Windows 10 の仮想マシンで読み込み、ホストの `usbmon` で記録する方法を使えます (「[ベンダーのドライバーの動作環境](#ベンダーのドライバーの動作環境)」)。選局には、仮想マシンの画面で、選局できるアプリを動かす必要があります。

取得した通信記録には、機器のシリアル番号やカードの情報が含まれる場合があります。
公開の資料に載せる前に、該当部分を除いてください。

## 参考: 他の ASV5211 機種との違いを確認する順序

HZ2W は、PX-S3U 系と同じブリッジを使いますが、基板の構成が同じとは限りません。
AGENTS.md の「機種に関する前提」にあるとおり、電源、GPIO、入力数、TS の形式、カードリーダーの有無は、製品名が似ていても異なることがあるため、段階 2 の調査結果を coax の `px3` の資料と照らして、一致を確認できた部分だけを共有します。
